# MealKit decision log

Decisions that changed or set the engine's direction, and features not included or deferred. Future plans and order are in `docs/ROADMAP.md`, implementation details of finished items in `docs/CHANGELOG.md`, design answers in `docs/CODING_MODEL.md`.
New features follow the ROADMAP order and the "Deferred" table below. When a decision changes, add a new row to "Decision log" (don't delete the old row; note what changed), and update the corresponding parts of ROADMAP and CODING_MODEL too.

## Decision log

| Date | Decision | Reason and impact |
|---|---|---|
| 2026-10-15 | **Minimum spec: Intel 11th gen (Xe integrated graphics) or newer** | Shader Model 6.6 bindless is available, simplifying texture, material, and GPU culling code. 10th gen and older office PCs aren't supported. Updated requirements in `docs/GUIDE.md`. Xe-LP doesn't support mesh shaders, so they stay unused. CPU instructions (up to SSE4.2, AVX/FMA off) are a determinism rule and aren't changed |
| 2026-10-15 | **Godot-style general-purpose editor** (one editor + a game DLL per project) | Game code hot reload with the editor left open, a project manager. In exchange, a DLL boundary and versioning appear. The shipping exe stays static single (stage 0) |
| 2026-10-15 | **Separating players and characters: `PlayerSlot` / `Pawn` / `Controller`** (Unreal-style possession, as data without inheritance) | Respawn, spectating, mounting, AI characters, and mid-match joining sit on the same structure. No Actor inheritance tree; flat arrays + id order are kept (determinism debugging, lightness). Put in stage 0 to do it together with the template restructuring |
| 2026-10-15 | **AI runs deterministically inside the simulation** | Every peer does the same computation, so it costs no bandwidth and is unrelated to the `kInputBytes` (8 bytes) limit. In exchange, AI code also follows the determinism rules (deterministic math utils, fixed order). `--bot` stays as a test tool that generates and sends input |
| 2026-10-15 | **Allowing pose sampling for the simulation** (for active ragdolls) | The original rule was "animation results must not enter the simulation". For ragdoll target poses, the simulation may use poses only via a deterministic path separate from the visual one (tick time, arithmetic interpolation, deterministic math utils). Visual animation remains display-only (stage 2) |
| 2026-10-15 | **One answer per problem** (`docs/CODING_MODEL.md`) | For each design question like global access, object composition, pooling, async, and events, settle on one answer; the engine provides only those tools and blocks other approaches with the `sim/` check. Questions not in the table are added to the document first. In exchange, runtime component composition and "access from anywhere" convenience are given up |
| 2026-10-15 | **Game UI is designed in Penpot → the plugin exports to `.ui` → our own retained-mode runtime** (changes the same day's "custom immediate mode" decision) | Lets non-programmers design visually, like UMG or UI Toolkit. Penpot instead of Figma: it's open source so it can be self-hosted, its layout is CSS flex/grid so it's easy to match in the runtime, and it has a plugin API. No UI designer inside the editor (the largest development cost disappears). In exchange, Penpot's layout/text computations must be replicated exactly (verified with pixel comparison), and a TypeScript plugin and Node.js dev tools appear. The Penpot source is the reference and `.ui` is generated (stage 1) |
| 2026-10-15 | **Multi-style text supported from the start** | Brings in Penpot text style spans (only part bold, numbers in a different color, etc.) as is. Adding it later would mean redoing text layout, bindings, and the localization format. Localization strings mark spans with numbered tags (`<1>…</1>`) (stage 1) |
| 2026-10-15 | **Debug UI is Dear ImGui** (Editor/Dev builds only) | Dev screens are built quickly in code. Not mixed with game UI, and ImGui isn't linked into the shipping exe. Cheats are sent only via lockstep input (stage 1) |
| 2026-10-15 | **Graphics content is made visually in external tools** (the engine only reads standard formats and draws) | Models/materials/animations are Blender → glTF, textures are PNGs from painting tools, effects are an external effect tool (candidate Effekseer), color grading is LUTs. The same principle as the Penpot decision for game UI. Not building an engine material editor, shader graph, or particle editor keeps development and runtime light, and artists use tools they know. In exchange, materials outside the glTF supported range can't be used, and since external → engine turnaround becomes important, asset hot reload is pulled from stage 4 to stage 2. Only the engine has shader code (stage 2) |
| 2026-10-15 | **Shaders are style presets, post is one uber pass, feedback is events → feedback table** | Artists only choose the lighting model and material features and don't write shaders. Combinations are fixed so PSOs can be built ahead of time, with no hitches. Post is merged into one pass because of integrated graphics bandwidth. Impact feel (sound, effects, shake, screen freeze) is set in a data table so sound/VFX people can tune it alone. Hit stop freezes only the view (lockstep). The GPU budget is divided per feature and shown by the benchmark and the performance panel (stages 1·2) |
| 2026-10-15 | **Art workflow tools before graphics features** (Blender add-on, asset budget warnings, graphics regression tests, GPU capture/view modes) | Under the external tool principle, artists need to know engine rules (`extras` keys, budgets) inside their tool. The add-on plays the same role as the Penpot plugin and reads the engine schema so it doesn't drift. Regression tests automatically catch rendering breaking when shaders change. Lighting is HDRI ambient light + baked reflection probes + a few point lights per object, keeping the integrated graphics budget without real-time GI or reflections. One Blender LTS version and a Python add-on must be maintained (stage 2) |
| 2026-10-15 | **Stage 1 order: input action mapping, gamepads, debug UI, and localization before game UI** | Game UI depends on localization (the numbered-tag string format) and input action mapping (focus movement, confirm/back, key hint icons). Building UI first would mean redoing bindings, focus, and the string format. Debug UI is small and helps debug the work after it (stage 1) |
| 2026-10-15 | **Settings are outside the simulation** | Display, sound, key, and sensitivity settings live in the user data folder, aren't put in the content hash, and aren't read from `sim/`. Values that affect controls are applied only on the client before input quantization (stage 1) |
| 2026-10-16 | **The engine handles only what it must, and uses finished external things for the rest** (changes "external libraries only when truly needed") | The engine handles only the deterministic simulation, lockstep networking, renderer, and editor (placement, import, checks, debugging). External authoring tools are used actively, and runtime libraries are preferred over building our own too. Conditions for runtime libraries: determinism verification if they touch the simulation, source included/version pinned, permissive license, within the shipping exe budget |
| 2026-10-16 | **Assets are referenced by one path, only what's reached goes into the pack when shipping, and loading/unloading is per match** | Unlike Unity, there aren't three answers (Resources / AssetBundle / Addressables). Only paths, without GUIDs or `.meta` files, and renaming makes the editor fix references. Async loading, streaming, and DLC packs are deferred (stage 4) |
| 2026-10-16 | **Saves: snapshots inside a match, progress data as `SaveData` field declarations + user data folder + Steam Cloud. No account servers/DBs in the engine** | Lockstep P2P has no authoritative server, so preventing tampering with progress data would need service operations. Accounts, rankings, and storage are mostly covered by Steam. Progress values that affect a match are confirmed and sent to everyone as "match start data" (stage 1) |
| 2026-10-16 | **Cameras are virtual cameras + brain blending + impulses, cutscenes are Blender camera animations** (changes stage 4 "Camera templates") | Cinemachine-like usage built only inside `view/` (unrelated to determinism). No timeline editor. Cutscene starts are tick events so everyone sees them on the same tick, and the simulation doesn't stop |
| 2026-10-16 | **The main language is C++20 (a narrow subset enforced by SimCheck)**. Not changed after reviewing Rust | Same performance and determinism. Rust's memory safety benefit is small because `sim/` already bans pointers, allocation, and globals and uses only Pool ids. On the other hand, the borrow checker clashes with game code that "passes World mutably to modify several Pools", the unstable ABI makes DLL hot reload hard, and Jolt, Effekseer, Steamworks, ImGui, PIX, and Tracy are all C/C++. CMake's inconvenience is accepted |
| 2026-10-16 | **Reusable features are source modules** (not built-in engine features, not prefabs alone, not binary plugins) | A module is a folder holding `sim/`, `view/`, `.ui`, tuning, and prefabs, copied as source into the project, modified freely, and updated the way the upgrade tool works. Module functions take only their own state and are called by `World::step()`. Stage 4 "Damage/health" and "Basic object kinds" move to official modules instead of engine features |
| 2026-10-16 | **The engine decides the project folder layout** (top level + `assets/` kind folders, free inside kind folders, sources in `art/`) | Removes time spent deliberating over folder layout. Asset references stay paths, and moves are done in the editor asset browser (stage 4), which fixes references. Per-feature bundles are handled by source modules (stage 1) |
| 2026-10-16 | **External libraries are source copies + a `mealkit.txt` per folder, notices are generated** (no vcpkg or submodules). Games follow the same rule in the project's `third_party/` | Offline, pinned versions, static exe. Game libraries can't be used in `sim/`, and Export checks licenses and budget (stage 1) |
| 2026-10-16 | **Separating data and code at the very start of stage 1** (project settings, view tuning, sample cleanup, definition data tables) | Settle the answer for where numbers go (tuning / scene / view tuning / tables / code) and fix the sample to follow it. The sample is the template, so without fixing it now every project would copy numbers in code. View values are unrelated to the content hash, so they apply immediately even during multiplayer (stage 1) |
| 2026-10-16 | **v1.0 = contracts frozen after shipping one real game** | The point of freezing the API, file formats, and `sim/` rules is decided by real shipping experience, not feature count. Until then (0.x) things may change and are migrated with the upgrade tool |
| 2026-10-16 | **Details of finished items go to `docs/CHANGELOG.md`** | ROADMAP holds only future plans, and finished items are shortened to one line. Implementation details were burying the plan and making it hard to read |
| 2026-10-16 | **Strings (`std::string`) go into field declarations. Banned in simulation state** | Project settings (names, paths) and future `.table` row names/string keys use the same answer. Fixed-length strings could go into state, but length limits and truncation would need handling. State is copied and hashed byte-wise, so `game::Simulation` blocks it with `static_assert` (names in data, ids in state) (stage 1 project settings) |
| 2026-10-16 | **`mealkit.project` uses the same "path value" format as `.tuning`, game items with a `game.` prefix** | Read and written with one field declaration mechanism. Old "key=value" lines are read too, and `build.bat`, `editor.bat`, and the upgrade tool read both formats. Game items are `GameClass::ProjectSettingsType` (optional, `kApiVersion` 7). Engine common items are all excluded from the hash for now; items that aren't MEALKIT_VIEW_FIELD are hashed. The scene list needs a string list field, so it's added when a use appears (multiple scenes, packs) (stage 1) |
| 2026-10-16 | **Editor UI uses `tr()` keyed by English source text + per-language tables, Korean by default** (changes "editor UI is Korean") | Lets users choose Korean or English. On-screen text in code is written in English and `engine/res/strings/ko.txt` provides Korean. Separate from game UI's key approach (`docs/CODING_MODEL.md` "Editor UI strings and languages") |
| 2026-10-16 | **The project manager renames the game (= exe name) and moves the project folder** | Edited directly in the list, like Godot. The name is the CMake target/exe/DLL name, so `tools\rename_project.ps1` changes names from the template files and sample together and deletes `build\` (rebuild). When moving the folder, `build\` contains absolute paths so it's deleted too. Both are blocked for sample projects in the engine repo |
| 2026-10-16 | **Stage 1 is risk checks → data separation → starting the first game project, then in the order the game gets blocked** | Starting the game after building every engine feature puts v1.0 (shipping a real game) too far away and builds unneeded features. Minimum spec hardware, cross-PC determinism, and Steam can be checked in a day or two, but a failure would change the graphics plan and deferral decisions, so they go first. v0.5 = the first game can be shipped end to end (stage 1 items that game doesn't need may remain) |
| 2026-10-16 | **Non-input commands are one confirmed command channel** | Cheats, input delay changes, and votes aren't squeezed into the 8-byte input and don't modify state directly. The host attaches a tick number, confirms them, and distributes them with input, and they're processed in a fixed order at the very start of `World::step()`. They go into replays too (stage 1, `docs/CODING_MODEL.md`) |
| 2026-10-16 | **Time values: seconds in data, integer ticks in `sim/`** | So the tick rate (30/60 Hz) can be changed via project settings without fixing tuning or tables. Rounded once on load, so float time doesn't enter the simulation. In exchange, time values are rounded to one-tick units (during stage 1 view tuning) |
| 2026-10-16 | **Engine/editor background work is one thread per feature + locked queue + main thread handling** | Keeps file watching, the UI import server, and music streaming from each using different approaches (callbacks, event loops). State is modified in one place, the main thread. The async rule for game code (Job System + polling) stays as is |
| 2026-10-16 | **For game UI, the `.ui` runtime first, the Penpot plugin when a designer appears. Verification is mainly layout box comparison, pixel comparison is secondary** | The Penpot source → `.ui` decision stays. The plugin, import server, and comparison checks are big jobs, and if the first game has no designer, nobody would use them. Before that, `.ui` is written by hand, and since the format is the same nothing needs changing later. Penpot text is drawn by the browser so pixels can't be exactly the same, so layout matching is judged by per-node position/size. The import server blocks writes from other web pages with token/Origin checks (stage 1) |
| 2026-10-16 | **Mark not-yet-existing answers in CODING_MODEL with (stage n)** | Answers and the existence of tools weren't distinguished, leading to searching for nonexistent tools or working around them on the game side. When a marked tool is needed, don't work around it; pull that item forward |
| 2026-10-16 | **Games aren't built together in this repo. Features are verified with reference samples** (changes "stage 1 … starting the first game project" and "v1.0 = after shipping one real game") | The user has built games with several engines and already knows the list of needed features. This document sets the order, and real-use verification is handled by reference samples in `samples/` (per genre, 4 or fewer). Engine items are done only when actually used in a sample. v1.0 freezes contracts after the reference samples pass Export and determinism checks on all tier-1 platforms. In exchange, problems that only appear in real shipping (store review, patch distribution, large content) may not surface before v1.0 |
| 2026-10-16 | **Multi-platform support: a platform layer + a thin RHI built by the engine, DX12 as the reference backend** (changes the absolute rule "DX12 only. No RHI") | Linux/Steam Deck, macOS, Android/iOS, and web are shipping targets (stage 5 order). OS APIs are called only behind `mealkit/platform/`, graphics APIs only behind `mealkit/rhi/`. The platform layer is done in stage 1 (before audio/input choose OS APIs), the RHI layer at the very start of stage 2 (before DX12 calls grow). New rendering features are built on DX12 first and other backends follow, without lowering features to a common denominator. External RHI libraries lack bindless or are heavy, so they aren't used. The editor stays Windows-only. Cross-platform crossplay is only between determinism groups that passed cross-platform `mp_test`. In exchange, each backend adds shader conversion, verification, and device testing costs, and stages 1·2 get that much longer |
| 2026-10-16 | **Consoles, editors on other OSes, and crossplay go into the plan** (deletes three rows of the same day's deferred table) | The goal is shipping on all of PC, mobile, web, and consoles, editors on Windows, macOS, and Linux, and crossplay where every platform joins one match. Only tier 1 (Windows, Linux, macOS) blocks v1.0; mobile, web, and consoles are tier 2. For crossplay, simulation code has no platform branches, connection comparison changes from exe hash to simulation version, the content hash uses only platform-common data, and direct Steam use is wrapped in an online service layer (common service candidate EOS). Console code is under NDA, so it lives in a private repo. Console certification requirements (suspend/resume, platform save APIs) are reflected ahead of time in the stage 1 save/app flow design. In exchange, device, account, and CI costs grow a lot and determinism must be verified per platform |
| 2026-10-16 | **Online features are one `mealkit/online/` layer, crossplay lobbies/relays are Epic Online Services** | Steam only reaches Steam and isn't on mobile, web, or consoles. EOS is free and covers every target platform, and EOS Connect logs in with Steam/console accounts without an Epic account. The layer and Steam backend are done in stage 1 (before saves/achievements use Steam directly), the EOS backend in stage 3 (verified on Windows before porting). Crossplay matches are always set up via EOS. In exchange, two SDKs (both outside the repo, Stub) and Epic developer portal management appear, and engine packet sizes may need to fit EOS P2P packet limits |
| 2026-10-16 | **Headless simulation and the CI build matrix move to stage 1** (headless pulled from stage 4) | Since crossplay is the goal, determinism across compilers/CPUs must be compared automatically on every commit. Headless is needed to produce per-tick hashes on CI runners without GPUs. CI is GitHub Actions, starting with Windows MSVC and clang-cl, adding Linux and macOS in stage 5 |
| 2026-10-16 | **Input delay has defaults and caps per platform kind** | Wireless, WebRTC, and console networks have different RTT from wired PCs. Within a match the delay is the same (lockstep) and set by the slowest peer, and the lobby warns above the cap. Values are filled in from measurements when each platform is started (stage 1 automatic input delay adjustment) |
| 2026-10-16 | **2D games aren't supported** | Same as the absolute rule (3D). 2D physics (Box2D etc.) would need one more determinism verification, and sprite/tilemap tools are outside the engine's scope. There is quad drawing for UI/particles, but it isn't extended into 2D game features |
| 2026-10-16 | **The engine license is MIT** (repo root `LICENSE`, copyright holder KingProtea99) | A permissive license like Godot's, the same kind as the libraries in `third_party/` (MIT/BSD/zlib/public domain), so games made with the engine only need to include notices. Console backends (private repo) follow SDK terms, so they're separate from this license. Publication timing, contribution rules, and sample asset licenses aren't decided yet |
| 2026-10-16 | **For other platforms, "checks and layers" go first and "full porting" goes later: stage 1 CI checks Linux/macOS headless determinism, and the stage 2 RHI builds DX12 + Vulkan backends together** (changes the same day's "RHI layer DX12 backend only, other backends in stage 5") | To reduce code to fix later, block the most expensive things to fix up front. Determinism is the hardest to trace once broken, so the headless build that runs without graphics is compared on every commit from day one on Linux x64 and macOS ARM64 Clang (the POSIX platform layer only that far). An abstraction needs two implementations so one API's assumptions don't leak, so the RHI is built together with Vulkan, and stage 2 graphics items finish on both backends together. Intel Xe on Windows can run both backends, so no more devices are needed. Conversely, Metal/WebGPU/console backends, mobile/web lifecycles, and editors on other OSes would be wasteful to build N times while features still change, so they're in stage 5. In exchange, stage 2 graphics work is two backends' worth |
| 2026-10-16 | **The README is a one-line English introduction + features only; usage docs later as a separate docs project** | Split the engine repo and docs like Godot's godot-docs. | 2026-10-19 | **Connection comparison uses determinism group + simulation version + content hash composition instead of the executable id** (changes "only identical executables") | The executable id (compile time) blocks even builds that changed only view code, and in principle blocks crossplay (stage 5) where exes differ per platform. Until real-device determinism is verified, different determinism groups (compiler/CPU) aren't accepted (ROADMAP stage 5 "until passing"). | 2026-10-19 | **Screen flow: session lifetime is the engine's `game::MatchService`, screens are the game template `app/Flow` + `.ui`** (`docs/CODING_MODEL.md` "Screen flow from title to results") | Hosting, joining, Steam lobbies, LAN room announcements, returning to the lobby, and leaving are network details (match numbers, late packets), easy to get wrong if written per game. To run several matches per session, `returnToLobby`, `matchIndex`, `openOffline`, `reset` were added to `LockstepSession`, and the simulation decides the end of a match (the game's `MatchPhase`, generalized by stage 4 "Game flow framework"). Lobby names, ready, and chat are session packets (outside ticks, outside recording). Existing games have `GameInstance::menus()` false, so command line behavior is unchanged |

Two backward spots were fixed: table file reading `game/Tables.h` → new folder `data/Tables.h` (`data::loadTable`, used by input, sound, and feedback below the game boundary), gamepad state `input::PadState` → `PadState` in `platform/Gamepad.h`. If a subsystem that really must be removed appears (a dedicated server without sound, etc.), add a CMake option and a row then |

## Deferred / not included

| Feature | Decision | Reason | Revisit when |
|---|---|---|---|
| 2D games (sprite renderer, tilemaps, 2D physics) | Not included | 3D is an absolute rule. 2D physics would need one more determinism verification. 3D games that look flat with an orthographic camera work with current features | - |
| Genre project templates (racing, co-op) + genre list in "New Project" | Deferred | Each template is a sample to keep in step with the upgrade tool; until samples settle the cost is upkeep, not use (2026-11-02) | When 2~3 reference samples are settled |
| Old graphics API backends like OpenGL/DX11 | Not included | RHI backends are only DX12, Vulkan, Metal, WebGPU. They don't fit the bindless/explicit barrier shape | - |
| External RHI libraries (SDL3 GPU, bgfx, Diligent, etc.) | Not included | They lack bindless or are large and dictate the renderer's shape. We build an RHI layer holding only what we use | When backend maintenance cost blocks engine development |
| Server-authoritative netcode (snapshot interpolation, prediction) | Not included | Lockstep has small bandwidth regardless of object count | When making a genre with dozens of players or more |
| Ray tracing, deferred rendering, GI | Not included | Exceeds the integrated graphics budget | - |
| Mesh shaders | Not included | The minimum spec (Xe-LP) doesn't support them. If GPU-driven rendering is needed, ExecuteIndirect + compute culling | When the minimum spec is raised again |
| Rollback netcode (GGPO style) | Deferred | My input reacts immediately, but every misprediction requires recomputing several ticks, exceeding the budget in games with thousands of objects. Instead "predict only my character's appearance" (stage 1) | When making a 1v1 versus/fighting game with few objects |
| GPU-driven rendering (GPU culling, ExecuteIndirect) | Deferred | CPU cost becomes nearly zero with tens of thousands of objects, but it's hard to implement and debug, and CPU culling suffices at the thousands level | When a real game measures a CPU bottleneck in render preparation |
| Forward+ (many lights) | Deferred | Hundreds of point lights become possible, but the culling pass costs on integrated graphics | Games with many lights like night maps or interiors |
| Fixed-point gameplay math | Deferred | Determinism independent of CPU/compiler, but Jolt is float so two systems would mix and new overflow bugs appear | When desyncs between different CPUs are actually found |
| Scripting languages (Lua, etc.) | Deferred | Instant editing and modding, but needs deterministic VM modifications, is tens of times slower than C++, and means debugging two languages. Stage 0 hot reload + tuning data captures most of the benefit | When hot reload isn't enough or modding becomes a goal |
| General ECS | Deferred | Good for tens of thousands of objects and flexible composition, but loses the current simple arrays and explicit execution order (good for determinism debugging) | When system/object counts can't be handled with the array structure |
| Unreal-style Actor inheritance hierarchy | Not included | Only the possession structure is borrowed (stage 0 "Separating players and characters"); no inheritance tree or virtual `Tick`. Execution order would hide and determinism debugging would get harder | - |
| Singletons, service locators, DI containers | Not included | Engine features are taken as arguments (`GameContext&`, `World&`). Global state breaks the shadow simulation (two Worlds) and hot reload (`docs/CODING_MODEL.md`) | - |
| Coroutines/async inside the simulation | Not included | Completion timing differs per PC causing desyncs, and coroutine frames can't be hashed or snapshotted. Tick timers and `enum` state machines are used | - |
| Shader graph, material editor inside the engine | Not included | Materials are made in Blender as glTF PBR. As shader combinations grow, the integrated graphics budget and compile time can't be managed | When looks impossible within the glTF range repeat across several games (even then as engine shader features) |
| Particle editor inside the engine | Not included | External effect tools handle it. If no suitable tool, field declarations + inspector preview | - |
| Game projects' own shaders ("surface function" HLSL snippets) | Deferred | The engine manages shader combinations and budgets. If added, technical artists would write only one `Surface surf(Input)` function and the engine attaches lighting, shadows, and fog (verified with shader hot reload) | When looks impossible with style presets, like water or lava, are truly needed |
| Screen-space outlines (depth/normal edges) | Deferred | Used only in toon styles and costs about 0.3 ms. Material inverted-hull outlines come first | When inverted-hull outlines aren't enough in a toon-style game |
| SSAO, depth of field, motion blur, SSR | Deferred | Exceeds the integrated graphics post budget (1 ms). AO is baked in Blender | When the minimum spec is raised or a "high quality" preset is made |
| SMAA | Deferred | Three passes + area/search textures burden the one-uber-pass principle and the post budget (1 ms). Starts with FXAA (inside the uber pass) | When there's art feedback that FXAA quality is lacking, or a "high quality" preset |
| UI designer inside the editor | Not included | Penpot handles it. The editor has only a preview panel.
