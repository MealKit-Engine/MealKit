# MealKit 결정 기록

엔진 방향을 바꾸거나 정한 결정과, 넣지 않거나 미룬 기능. 앞으로의 계획과 순서는 `docs/ROADMAP.md`, 끝낸 항목의 구현 상세는 `docs/CHANGELOG.md`, 설계 답은 `docs/CODING_MODEL.md`.
새 기능은 ROADMAP 순서와 아래 "보류" 표를 따른다. 결정이 바뀌면 "결정 기록"에 새 행을 더하고(지난 행은 지우지 않고 무엇을 바꿨는지 적는다), ROADMAP·CODING_MODEL의 해당 부분도 같이 고친다.

## 결정 기록

| 날짜 | 결정 | 이유와 영향 |
|---|---|---|
| 2026-10-15 | **최소 사양: Intel 11세대(Xe 내장 그래픽) 이상** | Shader Model 6.6 bindless를 쓸 수 있어 텍스처·머티리얼·GPU 컬링 코드가 단순해진다. 10세대 이하 사무용 PC는 지원하지 않는다. `docs/GUIDE.md` 요구사항 갱신. 메시 셰이더는 Xe-LP가 지원하지 않으므로 계속 쓰지 않는다. CPU 명령어(SSE4.2까지, AVX/FMA 끔)는 결정론 규칙이라 바꾸지 않는다 |
| 2026-10-15 | **고도식 범용 에디터** (에디터 하나 + 프로젝트별 게임 DLL) | 에디터를 켜 둔 채 게임 코드 핫 리로드, 프로젝트 관리자. 대신 DLL 경계·버전 관리가 생긴다. 출시 exe는 정적 단일 그대로 (0단계) |
| 2026-10-15 | **플레이어와 캐릭터 분리: `PlayerSlot` / `Pawn` / `Controller`** (언리얼식 빙의, 상속 없이 데이터) | 리스폰·관전·탑승·AI 캐릭터·중간 참가가 같은 구조 위에 놓인다. Actor 상속 트리는 만들지 않고 평평한 배열 + id 순서를 유지한다(결정론 디버깅, 가벼움). 템플릿 재구성과 같이 하려고 0단계에 넣는다 |
| 2026-10-15 | **AI는 시뮬레이션 안에서 결정론으로 돈다** | 모든 피어가 같은 계산을 해 대역폭이 들지 않고 `kInputBytes`(8바이트) 제한과 무관하다. 대신 AI 코드도 결정론 규칙(결정론 수학 유틸, 순서 고정)을 따른다. `--bot`은 입력을 만들어 보내는 테스트 도구로 남긴다 |
| 2026-10-15 | **시뮬레이션용 포즈 샘플링 허용** (액티브 래그돌용) | 원래 규칙은 "애니메이션 결과가 시뮬레이션에 들어가면 안 된다". 래그돌 목표 포즈를 위해, 화면용과 분리된 결정론 경로(틱 시간, 사칙연산 보간, 결정론 수학 유틸)에 한해 시뮬레이션이 포즈를 쓸 수 있게 한다. 화면용 애니메이션은 계속 보이기만 한다 (2단계) |
| 2026-10-15 | **한 문제에 한 답** (`docs/CODING_MODEL.md`) | 전역 접근·오브젝트 구성·풀링·비동기·이벤트 같은 설계 질문마다 답을 하나로 정하고, 엔진은 그 도구만 주며 `sim/` 검사로 다른 방법을 막는다. 표에 없는 질문은 문서에 먼저 추가한다. 대신 실행 중 컴포넌트 조합과 "아무 데서나 접근" 편의를 포기한다 |
| 2026-10-15 | **게임 UI는 Penpot에서 디자인 → 플러그인이 `.ui`로 내보냄 → 자체 유지 모드 런타임** (같은 날의 "직접 만든 즉시 모드" 결정을 바꿈) | 프로그래머가 아닌 사람도 UMG·UI Toolkit처럼 시각적으로 디자인하게 한다. Figma 대신 Penpot: 오픈소스라 직접 서버를 띄울 수 있고, 레이아웃이 CSS flex/grid라 런타임과 맞추기 쉽고, 플러그인 API가 있다. 에디터 안 UI 디자이너는 만들지 않는다(가장 큰 개발량이 사라짐). 대신 Penpot 레이아웃·글자 계산을 똑같이 만들어야 하고(픽셀 비교로 확인), TypeScript 플러그인과 Node.js 개발 도구가 생긴다. Penpot 원본이 기준이고 `.ui`는 생성물이다 (1단계) |
| 2026-10-15 | **여러 스타일 글자를 처음부터 지원** | Penpot 글자의 스타일 구간(굵게 일부만, 색이 다른 숫자 등)을 그대로 가져온다. 나중에 넣으면 글자 배치·바인딩·로컬라이제이션 형식을 다시 고쳐야 한다. 로컬라이제이션 문자열은 번호 태그(`<1>…</1>`)로 구간을 표시한다 (1단계) |
| 2026-10-15 | **디버그 UI는 Dear ImGui** (Editor·Dev 빌드만) | 개발용 화면은 코드로 빨리 만든다. 게임 UI와 섞지 않고, 출시 exe에는 ImGui를 링크하지 않는다. 치트는 락스텝 입력으로만 보낸다 (1단계) |
| 2026-10-15 | **그래픽 콘텐츠는 외부 도구에서 시각적으로 만든다** (엔진은 표준 형식을 읽어 그리기만) | 모델·머티리얼·애니메이션은 Blender → glTF, 텍스처는 페인팅 도구 PNG, 효과는 외부 효과 도구(후보 Effekseer), 색감은 LUT. 게임 UI의 Penpot 결정과 같은 원칙이다. 엔진 머티리얼 에디터·셰이더 그래프·파티클 에디터를 만들지 않아 개발량과 런타임이 가볍고, 아티스트가 아는 도구를 쓴다. 대신 glTF 지원 범위 밖 머티리얼은 쓸 수 없고, 외부 → 엔진 반영 속도가 중요해져 에셋 핫 리로드를 4단계에서 2단계로 당긴다. 셰이더 코드는 엔진만 갖는다 (2단계) |
| 2026-10-15 | **셰이더는 스타일 프리셋, 포스트는 우버 패스 하나, 연출은 이벤트 → 연출 표** | 아티스트는 조명 모델과 머티리얼 기능만 고르고 셰이더를 짜지 않는다. 조합이 고정돼 PSO를 미리 만들 수 있어 끊김이 없다. 포스트는 내장 그래픽 대역폭 때문에 한 패스로 합친다. 타격감(소리·효과·흔들림·화면 정지)은 데이터 표로 정해 사운드·VFX 담당이 혼자 고친다. 히트 스톱은 화면만 멈춘다(락스텝). GPU 예산을 기능별로 나눠 벤치마크와 성능 패널이 보여 준다 (1·2단계) |
| 2026-10-15 | **아트 작업 흐름 도구를 그래픽 기능보다 먼저** (Blender 애드온, 에셋 예산 경고, 그래픽 회귀 테스트, GPU 캡처·보기 모드) | 외부 도구 원칙이면 아티스트가 엔진 규칙(`extras` 키, 예산)을 도구 안에서 알아야 한다. 애드온이 Penpot 플러그인과 같은 역할을 하고, 엔진 스키마를 읽어 어긋나지 않는다. 회귀 테스트는 셰이더를 고칠 때 그림이 깨지는 것을 자동으로 잡는다. 조명은 HDRI 환경광 + 구운 반사 프로브 + 물체당 점광원 몇 개로, 실시간 GI·반사 없이 내장 그래픽 예산을 지킨다. Blender LTS 버전 하나와 Python 애드온을 유지해야 한다 (2단계) |
| 2026-10-15 | **1단계 순서: 입력 액션 매핑·게임패드·디버그 UI·로컬라이제이션을 게임 UI보다 먼저** | 게임 UI가 로컬라이제이션(문자열 번호 태그 형식)과 입력 액션 매핑(포커스 이동, 확인·뒤로, 키 안내 아이콘)에 의존한다. UI를 먼저 만들면 바인딩·포커스·문자열 형식을 다시 고쳐야 한다. 디버그 UI는 작고 이후 작업의 디버깅을 돕는다 (1단계) |
| 2026-10-15 | **설정은 시뮬레이션 밖** | 화면·소리·키·감도 설정은 사용자 데이터 폴더에 두고 콘텐츠 해시에 넣지 않으며 `sim/`에서 읽지 않는다. 조작에 닿는 값은 입력 양자화 전에 클라이언트에서만 적용한다 (1단계) |
| 2026-10-16 | **엔진은 꼭 필요한 부분만 맡고, 나머지는 완성된 외부 것을 가져다 쓴다** ("외부 라이브러리는 꼭 필요할 때만"을 바꿈) | 엔진이 맡는 것은 결정론 시뮬레이션, 락스텝 네트워크, 렌더러, 에디터(배치·가져오기·검사·디버깅)뿐이다. 외부 제작 도구는 적극적으로 쓰고, 런타임 라이브러리도 직접 만드는 것보다 우선한다. 런타임 라이브러리의 조건: 시뮬레이션에 닿으면 결정론 검증, 소스 포함·버전 고정, 허용 라이선스, 출시 exe 예산 안 |
| 2026-10-16 | **에셋은 경로 하나로 참조하고, 출시 때 닿는 것만 팩에 넣고, 매치 단위로 올리고 내린다** | 유니티처럼 Resources / AssetBundle / Addressables 세 가지 답을 두지 않는다. GUID·`.meta` 파일 없이 경로만 쓰고, 이름을 바꾸면 에디터가 참조를 고친다. 비동기 적재·스트리밍·DLC 팩은 보류 (4단계) |
| 2026-10-16 | **세이브: 매치 안은 스냅샷, 진행 데이터는 `SaveData` 필드 선언 + 사용자 데이터 폴더 + Steam Cloud. 계정 서버·DB는 엔진에 넣지 않는다** | 락스텝 P2P에는 권위 서버가 없어 진행 데이터 조작을 막으려면 서비스 운영이 필요하다. 계정·순위·저장은 Steam으로 대부분 된다. 매치에 영향을 주는 진행 값은 "매치 시작 데이터"로 모두에게 확정해 보낸다 (1단계) |
| 2026-10-16 | **카메라는 가상 카메라 + 브레인 블렌드 + 임펄스, 컷신은 Blender 카메라 애니메이션** (4단계 "카메라 템플릿"을 바꿈) | 시네머신과 같은 사용법을 `view/` 안에서만 만든다(결정론 무관). 타임라인 에디터는 만들지 않는다. 컷신 시작은 틱 이벤트로 모두 같은 틱에 보고 시뮬레이션은 멈추지 않는다 |
| 2026-10-16 | **주 언어는 C++20 (SimCheck가 강제하는 좁은 부분집합)**. Rust 검토 후 바꾸지 않음 | 성능·결정론은 같다. Rust의 메모리 안전 이점은 `sim/`이 이미 포인터·할당·전역을 금지하고 Pool id만 쓰므로 작다. 반면 빌림 검사기가 "World를 가변으로 넘겨 여러 Pool을 고치는" 게임 코드와 부딪히고, ABI가 고정되지 않아 DLL 핫 리로드가 어렵고, Jolt·Effekseer·Steamworks·ImGui·PIX·Tracy가 모두 C/C++이다. CMake의 불편은 감수한다 |
| 2026-10-16 | **재사용 기능은 소스 모듈** (엔진 기본 기능도, 프리팹만도, 바이너리 플러그인도 아님) | 모듈은 `sim/`·`view/`·`.ui`·튜닝·프리팹을 담은 폴더로, 프로젝트에 소스째 복사해 고쳐 쓰고 업그레이드 도구 방식으로 갱신한다. 모듈 함수는 자기 상태만 받아 `World::step()`이 부른다. 4단계 "데미지·체력", "기본 오브젝트 종류"는 엔진 기능 대신 공식 모듈로 옮긴다 |
| 2026-10-16 | **프로젝트 폴더 구조를 엔진이 정한다** (최상위 + `assets/` 종류 폴더, 종류 폴더 안은 자유, 원본은 `art/`) | 폴더 구조를 고민하는 시간을 없앤다. 에셋 참조는 지금처럼 경로이고, 옮기기는 에디터 에셋 브라우저(4단계)가 참조를 고친다. 기능 단위 묶음은 소스 모듈이 맡는다 (1단계) |
| 2026-10-16 | **외부 라이브러리는 소스 복사 + 폴더별 `mealkit.txt`, 고지문은 생성물** (vcpkg·서브모듈 안 씀). 게임도 프로젝트 `third_party/`에 같은 규칙 | 오프라인·고정 버전·정적 exe. 게임 라이브러리는 `sim/`에서 쓸 수 없고, Export가 라이선스와 예산을 검사한다 (1단계) |
| 2026-10-16 | **데이터와 코드 분리를 1단계 맨 앞에** (프로젝트 설정, 화면용 튜닝, 예제 정리, 정의 데이터 표) | 숫자를 둘 곳의 답(튜닝 / 씬 / 화면용 튜닝 / 표 / 코드)을 정하고 예제를 그 답대로 고친다. 예제가 템플릿이라 지금 고치지 않으면 모든 프로젝트가 코드 안 숫자를 따라 한다. 화면용 값은 콘텐츠 해시와 무관하므로 여러 명 플레이 중에도 바로 적용한다 (1단계) |
| 2026-10-16 | **v1.0 = 실제 게임 하나 출시 후 약속 고정** | API·파일 형식·`sim/` 규칙을 고정하는 시점을 기능 수가 아니라 실제 출시 경험으로 정한다. 그 전까지(0.x)는 바꿀 수 있고 업그레이드 도구로 옮긴다 |
| 2026-10-16 | **완료 항목 상세는 `docs/CHANGELOG.md`로** | ROADMAP은 앞으로의 계획만 담고, 끝낸 항목은 한 줄로 줄인다. 구현 상세가 계획을 덮어 읽기 어려웠다 |

| 2D 게임 (스프라이트 렌더러, 타일맵, 2D 물리) | 넣지 않음 | 3D가 절대 규칙이다. 2D 물리는 결정론 검증이 하나 더 든다. 직교 카메라로 평면처럼 보이는 3D 게임은 지금 기능으로 된다 | - |
| OpenGL·DX11 등 낡은 그래픽 API 백엔드 | 넣지 않음 | RHI 백엔드는 DX12·Vulkan·Metal·WebGPU만. bindless·명시적 배리어 모양이 맞지 않는다 | - |
| 외부 RHI 라이브러리 (SDL3 GPU, bgfx, Diligent 등) | 넣지 않음 | bindless가 없거나 크고 렌더러 모양을 정한다. 우리가 쓰는 만큼만 담은 RHI 층을 만든다 | 백엔드 유지 비용이 엔진 개발을 막을 때 |
| 서버 권위형 넷코드 (스냅샷 보간, 예측) | 넣지 않음 | 락스텝이 물체 수와 무관하게 대역폭이 작다 | 수십 명 이상 장르를 만들 때 |
| 레이트레이싱, 디퍼드 렌더링, GI | 넣지 않음 | 내장 그래픽 예산을 넘는다 | - |
| 메시 셰이더 | 넣지 않음 | 최소 사양(Xe-LP)이 지원하지 않는다. GPU 주도 렌더링이 필요하면 ExecuteIndirect + 컴퓨트 컬링으로 | 최소 사양을 다시 올릴 때 |
| 롤백 넷코드 (GGPO 방식) | 보류 | 내 입력이 즉시 반응하지만, 틀릴 때마다 여러 틱을 다시 계산해야 해 물체 수천 개 게임에서는 예산을 넘는다. 대신 "내 캐릭터 겉모습만 예측"(1단계) | 물체가 적은 1:1 대전·격투 게임을 만들 때 |
| GPU 주도 렌더링 (GPU 컬링, ExecuteIndirect) | 보류 | 물체 수만 개에서 CPU 비용이 거의 0이 되지만 구현·디버깅이 어렵고, 수천 개 수준에서는 CPU 컬링이 충분하다 | 실제 게임에서 렌더링 준비 CPU 병목이 측정될 때 |
| Forward+ (광원 다수) | 보류 | 점광원 수백 개가 가능해지지만 내장 그래픽에서 컬링 패스 비용이 든다 | 밤 맵·실내처럼 광원이 많은 게임 |
| 고정소수점 게임플레이 수학 | 보류 | CPU·컴파일러와 무관한 결정론이지만, Jolt가 float라 두 체계가 섞이고 오버플로 버그가 새로 생긴다 | 다른 CPU 사이 디싱크가 실제로 발견될 때 |
| 스크립트 언어 (Lua 등) | 보류 | 즉시 수정·모딩이 되지만, 결정론 VM 개조가 필요하고 C++보다 수십 배 느리며 두 언어 디버깅. 0단계 핫 리로드 + 튜닝 데이터화가 효과 대부분을 가져간다 | 핫 리로드로도 부족하거나 모딩이 목표가 될 때 |
| 범용 ECS | 보류 | 객체 수만 개·유연한 조합에 유리하지만, 지금의 단순한 배열과 명시적 실행 순서(결정론 디버깅에 유리)를 잃는다 | 시스템 수·객체 수가 배열 구조로 감당 안 될 때 |
| 언리얼식 Actor 상속 계층 | 넣지 않음 | 빙의 구조만 가져오고(0단계 "플레이어와 캐릭터 분리") 상속 트리·가상 `Tick`은 쓰지 않는다. 실행 순서가 숨고 결정론 디버깅이 어려워진다 | - |
| 싱글톤·서비스 로케이터·DI 컨테이너 | 넣지 않음 | 엔진 기능은 인자(`GameContext&`, `World&`)로 받는다. 전역 상태는 그림자 시뮬레이션(World 두 개)과 핫 리로드를 깨뜨린다 (`docs/CODING_MODEL.md`) | - |
| 시뮬레이션 안의 코루틴·async | 넣지 않음 | 완료 시점이 PC마다 달라 디싱크가 나고, 코루틴 프레임은 해시·스냅샷할 수 없다. 틱 타이머와 `enum` 상태 머신을 쓴다 | - |
| 셰이더 그래프, 엔진 안 머티리얼 에디터 | 넣지 않음 | 머티리얼은 glTF PBR로 Blender에서 만든다. 셰이더 조합이 늘면 내장 그래픽 예산과 컴파일 시간을 관리할 수 없다 | glTF 범위로 안 되는 모양이 여러 게임에서 반복될 때 (그때도 엔진 셰이더 기능으로) |
| 엔진 안 파티클 에디터 | 넣지 않음 | 외부 효과 도구가 맡는다. 맞는 도구가 없으면 필드 선언 + 인스펙터 미리보기로 | - |
| 게임 프로젝트의 자체 셰이더 ("표면 함수" HLSL 조각) | 보류 | 셰이더 조합·예산을 엔진이 관리한다. 넣는다면 테크니컬 아티스트가 `Surface surf(Input)` 함수 하나만 쓰고 조명·그림자·안개는 엔진이 붙이는 방식(셰이더 핫 리로드로 확인) | 물·용암처럼 스타일 프리셋으로 안 되는 모양이 꼭 필요할 때 |
| 화면 공간 외곽선 (깊이·법선 경계) | 보류 | 툰 스타일에만 쓰이고 0.3 ms 정도 든다. 먼저 머티리얼의 뒤집은 껍질 외곽선을 쓴다 | 툰 스타일 게임에서 껍질 외곽선이 부족할 때 |
| SSAO, 피사계 심도, 모션 블러, SSR | 보류 | 내장 그래픽 포스트 예산(1 ms)을 넘는다. AO는 Blender에서 구워 온다 | 최소 사양을 올리거나 "고품질" 프리셋을 만들 때 |
| 에디터 안 UI 디자이너 | 넣지 않음 | Penpot이 맡는다. 에디터는 미리보기 패널만 둔다 | - |
| Figma 연동 | 보류 | 클라우드 전용이고 REST API 호출 제한이 빡빡하다. `.ui`가 중간 형식이라 나중에 Figma 플러그인만 따로 만들 수 있다 | 디자이너가 Figma만 쓸 수 있을 때 |
| HTML/CSS·XAML UI 미들웨어, Rive | 넣지 않음 | 런타임이 크고 무겁다. 상태 전환(시간·이징)으로 기본 움직임은 된다 | 벡터 애니메이션이 게임의 핵심 연출일 때 Rive만 다시 본다 |
| UI 양방향 바인딩, 식 언어, 변환기 | 넣지 않음 | 단방향 뷰 모델 + 액션 하나로 정한다. 입력 위젯만 자기 필드에 쓴다 | - |
| UI 키프레임 애니메이션 (타임라인) | 보류 | 상태 전환으로 시작한다. Penpot 프로토타입 애니메이션은 가져오지 않는다 | 화면 연출 요구가 상태 전환으로 안 될 때 |
| UI 블러 효과 (레이어·배경) | 보류 | 내장 그래픽에서 비싸다. 플러그인이 경고한다 | 성능 예산에 여유가 확인될 때, 끌 수 있는 옵션으로 |
| 글자 모양 조합 (HarfBuzz) | 보류 | 한국어·영어·일본어는 필요 없다 | 아랍어·태국어·힌디어 지원이 필요할 때 |
| Recast 내비메시 | 보류 | 경사·다층 지형에서 정확하지만 큰 외부 라이브러리이고 결정론을 따로 검증해야 한다. 그리드·웨이포인트 길찾기(4단계)를 먼저 쓴다 | 넓은 열린 맵이나 복잡한 다층 지형에서 그리드가 부족할 때 |
| FMOD·Wwise (오디오 미들웨어) | 넣지 않음 | 유료 상용 SDK. 허용 라이선스·소스 포함 규칙과 단일 exe 예산에 맞지 않는다. 구조만 가져온다(위 결정 기록 2026-10-18) | - |
| 엔진 안 소리 타임라인 편집기 (FMOD Studio식) | 넣지 않음 | 클립 편집은 외부 도구(Audacity·Reaper·sfxr 계열)가 맡는다. 엔진은 이벤트 표와 [소리] 패널만 | - |
| Steam Audio (HRTF, 정밀 가림·반사) | 보류 | Apache-2.0으로 공개됐지만(도입 때 라이선스 다시 확인) 크고, 4단계 광선 가림·잔향 구역으로 시작한다 | 헤드폰 위치감이 게임의 핵심일 때 |
| 보이스 챗 | 보류 | 디스코드 권장 (`docs/GUIDE.md` "보이스 챗") | 게임 안 음성이 꼭 필요할 때 Steam Voice 선택 모듈 |
| Rust (엔진·게임 코드 언어) | 넣지 않음 | 위 "결정 기록" (빌림 검사기와 게임 코드, 핫 리로드, 생태계) | SimCheck로 못 막는 메모리 버그가 반복될 때 |
| 계정 서버·게임 DB (자체 백엔드) | 보류 | 서비스 운영 문제이고 엔진이 무거워진다. 계정·순위·저장은 Steam으로 | 진행 데이터 조작이 게임에 치명적이거나 Steam 밖 출시가 필요할 때. 그때도 외부 백엔드(Nakama 직접 운영, PlayFab 등)를 게임 모듈로 붙인다 |
| 서버 검증 (로드아웃·진행 데이터) | 보류 | 권위 서버가 없다. 협동·친구끼리 게임에서는 감수한다 | 경쟁 랭크 게임을 만들 때 (계정 서버와 같이) |
| 비동기 에셋 적재·스트리밍 (Addressables식) | 보류 | 매치 단위 동기 적재가 단순하고 순서 문제가 없다 | 로딩 화면이 길어지거나 열린 월드를 만들 때 (Job System 이후) |
| DLC·모드용 추가 팩 | 보류 | `.pak` 덧씌우기로 할 수 있지만 콘텐츠 해시·버전 관리가 늘어난다 | DLC나 모딩이 목표가 될 때 |
| 에셋 GUID·`.meta` 파일 | 넣지 않음 | 경로 참조 + 에디터가 이름 바꾸기 때 참조를 고친다. `.meta`는 버전 관리에서 짝이 어긋나는 문제가 크다 | - |
| 바이너리 플러그인 (게임 기능 DLL) | 넣지 않음 | 출시 exe는 정적 단일 파일이고 `sim/` 코드는 SimCheck를 통과해야 한다. 소스 모듈을 쓴다 | - |
| 엔진 안 타임라인·시퀀서 에디터 | 넣지 않음 | 컷신 카메라·애니메이션은 Blender에서 만든다 | 여러 캐릭터·소리·효과를 맞춘 긴 컷신이 게임의 핵심일 때 |
