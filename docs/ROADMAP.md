# MealKit 엔진 로드맵

엔진에 넣을 기능과 순서. 이 저장소에서는 게임을 만들지 않는다. 다른 엔진(Unity·Unreal·Godot 등)에서 게임에 필요했던 기능을 기준으로 정하고,
각 기능은 `samples/`의 기준 샘플로 검증한다(1단계 "기준 샘플").
끝낸 항목은 `[x]` 한 줄로 줄이고 구현 상세는 `docs/CHANGELOG.md`로 옮긴다. 순서가 바뀌면 이 문서를 고친다.

## 판단 기준

모든 기능은 아래 순서로 따져서 넣을지 정한다.

1. **3D + 멀티플레이를 해치지 않는가.** 시뮬레이션에 닿는 기능은 락스텝 결정론(`docs/GUIDE.md` "결정론 규칙")을 지켜야 한다.
2. **가벼움과 속도.** 목표 하드웨어는 Intel 내장 그래픽 사무용 PC, **최소 사양은 Intel 11세대(Xe 내장 그래픽) 이상**이다. 아래 예산을 넘는 기능은 끌 수 있어야 한다.
3. **여러 플랫폼, DX12가 기준.** OS API는 플랫폼 계층(`mealkit/platform/`), 그래픽 API는 얇은 RHI(`mealkit/rhi/`) 뒤에서만 부른다.
   새 렌더링 기능은 DX12 백엔드에서 먼저 설계하고 **Vulkan 백엔드는 2단계부터 같은 항목 안에서 같이** 만든다. Metal·WebGPU·콘솔 백엔드(5단계)는 따라간다. 다른 API에 맞추려고 기능을 낮추지 않고, 백엔드가 못 하는 기능은 그 플랫폼 프리셋에서 끈다.
   에디터는 Windows 먼저, macOS·Linux는 5단계. 목표는 모든 플랫폼 사이 크로스플레이다(플랫폼 표와 조건은 5단계).
4. **직접 만들지 않고 완성된 것을 가져다 쓴다.** 엔진이 맡는 것은 결정론 시뮬레이션(+ 물리 접착), 락스텝 네트워크, 렌더러, 에디터(배치·가져오기·검사·디버깅)뿐이다.
   - **외부 제작 도구**(Blender, Penpot, Effekseer 에디터, VS Code, DaVinci 등)는 적극적으로 쓴다. 게임 exe에 들어가지 않으므로 비용이 없다. 엔진은 가져오기·검사·미리보기와 도구용 플러그인만 만든다.
   - **런타임 라이브러리**(exe에 링크)도 직접 만드는 것보다 우선한다. 단 조건이 있다:
     화면 쪽(`view/`)만 쓰면 자유롭게, 시뮬레이션에 닿으면 결정론을 검증한 것만(Jolt처럼). 소스 포함·버전 고정(`third_party/`), 허용 라이선스(MIT/BSD/zlib/퍼블릭 도메인 등), 출시 exe 예산(5 MB) 안.
     모든 대상 플랫폼에서 돌아가는 라이브러리를 먼저 본다. 한 플랫폼의 기본 API(XAudio2, XInput, WIC 등)는 플랫폼 계층의 그 플랫폼 구현 안에서만 쓴다.

### 성능 예산 (최소 사양 Intel 11세대 Xe 내장 그래픽, 1280×720, 60 fps 기준)

"현재" 값은 최소 사양보다 빠른 Core Ultra 5 125U(Xe-LPG)에서 잰 것이다. 최소 사양 실기에서 다시 재야 한다.
이 표는 Windows 기준이다. 다른 플랫폼의 최소 사양과 예산은 그 플랫폼을 시작할 때(5단계) 같은 모양의 표로 정한다. 실행 파일 5 MB는 모든 플랫폼에 같다.

| 항목 | 예산 | 현재 |
|---|---|---|
| 프레임 전체 (GPU) | 8 ms 이하 (60 fps에서 절반을 여유로 남김) | 약 0.3 ms |
| 시뮬레이션 틱 (30 Hz) | 틱당 4 ms 이하 | 0.9~2.5 ms (바디 2,000개) |
| 드로우 콜 | 200회 이하 | 4회 |
| 네트워크 (4인, 호스트 송신) | 10 KB/s 이하 | 약 5 KB/s |
| 게임 실행 파일 | 5 MB 이하 (에셋 제외) | 약 1.4 MB |

## 버전

엔진 버전은 저장소 루트 `VERSION`. **v0.n = n단계를 끝낸 엔진**이다(0단계 → v0.4는 그 전 버전 번호를 이어받았다). 0.x 동안은 `GameInstance` API(`kApiVersion`)와 파일 형식이 바뀔 수 있고, 기존 프로젝트는 업그레이드 도구로 옮긴다.

| 버전 | 뜻 |
|---|---|
| v0.4 (지금 0.4.3) | 0단계: 에디터·핫 리로드·결정론 검사·디버깅 도구. 1단계 항목을 끝내며 템플릿이 바뀌면 0.4.x를 올린다 |
| v0.5 | 1단계: 게임 하나를 끝까지 낼 수 있는 기능 (플랫폼 계층, 데이터 분리, 소리, UI, 입력, 메뉴, 세이브). 기준 샘플이 타이틀부터 결과 화면까지 끝까지 돈다 |
| v0.6 / v0.7 / v0.8 | 그래픽(RHI: DX12 + Vulkan) / 멀티플레이 강화 / 게임플레이 프레임워크·모듈·툴 |
| v0.9 | 5단계 1군: Linux·Steam Deck, macOS 출시와 에디터, 1군 사이 크로스플레이(EOS). 2군(모바일·웹·콘솔)은 그 뒤 순서대로, v1.0을 막지 않는다 |
| **v1.0** | v0.9 이후, **기준 샘플이 모두 1군 플랫폼에서 Export·결정론 검사(`mp_test`, 플랫폼 사이 포함)를 통과**하고 **약속을 고정**한 버전: `GameInstance` API, 파일 형식(`.scene`, `.tuning`, `.table`, `.ui`, `mealkit.project`, 세이브), `sim/` 규칙(SimCheck) |
| v1.x 이후 | 고정한 약속을 깨지 않는다. 꼭 깨야 하면 메이저 버전(v2.0)을 올리고 업그레이드 도구가 옮긴다 |

## 현재 있는 것 (v0.4, 0단계 완료)

Windows 전용. DX12 포워드 렌더러(인스턴싱, 정점 색, RHI 없이 DX12 직접 호출), Jolt 물리(결정론, 스냅샷), 입력만 보내는 락스텝(UDP/Steam), glTF 모델 + LOD,
`.scene` 씬(게임 정의 오브젝트 종류, 부모·자식 계층), 범용 에디터(프로젝트 관리자, 게임 DLL 핫 리로드, 기즈모, 되돌리기, 자동 저장,
튜닝·상태 패널, 혼자/여러 명 플레이, 그림자 시뮬레이션, 일시정지·되감기, 출시 빌드), 필드 선언(`MEALKIT_FIELD`), 결정론 수학,
`sim/` 검사(SimCheck), Tracy 프로파일링, 프로젝트 템플릿과 업그레이드 도구, 검증 스크립트(`tools/check.ps1`).

**네트워크 방식** (`net::LockstepSession`):
- **호스트-클라이언트(리슨 서버형)**: 방장 PC가 플레이어이자 중계자다. 전용 서버는 없다(헤드리스 시뮬레이션이 생기면 방장 역할만 하는 프로세스는 가능).
- **결정론 입력 락스텝**(서버 권위형 아님): 모든 피어가 같은 시뮬레이션을 돌리고 틱당 플레이어 입력 8바이트만 주고받는다. 호스트가 입력을 모아 확정·배포하고 상태 해시로 디싱크를 잡는다.
- **UDP**(TCP 안 씀): 재전송 대신 확인받지 못한 입력을 매 패킷에 다시 싣는 중복 전송, 패킷 1200바이트 이하. Steam을 쓰면 Steam 네트워킹 릴레이(NAT 통과, 포트 포워딩 불필요).
- **맞는 장르**: 협동, 파티, RTS, 물리 게임, 8명 이하 소규모 대전. 물체가 수천 개여도 대역폭이 일정하고(4인 약 5 KB/s), 상태 조작 치트(스피드핵 등)는 디싱크로 드러난다.
- **안 맞는 장르**: 경쟁 FPS, 대규모 인원. 모든 피어가 전체 상태를 가져 맵핵을 막을 수 없고, 입력 지연(지금 100 ms)이 있고, 최대 8명(`kMaxPlayers`)이다. 방장이 나가면 매치가 끝난다(3단계 호스트 이전).

**없는 것 중 게임을 만들 때 바로 막히는 것**: 소리, 화면 글자(HUD·메뉴), 게임패드, 텍스처, 중간 참가. → 1단계부터.

## 1단계 (v0.5): 게임이 되게 하는 최소 기능

게임을 실제로 내놓으려면 빠져서는 안 되는 기능. 대부분 렌더링·시뮬레이션과 독립적이라 결정론 위험이 낮다. 진행 순서:

1. **위험 확인**(하루 이틀): 최소 사양 실기·다른 PC 결정론(+ clang-cl 비교)·Steam 실검증(+ 온라인 서비스 계층으로 감싸기). 실패하면 2단계 그래픽 계획과 보류 표 결정이 바뀌므로 무엇보다 먼저 한다.
2. **플랫폼 계층 → 헤드리스 → CI**: 오디오·입력·게임패드·UI 이미지가 OS API를 고르기 전에 OS 코드를 한 곳으로 모은다. 늦으면 그 항목들을 다시 짠다. 그 위에 헤드리스 모드와 CI를 세워 이후 모든 작업이 컴파일러·OS·CPU(x64·ARM64) 사이 결정론 검사를 받게 한다. 결정론은 나중에 고치기 가장 어려운 것이라 이식보다 먼저 검사부터 건다. 라이선스는 이때 정한다.
3. **데이터와 코드 분리**: 화면용 튜닝 → 폴더 구조 → 예제 정리 → 정의 데이터 표. 예제(sandbox)가 새 프로젝트의 템플릿이라, 예제에 코드 안 숫자가 남아 있으면 모든 프로젝트가 따라 한다.
4. **나머지는 아래 순서대로**: 게임을 같이 만들지 않으므로 순서는 이 문서가 정한다. 항목을 끝낼 때 기준 샘플에서 실제로 쓰여야 끝난 것으로 친다.

- [x] 프로젝트 설정 (`mealkit.project`를 필드 선언으로) — v0.4.1, 상세는 `docs/CHANGELOG.md`
- [x] 고도식 프로젝트 관리자 + 에디터 한국어/영어 + 게임 exe 아이콘 — v0.4.2, 상세는 `docs/CHANGELOG.md`

### [ ] 최소 사양 실기 측정과 다른 PC 결정론
- **왜**: 성능 예산의 "현재" 값과 SM 6.6 bindless 계획은 최소 사양보다 빠른 Core Ultra에서만 확인했다. `mp_test`는 한 PC 안에서만 돌아, Intel과 AMD CPU 사이 결정론은 시험한 적이 없다. 보류 표의 "고정소수점" 결정은 "다른 CPU 사이 디싱크가 발견될 때" 다시 보기로 했는데, 발견할 절차가 없다.
- **할 일**:
  - 11세대(Xe-LP) 실기에서 SM 6.6, 리소스 바인딩 티어 3, Vulkan 버전·descriptor indexing 지원(2단계 Vulkan 백엔드), 드라이버 버전을 기록하고 `sandbox.exe --bot`으로 프레임·틱 시간을 잰다(벤치마크 모드 전이라 창 제목·Tracy 값). 성능 예산 표의 "현재"를 고친다.
  - 사무용 PC는 제조사가 깐 오래된 드라이버가 많다. 시작 때 드라이버 버전을 로그에 남기고, SM 6.6이 없으면 이유를 알려 주고 끝내는 검사를 넣는다.
  - Intel PC와 AMD PC(가능하면 CPU 세대가 다른 것)를 UDP로 이어 봇 입력 900틱 이상 디싱크가 없는지 본다. 결과(CPU 이름, PASS/틱)를 CHANGELOG에 남긴다.
  - 크로스플레이 목표(5단계) 때문에 clang-cl 빌드(`-ffp-contract=off`)도 만들어 MSVC 빌드와 `detmath-bits` 해시·`mp_test`를 맞붙인다. Windows on ARM 기기가 있으면 같이 본다.
- **같이 할 것**: 아래 "Steam 실검증"을 같은 때 한다(두 PC가 이미 있다).
- **실패하면**: SM 6.6이 없으면 2단계 텍스처 방식(bindless)을 다시 정한다. CPU 사이 디싱크면 디싱크 진단 도구(3단계)를 당겨 원인을 찾고, 고정소수점 보류를 다시 본다.

### [ ] Steam 실검증
- **왜**: SDK(v1.65)로 컴파일·링크만 확인했다. 실제 로비·초대·릴레이는 아직 검증하지 않았다. 릴레이 지연이 입력 지연(100 ms) 가정에 맞는지도 여기서 안다.
- **할 일**: 두 계정(또는 두 PC)으로 `--steam` → 초대 → `+connect_lobby` 참가 → 900틱 이상 디싱크 없음 확인. 끊김·재시도·NAT 상황 로그. 릴레이를 거친 RTT를 기록한다.
- **같이 할 것**: Steam 오버레이가 DX12 스왑체인 위에 뜨는지 확인. Steam Deck(또는 Linux PC)이 있으면 Windows exe를 Proton으로 돌려 봐 그림·입력·Windows PC와 결정론이 맞는지 본다(5단계 첫 항목의 사전 확인).

### [ ] 온라인 서비스 계층 (`mealkit/online/`, Steam 백엔드)
- **왜**: 지금 로비·초대·릴레이가 Steam에 직접 묶여 있고, 세이브(클라우드)와 업적도 Steam 기준으로 계획돼 있다. 크로스플레이(5단계)와 Steam이 없는 플랫폼에서는 쓸 수 없어, 늦게 감쌀수록 걷어 낼 코드가 늘어난다.
- **방식**: 계정, 친구·초대, 로비, P2P 전송(`net::Transport` 구현), 업적·통계·리더보드, 클라우드 세이브를 한 인터페이스로 둔다. 백엔드는 빌드 때 고르고 여럿을 같이 켤 수 있다(Steam 친구로 초대 + EOS 로비로 접속).
  이 단계에서는 **Steam 백엔드와 "없음"(LAN UDP)** 만 만들고, 지금 `--steam` 경로를 이 계층 위로 옮긴다. Steam 실검증과 같이 한다.

  | 기능 | Steam | EOS (3단계) | 콘솔 플랫폼 서비스 (5단계) |
  |---|---|---|---|
  | 계정 | Steam ID | Product User ID (EOS Connect로 Steam·콘솔·기기 ID 로그인, Epic 계정 불필요) | 플랫폼 계정 |
  | 친구·초대 | Steam 오버레이 | 플랫폼 친구 + EOS 로비 초대 | 플랫폼 |
  | 로비·P2P 릴레이 | Steam 로비·릴레이 (Steam끼리) | EOS 로비·P2P (**크로스플레이 매치는 항상 이것**) | EOS |
  | 업적·통계·리더보드 | Steam | EOS | 플랫폼 (트로피 등) |
  | 클라우드 세이브 | Auto-Cloud (설정만) | Player Data Storage | 플랫폼 세이브 |

- **SDK**: Steamworks·EOS SDK는 약관상 저장소에 넣지 않는다. 없으면 Stub이 빌드된다(지금 Steam 방식). Editor 빌드는 Stub.
- **결정론**: 영향 없음. 전송 구현이 바뀌어도 패킷 형식·중복 전송은 같다(`mp_test`).

### [ ] 플랫폼 계층 (`mealkit/platform/`)
- **왜**: 지금 OS 코드(Win32 창·입력, 파일, 소켓, 스레드, `ChildProcess`, 파일 감시)가 기능마다 흩어져 있다. 1단계 오디오·입력·게임패드·UI 이미지가 Windows API(XAudio2, XInput, WIC)를 먼저 고르면 5단계 이식 때 모두 다시 짠다.
- **방식**:
  - 엔진의 OS API 호출은 `mealkit/platform/` 안에서만 한다. 인터페이스는 엔진이 쓰는 만큼만: 창·이벤트, 키보드·마우스·터치·게임패드, 오디오 장치, 파일·사용자 데이터 폴더, 시간, 스레드, 소켓(UDP), 동적 라이브러리, 파일 감시, 자식 프로세스.
  - 구현은 플랫폼별 `.cpp`(빌드 때 고른다). 가상 함수 계층은 두지 않는다. 한 빌드에 플랫폼은 하나다.
  - 창·입력·게임패드·오디오 장치는 **후보 SDL3**(zlib)를 먼저 본다. 모든 대상 플랫폼(웹 포함)과 PlayStation·Switch 패드를 덮는다. 출시 exe 크기(5 MB 예산)와 입력 지연을 재서 정하고, 맞지 않으면 플랫폼마다 기본 API를 직접 감싼다.
  - 에디터 전용 기능(DLL 핫 리로드, 자식 프로세스, `ReadDirectoryChangesW` 파일 감시)도 이 계층에 두지만 Windows 구현만 만든다.
  - **POSIX 구현(Linux·macOS)은 헤드리스에 필요한 만큼만** 이 단계에서 만든다: 파일·사용자 데이터 폴더, 시간, 스레드, UDP 소켓, 로그. 창·입력·오디오는 5단계.
- **검사**: `tools\check_platform.ps1`(check.ps1)가 `platform/`·RHI 백엔드 밖에서 `<windows.h>`·Win32 함수를 쓰는 엔진 코드를 찾는다. 게임 코드는 원래 OS API를 쓰지 않는다(`GameContext`).
- **결정론**: 영향 없음. 단 소켓 구현이 바뀌어도 패킷 형식·중복 전송은 같아야 한다(`mp_test`).
- **이 단계에서 안 하는 것**: 그래픽 API 분리(2단계 "RHI 층")와 헤드리스 밖의 다른 OS 구현(5단계).

### [ ] 헤드리스 시뮬레이션 (4단계에서 당김)
- **왜**: 플랫폼 사이 결정론(5단계 크로스플레이의 바탕)과 컴파일러 비교(clang-cl)를 CI에서 매번 하려면 GPU·창 없이 시뮬레이션만 도는 모드가 먼저 있어야 한다. 규칙 테스트도 몇 초로 끝난다.
- **방식**: `--headless`: 창·RHI·오디오를 만들지 않고 `World`만 N틱 돌린다. 봇 입력과 확정 명령은 그대로, 틱별 상태 해시를 파일로 남긴다(`--hash-log`). `mp_test`도 렌더링 없이 돌 수 있게 한다.
  방장 역할만 하는 프로세스(전용 중계)도 이 모드로 된다.
- **입력 기록 재생**: `--record-inputs`로 확정된 입력·명령을 파일에 남기고 `--replay-inputs`로 그대로 다시 돌린다(3단계 리플레이의 첫 형태). 빌드마다 봇을 따로 돌리지 않고 **같은 입력 파일**을 넣어야 빌드 사이 해시 비교가 된다.
- **헤드리스 빌드 타깃**: 렌더러·에디터·오디오 없이 시뮬레이션·물리(Jolt)·네트워크·플랫폼 계층만 링크하는 `<게임>_headless`. 이것은 **Linux(x64, Clang)와 macOS(ARM64, Clang)에서도 빌드된다**. 엔진 CMake의 MSVC 전용 옵션은 Clang 짝(`-ffp-contract=off` 등)을 같이 둔다.
- **의존**: 플랫폼 계층(창 없이 시작하는 길, POSIX 최소 구현).

### [ ] 화면용 튜닝 (`ViewTuning`)

### [ ] 정의 데이터 표 (`.table`)
- **왜**: 무기·아이템·스킬·적 종류처럼 **같은 모양의 행이 많은 데이터**를 둘 곳이 없다. 튜닝은 구조체 하나라 맞지 않다(유니티 ScriptableObject 목록에 해당).

- **결정론**: 시뮬레이션이 읽는 표는 `World`가 매치 시작 때 복사하고 콘텐츠 해시에 넣는다. 화면 전용 표(아이콘, 설명 문자열 키)는 표시해서 해시에서 뺀다.
- **이어지는 것**: 4단계 소스 모듈(인벤토리·스킬)과 매치 시작 데이터(로드아웃이 행 id를 담는다)가 이 위에 놓인다.

### [ ] 기준 샘플 (게임 대신 엔진을 검증하는 작은 예제)
- **왜**: 이 저장소에서는 게임을 같이 만들지 않는다(결정 기록). 그러면 "실제로 쓰여서 맞는지"를 확인할 곳이 없어, 쓰는 곳 없는 기능과 쓰기 불편한 API가 쌓인다. 기준 샘플이 그 자리를 맡는다.
- **방식**: `samples/<이름>/`에 장르가 다른 작은 샘플을 둔다. 모두 에디터에서 프로젝트로 열 수 있고 템플릿 후보다(지금 sandbox는 저장소 루트 `mealkit.project`로 연다. 샘플이 둘이 되면 샘플 폴더마다 `mealkit.project`를 둔다).

  - 그 뒤 샘플은 기능이 필요로 할 때 하나씩 더한다(예: 유닛 수천 개 RTS — Job System·컬링·길찾기, 협동 3인칭 — 캐릭터 이동 모드·가상 카메라·스켈레탈 애니메이션). 샘플 수는 4개 이하로 유지한다.
- **규칙**:
  - 엔진 항목은 기준 샘플 하나 이상에서 실제로 쓰여야 `[x]`가 된다. 단위 테스트만으로는 끝나지 않는다.
  - 샘플을 만들다 엔진이 없어 막히면 샘플 쪽 우회 코드로 넘어가지 않고 그 항목을 당긴다(`docs/CODING_MODEL.md`의 단계 표시 규칙).
  - 모든 샘플이 `check.ps1`(빌드, `mp_test`, 화면 캡처)과 Export를 통과한다. 5단계부터는 각 플랫폼에서도.
- **범위**: 샘플은 게임이 아니다. 아트·콘텐츠·밸런스는 기능을 보일 만큼만 넣는다.

### [ ] 오디오
- **왜**: 지금 엔진에는 소리가 전혀 없다. 효과음·배경음 없이는 게임이 되지 않는다.
- **방식**: 플랫폼 계층의 오디오 장치 위에서 믹싱. **후보 miniaudio**(퍼블릭 도메인/MIT-0, 파일 하나, 모든 대상 플랫폼, 3D 감쇠·버스 믹싱 포함)를 먼저 보고, 맞지 않으면 Windows는 XAudio2. 효과음은 WAV, 배경음은 Ogg Vorbis 스트리밍.
- **API 초안**: `audio::Engine::play(SoundId, Vec3 position, f32 volume)`, 리스너 = 카메라. 3D 감쇠·좌우 패닝(X3DAudio).
- **라이브러리 후보**: `stb_vorbis` (퍼블릭 도메인, 파일 하나)로 Ogg 디코딩.
- **결정론**: 소리는 렌더링처럼 **결과만 읽는다.** 시뮬레이션이 "이벤트"(충돌, 점프)를 남기면 프레임 쪽에서 재생한다. 시뮬레이션이 오디오 상태를 읽으면 안 된다.
- **비용**: CPU 코어 하나의 1% 미만. 개발 중간.

### [ ] 이벤트 → 연출 표 (타격감을 데이터로)
- **왜**: 지금은 틱 이벤트에 효과를 붙이려면 `view/Effects.cpp`처럼 코드를 써야 한다. 사운드·VFX 담당이 프로그래머 없이 타격감을 만질 수 없다.
- **방식**: 데이터 파일(`assets/feedback.table`) 한 줄 = 이벤트 종류 → 연출 묶음. 예: `Hit` → 소리 `hit_01` + 효과 `hit_spark` + 화면 흔들림 0.2 + 번쩍임 0.1초 + 화면 정지 0.05초.
  에디터 [연출] 패널에서 고치고 바로 플레이해 본다(Unity의 Feel 같은 방식). 틱 이벤트 타입을 `MEALKIT_STRUCT`로 선언하면 이벤트 필드(위치, 대상 id, 세기)를 연출 값(재생 위치, 세기 배율)에 고를 수 있다.
  처음에는 소리·흔들림·번쩍임만, 2단계 파티클이 생기면 효과를 더한다.
- **화면 정지(히트 스톱)**: 시뮬레이션을 멈추면 락스텝에 닿으므로 **화면만** 멈춘다(애니메이션·효과·카메라만 잠깐 정지, 시뮬레이션은 계속).
- **결정론**: 영향 없음(`view/`에서 이벤트를 읽기만 한다). 표는 콘텐츠 해시에 넣지 않는다.
- **의존**: 오디오. 화면 흔들림은 여기서 **카메라 임펄스**(흔들림 신호를 카메라 위치·회전에 더하는 작은 코드)로 만들고, 4단계 "가상 카메라"가 같은 코드를 이어 쓴다.

### [ ] 확정 명령 채널
- **왜**: 락스텝으로 보내는 것은 틱당 플레이어 입력 8바이트(`kInputBytes`)뿐이다. 디버그 치트, 입력 지연 변경, 일시정지 투표, 매치 중 설정 변경처럼 **가끔 있고 크기가 제각각인 명령**을 보낼 길이 없어, 기능마다 다른 방법을 만들게 된다.
- **방식** (`docs/CODING_MODEL.md` "시뮬레이션에 넣는 입력 외 명령"): 피어가 명령을 호스트에 보내면 호스트가 적용할 틱 번호를 붙여 확정하고, 그 틱의 입력과 함께 모두에게 배포한다(재전송·중복 전송도 입력과 같은 길).
  명령 타입은 게임이 `MEALKIT_STRUCT`로 선언하고, 엔진 명령(입력 지연 변경 등)은 엔진이 예약한 타입이다. `World::step()` 맨 앞에서 플레이어 번호 → 보낸 순서로 처리한다. 틱당 크기 제한(예: 256바이트)을 넘으면 다음 틱으로 미룬다.
- **결정론**: 명령은 확정된 뒤에만 실행되므로 모든 피어·그림자 시뮬레이션이 같다. 리플레이와 되감기 기록에 입력과 같이 들어간다.
- **쓰는 곳**: 디버그 UI 치트, 입력 지연 자동 조절, 로드아웃 이후의 매치 중 변경. 네트워크 대역폭 예산(4인 10 KB/s)에 명령이 거의 없는 평소 상태는 영향이 없다.

### [ ] 디버그 UI (Dear ImGui)
- **왜**: 성능·치트·시뮬레이션 상태·디싱크 정보 같은 개발용 화면은 프로그래머가 코드로 빨리 만드는 게 맞다. 게임 UI(Penpot)와 섞지 않는다.
- **방식**: 게임 코드는 `GameContext`로 받은 ImGui로 패널을 그린다. Editor 빌드에서는 에디터의 ImGui 컨텍스트를 게임 DLL에 넘긴다(DLL마다 ImGui 전역이 따로라서 `ImGui::SetCurrentContext`).
  Dev 게임 빌드에서는 게임 창 위의 오버레이(키 하나로 켜고 끔). 출시 빌드에서는 `MEALKIT_DEBUG_UI`로 코드가 빠지고 ImGui를 링크하지 않는다.
- **결정론**: 디버그 패널이 시뮬레이션을 바꾸는 치트는 상태를 직접 고치지 않고 확정 명령(위 항목)으로 보낸다. 직접 고치면 다른 피어와 그림자 시뮬레이션이 디싱크된다.
- **이어지는 것**: 4단계 "디버그 그리기 API", "성능 패널과 예산 경고"가 이 위에 놓인다.

### [ ] 로컬라이제이션 문자열 테이블
- **왜**: UI를 만들면서 문자열을 코드에 바로 쓰면, 나중에 영어를 넣을 때 모든 문자열을 찾아 바꿔야 한다.
- **방식**: `assets/strings/ko.txt`, `en.txt`(키 = 문자열). Penpot 글자에는 플러그인이 키를 붙이고(기본값은 레이어 이름), 게임 코드는 `L("menu.start")`처럼 키만 쓴다. 언어는 설정에서 고르고, 없는 키는 키 이름을 그대로 보여 주고 로그를 남긴다.
- **여러 스타일 글자**: 한 글자 상자에 스타일 구간이 여럿이면 문자열에 번호 태그를 쓴다: `점수 <1>{score}</1>점`. 번호는 디자인의 구간 순서이고, 번역할 때는 태그 위치만 옮긴다.
  플러그인은 처음 내보낼 때 한국어 원문을 태그와 함께 `ko.txt`에 넣고, 이미 있는 키는 덮어쓰지 않고 차이만 경고한다.
- **글꼴**: 테이블에 있는 글자가 모두 글꼴 파일에 들어 있는지 빌드 때 검사한다(글자는 실행 중에 굽는다).
- **결정론**: 영향 없음 (화면 쪽만, 콘텐츠 해시에 넣지 않는다).

### [ ] 게임 화면 UI (Penpot 디자인 → `.ui` 런타임)
- **왜**: 지금은 점수·로비 상태를 창 제목으로만 보여 준다. 게임 UI는 프로그래머가 아닌 사람도 UMG·UI Toolkit처럼 시각적으로 디자인할 수 있어야 한다.
- **구조**: **Penpot이 원본이고 엔진은 가져오기만 한다.**
  - 디자이너가 Penpot(오픈소스 웹 디자인 도구, 직접 서버를 띄울 수도 있다)에서 화면을 만든다.
  - 엔진 저장소의 Penpot 플러그인(`tools/penpot-plugin/`, TypeScript)이 지원 범위를 검사하고 `.ui`(텍스트, 키는 영어)와 이미지로 내보낸다.
  - 엔진은 `.ui`를 유지 모드 런타임(`mealkit/ui/`)으로 그린다. 에디터 안에 UI 디자이너는 만들지 않는다.
- **원본 규칙**: 플러그인이 내보낸 `assets/ui/*.ui`는 생성물이라 손으로 고치지 않는다(첫 줄에 표시, Penpot 파일·보드 id 기록). 첫 줄 표시가 없는 `.ui`는 손으로 쓴 파일이다(플러그인 전, 아래 "순서").
  바인딩·액션까지 전부 Penpot 안(플러그인 데이터)에 두어 엔진에서 고칠 것이 없게 한다(왕복 없음). Penpot 원본은 `.penpot` 파일로 내보내 프로젝트 `design/`에 백업한다.
- **가져오는 길**: 에디터가 localhost 서버를 연다.
  - 플러그인 파일을 제공한다(디자이너는 그 주소로 플러그인을 설치).
  - 플러그인이 보낸 `.ui`·이미지를 `assets/ui/`에 쓰고 핫 리로드한다. Penpot에서 고치면 수 초 안에 엔진 화면에 보인다.
  - 게임 DLL의 뷰 모델 필드 목록과 액션 목록을 플러그인에 알려 준다(바인딩을 드롭다운으로 고른다).
  - 에디터가 없을 때는 플러그인이 zip으로 내려받게 한다. Penpot 클라우드(penpot.app)로 시작하고 필요하면 직접 띄운다.
  - 플러그인에서 localhost로 보내는 방법(권한, CORS)은 도입 때 확인한다.
  - **보안**: 브라우저의 아무 웹 페이지나 localhost로 요청을 보낼 수 있으므로, 서버는 127.0.0.1에만 열고, 에디터를 켤 때마다 무작위 토큰을 만들어 플러그인 설치 주소에 넣고, 토큰이 없거나 `Origin`이 Penpot이 아닌 요청은 거절한다. 쓰기는 `assets/ui/` 안 경로만 받는다(`..` 거절).
- **지원 범위** (플러그인이 내보내기 전에 검사하고, 벗어나면 경고):

  | Penpot | 엔진 |
  |---|---|

  | 이미지 채우기 | PNG로 내보냄. 9-slice는 플러그인에서 여백 지정 |

- **글자 (여러 스타일을 처음부터 지원)**:
  - Penpot 글자 구조(문단 → 스타일 구간)를 그대로 가져온다. 구간마다 글꼴·굵기·기울임·크기·색·자간·밑줄·취소선·대소문자 변환, 문단마다 정렬·줄 높이.
  - 줄바꿈은 구간 경계를 넘어 한 번에 계산한다. 한글 줄바꿈 단위(음절 / 어절), 줄 높이·기준선 계산은 Penpot 결과에 맞추고 줄 나뉨·줄 상자 위치 비교로 확인한다.
  - 자동 크기(너비·높이 / 높이 / 고정), 넘치면 말줄임.
  - 글꼴: `stb_truetype`(퍼블릭 도메인, 파일 하나)로 **쓰는 글자만 실행 중에 SDF로 구워** 아틀라스 캐시에 넣는다. 굵기·기울임마다 글꼴 파일 하나.
    미리 굽는 완성형 2,350자 방식은 쓰지 않는다(드문 한글, Steam 닉네임의 일본어 등을 못 보여 준다). 기본 글꼴 후보는 Pretendard, Noto Sans KR(OFL).
    Penpot에서 쓴 글꼴·굵기가 `assets/fonts/`에 다 있는지 플러그인이 검사한다. 글자 모양 조합(HarfBuzz)은 하지 않는다(한·영·일은 필요 없음).
- **게임 코드와 연결**: 단방향 뷰 모델 + 액션. 방법은 이것 하나다.
  ```cpp
  // 게임 코드가 선언하면 플러그인의 바인딩 목록에 나타난다
  MEALKIT_VIEWMODEL(HudVm) {
      MEALKIT_FIELD(u32, score, 0, "점수");
      MEALKIT_FIELD(f32, health01, 1.0f, "체력 비율");
      MEALKIT_LIST(PlayerRowVm, players, 4, "플레이어 목록");
  };
  void fillHud(const World& world, u8 me, HudVm& vm); // 매 프레임: 상태 → 뷰 모델
  void onUiAction(ui::Action action, AppState& app);  // 버튼 → "pause.resume" 같은 액션
  ```
  - 글자 바인딩은 글자 안에 `{score}`를 그냥 쓴다(그 구간의 스타일을 따른다). 서식은 정해진 몇 가지만(천 단위 구분, 소수 자릿수, 시간).
  - 그 밖의 바인딩(보이기, 너비 비율, 이미지, 색 토큰, 비활성)과 위젯 종류(버튼, 토글, 슬라이더, 선택 상자, 글자 입력, 스크롤 영역, 목록)는 플러그인 패널에서 정한다. 정하지 않은 것은 그림이다.
  - 버튼은 플러그인 패널에 액션 이름을 적는다. 입력 위젯만 자기 필드에 값을 쓰고 `changed` 액션을 낸다. 양방향 바인딩, 식 언어, 변환기는 없다.
  - 목록은 자식 하나를 반복 템플릿으로 표시하고 배열 필드에 묶는다. 나머지 예시 자식은 미리보기에서만 쓴다.
- **컴포넌트·상태·테마**:
  - Penpot 컴포넌트 = 재사용 `.ui`(인스턴스 덮어쓰기 반영).
  - 상태(보통 / 마우스 올림 / 눌림 / 포커스 / 비활성)는 컴포넌트 variants로 만든다. 쓰는 Penpot 버전에 variants가 없으면 `Button/Hover` 이름 규칙.
  - 전환 시간·이징은 테마 기본값, 컴포넌트별로 플러그인에서 덮어쓴다. 프로토타입 흐름과 애니메이션은 가져오지 않는다.
  - Penpot 디자인 토큰(색·숫자) = 테마 토큰(`assets/ui/theme`). 토큰 세트(예: 색약 모드)는 테마 변형으로.
- **게임패드·키보드 조작**: 포커스는 위젯 id로 기억하고, 방향 입력이 오면 그 방향에서 가장 가까운 위젯으로 옮긴다. 필요한 곳만 플러그인에서 "다음 포커스"를 지정한다.
  확인·뒤로·이동은 입력 액션 매핑의 액션이다. 버튼 안내 아이콘(키보드 / Xbox)은 마지막에 쓴 기기를 따라간다. 마우스를 움직이면 포커스 표시를 숨긴다.
- **런타임**:
  - `.ui`를 불러오면 포인터 없는 평평한 노드 배열(부모 번호, 깊이 우선 순서)이 된다. 바인딩 값이나 화면 크기가 바뀐 노드만 다시 배치한다(가만히 있는 화면은 CPU 거의 0).
  - 좌표는 기준 보드(1920×1080)의 논리 단위, 배율 = `min(가로/1920, 세로/1080) × 설정의 UI 배율`.
  - 그리기는 3D 장면 다음의 2D 패스 하나: 이미지 아틀라스 + 글자 아틀라스 + SDF 도형을 SM 6.6 bindless로 묶어 드로우 콜 1~2회. 동적 해상도와 무관하게 원래 해상도로 그린다.
  - UI 이미지는 `stb_image`(퍼블릭 도메인, 2단계 텍스처와 같은 라이브러리)로 PNG를 읽는다. 3D 머티리얼 텍스처는 2단계 그대로.
- **월드 위 UI**: 이름표·데미지 숫자·목표 표시는 `.ui` 템플릿을 3D 위치에 붙여 여러 개 띄운다. 화면 밖·카메라 뒤면 숨기거나 가장자리에 붙인다.
- **에디터 UI 미리보기 패널**: 해상도 전환(720p / 1080p / 21:9 / 4:3 / UI 배율), 가짜 뷰 모델 값, 언어 전환(글자 넘침 확인), 포커스 이동 표시, 바인딩 오류 목록(없는 필드·액션), 화면별 노드 수.
- **검증**: 두 가지로 나눈다(`tools/check.ps1`에 포함).
  - **배치 상자 비교(주 검사)**: 플러그인이 Penpot이 계산한 노드별 위치·크기와 글자 줄 나뉨을 같이 내보내고, 엔진 배치 결과와 비교한다(허용 오차 0.5 논리 픽셀). 레이아웃 계산이 같은지는 이것으로 판단한다.
  - **픽셀 비교(보조)**: 같은 보드의 Penpot PNG와 엔진 `--capture`를 허용 오차를 두고 비교한다. Penpot 글자는 브라우저 래스터라이저가 그려 엔진(`stb_truetype` SDF)과 픽셀이 완전히 같을 수 없으므로, 글자 영역은 느슨하게 보고 도형·색·이미지가 크게 어긋나는 것만 잡는다.
  화면당 노드 수 예산은 500개, 효과 없는 래퍼 보드는 플러그인이 납작하게 만든다.
- **결정론**: 영향 없음 (`view/`에서만). UI는 시뮬레이션 상태를 읽기만 하고, 액션은 입력이나 `AppState` 변경만 만든다.
- **순서**: 두 덩어리로 나눈다.
  1. **`.ui` 런타임 + 미리보기 패널**(1단계, 샘플에 필요): `.ui`를 텍스트로 직접 고쳐 핫 리로드한다. 샘플의 HUD·메뉴·설정·화면 흐름은 이것으로 만든다. 형식은 플러그인이 나중에 내보낼 형식 그대로라, 손으로 쓴 화면도 바꾸지 않고 계속 쓴다.
  2. **Penpot 플러그인 + 가져오기 서버 + 배치·픽셀 비교 검사**: 프로그래머가 아닌 사람이 UI를 만들기 시작할 때(디자이너가 생겼을 때) 한다. 그때까지 v0.5를 막지 않는다. 기본 화면 흐름 템플릿의 Penpot 원본(`design/`)도 이때 만든다.
- **의존**: 0단계 필드 선언(뷰 모델), 로컬라이제이션, 입력 액션 매핑(둘 다 이 항목보다 먼저 한다).
- **비용**: 큰 항목(런타임 + 플러그인). 글꼴 파일 약 2~5 MB(에셋), 글꼴 라이선스를 `THIRD_PARTY_NOTICES.txt`에. 플러그인 빌드에 Node.js가 필요하다(개발 도구, 게임에는 들어가지 않는다).
- **이어지는 것**: 로비·일시정지 메뉴는 아래 "기본 화면 흐름 템플릿", 설정 화면은 "설정 시스템 + 표준 설정 화면"에서 `.ui`로 만든다(Penpot 원본은 플러그인이 생길 때 더한다).

### [ ] 설정 시스템 + 표준 설정 화면
- **왜**: 거의 모든 게임이 화면·소리·키 설정을 같은 모양으로 다시 만든다. 엔진이 기본 화면을 주고 게임은 항목만 더하게 한다.
- **방식**: 0단계 필드 선언(`MEALKIT_FIELD`)으로 설정 스키마를 만들고, 탭이 있는 설정 화면을 `.ui`로 기본 제공한다(플러그인이 생기면 Penpot 원본도). 항목 줄은 목록 바인딩으로 스키마에서 채우므로, 게임은 디자인을 고치지 않고 탭·항목을 추가할 수 있다.
- **사용자 데이터 폴더**: 플랫폼 계층의 사용자 데이터 함수로만 연다(Windows는 `%LOCALAPPDATA%\<게임>\`, 콘솔은 플랫폼 세이브 API). 여기에 `settings.ini`, 키 바인딩, 세이브·통계, 리플레이, 크래시 리포트를 한 규칙으로 둔다. 세이브는 버전 번호를 붙여 형식이 바뀌어도 읽게 한다(아래 "세이브").
- **기본 항목**:
  - 화면: 창 모드(창 / 테두리 없는 창 / 전체화면), 해상도, 수직동기, 프레임 제한, 렌더 스케일(동적 해상도와 연결), 그래픽 프리셋(내장 그래픽이 기본), FOV, 밝기.
  - 오디오: 마스터 / 배경음 / 효과음 / UI 볼륨(오디오 버스), 창이 포커스를 잃으면 음소거.
  - 키: 입력 액션 매핑 위의 키 바꾸기 화면, 중복 키 경고, 기본값 복원, 게임패드 감도·축 반전.
  - 게임플레이·접근성: 마우스 감도, Y축 반전, 언어, UI 배율, 자막.
- **화면 변경 확인**: 해상도·창 모드를 바꾸면 "15초 안에 확인하지 않으면 되돌림" 창을 띄운다.
- **결정론**: 설정은 콘텐츠 해시에 넣지 않고 **시뮬레이션이 읽으면 안 된다**. `sim/` 금지 헤더 검사에 설정 헤더도 넣는다. 감도·반전처럼 조작에 닿는 값은 입력을 양자화하기 전에 클라이언트에서만 적용한다.
- **의존**: 오디오, 게임 UI, 입력 액션 매핑, 게임패드.

### [ ] 세이브 (진행 데이터)
- **왜**: 레벨·해금·인벤토리·통계처럼 매치 밖에 남는 데이터를 게임마다 다른 방식으로 저장하게 두면 형식 변경·클라우드 동기화를 매번 다시 만든다.
- **세 가지를 나눈다**:
  - **매치 안 상태**: 이미 있는 `WorldSnapshot`(상태 필드 + 물리). 협동 게임의 "중간 저장"은 스냅샷을 파일로 쓰고, 불러오면 그 상태로 매치를 시작한다(3단계 중간 참가와 같은 데이터).
  - **진행 데이터**: `app/`의 `AppState` 안 `MEALKIT_STRUCT(SaveData)` 하나를 사용자 데이터 폴더에 텍스트로 저장한다(필드 선언 장치가 저장·읽기를 맡는다). 파일에 형식 버전을 쓰고, 모르는 필드는 버리고 없는 필드는 기본값으로 읽는다.
  - **클라우드**: 온라인 서비스 계층의 클라우드 세이브. Steam은 Auto-Cloud(Steamworks 설정만, 코드 없음), Steam이 없는 플랫폼은 EOS Player Data Storage, 콘솔은 플랫폼 세이브.
- **넣지 않는 것**: 계정 서버·DB(보류 표). 계정은 온라인 서비스 계정(Steam ID, EOS Product User ID), 순위·통계는 온라인 서비스의 리더보드·통계(4단계)로 한다. 락스텝 P2P에는 권위 서버가 없어 진행 데이터는 각자 PC에 있고, 고치려면 고칠 수 있다는 것을 감수한다.
- **결정론**: 진행 데이터는 시뮬레이션이 직접 읽지 않는다. 매치에 영향을 주는 값(해금한 스킬, 장비)은 아래 "매치 시작 데이터"로 보낸다.

### [ ] 매치 시작 데이터 (플레이어별 로드아웃)
- **왜**: 지금 매치 시작 때 모두에게 보내는 값은 `seed`와 `matchData`(u32 하나)뿐이다. 각자 고른 캐릭터·장비·해금 스킬을 매치에 가져갈 곳이 없다.
- **방식**: 게임이 `MEALKIT_STRUCT(Loadout)`를 선언한다. 로비에서 각 피어가 자기 로드아웃을 호스트에 보내고, 호스트가 `startMatch` 때 모든 플레이어의 로드아웃을 확정해 배포한다.
  `World::reset`이 `PlayerSlot`으로 복사하고 시뮬레이션은 그 값만 읽는다. 크기 제한(예: 플레이어당 256바이트)을 두고, 넘으면 로비에서 막는다.
- **결정론**: 로드아웃은 상태 필드라 상태 해시·스냅샷에 들어간다. 잘못된 값(가지지 않은 아이템)은 막을 수 없으므로 경쟁 게임은 감수하거나 서버 검증(보류)이 필요하다.
- **의존**: 세이브(진행 데이터에서 로드아웃을 만든다). 아래 "기본 화면 흐름"의 로비가 로드아웃 고르기 화면을 이 위에 만든다.

### [ ] 기본 화면 흐름 템플릿
- **왜**: 타이틀부터 결과 화면까지의 흐름도 게임마다 비슷하다. 지금은 명령줄 옵션으로 호스트·참가를 고른다.
- **방식**: 타이틀 → 메인 메뉴 → 방 만들기 / 참가(IP 또는 Steam 초대) → 로비(준비, 팀) → 로딩 → 게임 → 일시정지(설정 열기, 나가기) → 결과 → 로비로. 프로젝트 템플릿에 화면별 `.ui`와 뷰 모델·액션 코드로 넣어 게임이 고쳐 쓴다(Penpot 원본 `design/`은 플러그인이 생길 때 더한다).
- **결정론**: 화면 흐름은 `view/`·`app/` 쪽. 매치 안의 상태(카운트다운, 결과)는 4단계 "게임 흐름 프레임워크"가 시뮬레이션에서 정하고, 화면은 그것을 읽기만 한다.

### [ ] 네트워크 상태 흉내 내기
- **왜**: 같은 PC 테스트는 지연이 0에 가깝다. 입력 지연 자동 조절, 끊김 처리, 재접속을 실제 친구 없이 시험할 수 없다.
- **방식**: `--net-lag <ms> --net-jitter <ms> --net-loss <%>` 옵션. `net::Transport` 위에 지연 큐와 무작위 손실을 두는 래퍼(UDP, Steam 모두). `mp_test.ps1`에도 같은 옵션.
- **결정론**: 영향 없음(전달 시점만 바뀐다). 손실은 실제 패킷 손실과 같은 재전송 경로를 탄다.
- **비용**: 작음. 입력 지연 자동 조절보다 먼저 한다.

### [ ] 버전 표시와 접속 거부 이유
- **왜**: 지금은 exe·씬·모델이 다르면 콘텐츠 해시가 달라 접속이 거부되지만, 친구는 이유를 알 수 없다.
- **방식**: exe에 게임 버전 + 빌드 번호(git 커밋)를 넣어 창 제목·로비에 표시한다. 접속 때 버전과 해시 구성(시뮬레이션 버전/씬/모델)을 따로 보내, 거부할 때 "게임 버전이 다릅니다 (내 1.2 / 방장 1.3)", "씬 파일이 다릅니다"처럼 알려 준다.
- **시뮬레이션 버전**: exe 해시가 아니라 게임 버전 + `sim/`·엔진 시뮬레이션 소스 해시를 빌드 때 박는다. 플랫폼마다 exe가 달라도 같은 값이 나와야 크로스플레이(5단계)가 된다.
- **같이 할 것**: 출시 폴더 이름에 버전(`export\<이름>-1.2\`) 옵션.

### [ ] 입력 지연 자동 조절
- **왜**: 지금은 `--delay 3`(100 ms) 고정이다. LAN에서는 너무 길고, 먼 상대에게는 짧아서 멈칫거린다.
- **방식**: 호스트가 피어별 RTT를 보고 매치 시작 때(그리고 진행 중에는 천천히) 입력 지연을 정해 모두에게 같은 틱부터 적용한다.
- **결정론**: 지연 변경 자체를 확정 명령(엔진 명령 타입)으로 보내, 모두 같은 틱부터 적용한다.
- **플랫폼별 기본값과 상한**: 프로젝트 설정에 플랫폼 종류(PC 유선 / 콘솔 / 모바일 / 웹)별 기본 지연과 상한을 둔다. 무선·WebRTC는 RTT와 흔들림이 커서 같은 기본값이 맞지 않는다.
  락스텝이라 한 매치의 지연은 모두 같고 가장 느린 피어가 정한다. 크로스플레이 매치에서 상한을 넘는 피어가 있으면 로비가 경고하고, 게임 설정으로 막을 수 있다. 값은 처음에 PC만 정하고 각 플랫폼을 시작할 때(5단계) 실측으로 채운다.
- **의존**: 확정 명령 채널, 네트워크 상태 흉내 내기(시험용).

### [ ] 내 캐릭터 겉모습만 예측
- **왜**: 입력 지연(약 100 ms) 때문에 내 조작이 늦게 느껴진다. 롤백 넷코드는 비용이 너무 크다(보류 표).
- **방식**: 시뮬레이션은 그대로 두고, 화면에서만 내 캐릭터를 아직 확정되지 않은 내 입력으로 미리 움직여 그린다. 확정 상태가 오면 부드럽게 맞춘다.
- **결정론**: 영향 없음 (`view/`에서만 한다). 다른 플레이어·물체와의 충돌은 확정 후에 보인다.

### [ ] 틱레이트를 프로젝트 설정으로
- **왜**: 30 Hz 고정. 물체가 적은 액션 게임은 60 Hz가 반응·충돌 정확도에 낫다.
- **방식**: 프로젝트 설정 `tickRate`(30 기본, 60 선택). 콘텐츠 해시에 포함.
- **비용**: 60 Hz는 시뮬레이션 CPU와 입력 패킷이 2배. 바디 수천 개짜리 게임에는 쓰지 않는다.
- **데이터**: 시간 값은 초로 적혀 있으므로(화면용 튜닝 항목의 "시간 값은 초로") 틱레이트를 바꿔도 튜닝·표를 고치지 않는다. 입력 지연(`--delay`)도 틱이 아니라 ms로 받는다.

### [ ] RHI 층 (`mealkit/rhi/`, DX12 + Vulkan 백엔드) — 2단계 맨 앞
- **왜**: 2단계는 bindless 텍스처, 그림자, 포스트, GPU 타임스탬프처럼 DX12 호출이 가장 많이 늘어나는 단계다. 그 전에 그래픽 API 호출을 한 층으로 모아야 5단계 백엔드가 렌더러 전체가 아니라 이 층만 새로 쓴다.
- **방식**:
  - 엔진이 직접 만드는 **얇은 층**: 장치·큐, 명령 목록, 버퍼·텍스처, bindless 디스크립터 힙, PSO, 배리어(명시적, 렌더 그래프 없음), 스왑체인, 타임스탬프 쿼리. 렌더러가 쓰는 만큼만 만들고 범용 그래픽 라이브러리를 목표로 하지 않는다.
  - 모양은 DX12를 따른다(명령 목록 기록, 명시적 배리어, bindless 인덱스). Vulkan·Metal은 같은 모양으로 옮기기 쉽고, WebGPU만 아래처럼 떨어진다.
  - 백엔드는 빌드 때 하나를 고른다(가상 함수 없이 백엔드별 `.cpp`). 한 빌드에서 API를 바꾸는 기능은 없다.
  - 지금 `render::Renderer`의 DX12 호출을 이 층으로 옮기고, **같은 항목에서 Vulkan 백엔드를 같이 만든다.** 그림이 같아야 한다(그래픽 회귀 테스트가 있으면 그것으로, 없으면 `--capture` 전후·백엔드 사이 비교).
- **Vulkan을 처음부터 같이 하는 이유**: 구현이 하나뿐인 추상화는 DX12의 가정(힙·배리어·루트 시그니처 모양)이 그대로 새어 나와, 두 번째 백엔드를 붙일 때 층을 다시 짜게 된다. 2단계 그래픽 기능을 처음부터 두 API로 만들면 5단계 이식 때 렌더러를 다시 고치지 않는다.
  Vulkan 하나가 Linux·Steam Deck 네이티브, Android, (선택) Switch를 덮는다. Metal·WebGPU는 5단계에서 이 두 백엔드의 모양을 따라 만든다.
- **Windows에서 둘 다 시험한다**: Intel Xe 드라이버는 Windows에서 Vulkan을 지원하므로 Linux 기기 없이 같은 PC에서 두 백엔드를 돌린다. `build.bat Vulkan`(별도 빌드 폴더 `build\Vulkan`)으로 Vulkan 백엔드 게임·에디터를 만든다. 출시 Windows 빌드는 DX12.
  `check.ps1`이 두 빌드로 같은 장면을 캡처해 비교하고(허용 오차 있음), Vulkan 검증 레이어 오류가 0개인지 본다.
- **최소 사양**: 11세대(Xe-LP)의 Vulkan 1.3·descriptor indexing 지원을 1단계 실기 측정 때 같이 기록한다.
- **셰이더**: HLSL 하나가 원본. DXC로 DXIL(DX12)과 SPIR-V(Vulkan)를 **둘 다 빌드 때 만들고**(한쪽 컴파일 실패는 빌드 실패), Metal·WebGPU는 SPIR-V에서 변환(후보 SPIRV-Cross, Tint/Naga)한다. 변환은 빌드 때만, 게임은 결과만 싣는다.
- **bindless**: DX12 SM 6.6 `ResourceDescriptorHeap[]` 기준. Vulkan은 descriptor indexing, Metal은 argument buffer tier 2로 옮긴다. WebGPU는 bindless가 없어 웹 백엔드는 머티리얼 묶음별 드로우로 떨어진다(웹 프리셋, 드로우 콜 예산을 따로 둔다).
- **외부 RHI 라이브러리를 쓰지 않는 이유**: SDL3 GPU·bgfx는 bindless가 없고, Diligent는 크고 렌더러 모양을 정해 버린다. 렌더러는 엔진이 맡는 영역(판단 기준 ④)이고, 우리가 쓰는 기능만 담은 층이 가장 가볍다.
- **결정론**: 영향 없음 (화면 쪽).
- **비용**: 큼. 렌더러 코드가 작은 지금(드로우 콜 4회)이 가장 싸다. 이후 2단계 그래픽 항목마다 백엔드 두 개 분량의 일이 들고, Vulkan 런타임은 OS가 주므로 출시 exe 예산에는 영향이 작다.

### [ ] 셰이더 핫 리로드 (엔진 개발용)
- **왜**: 지금 셰이더(`Forward.hlsl`)는 빌드 때 컴파일돼 exe에 들어간다. 그래픽 기능을 넣는 동안 셰이더를 고칠 때마다 엔진을 다시 빌드해야 한다.
- **방식**: Editor·Dev 빌드에서 `engine/shaders/` 변경을 감지해 dxc로 다시 컴파일하고 PSO를 바꾼다. 컴파일 오류는 로그에 남기고 이전 셰이더를 계속 쓴다. 출시 빌드는 지금처럼 박아 넣은 바이트코드만.
- **비용**: 작음. 아래 그래픽 기능 전에 한다.

### [ ] 벤치마크 모드 (그래픽 작업 전에 먼저)
- **왜**: 성능 예산의 "현재" 값은 최소 사양보다 빠른 PC에서 잰 것이다. 그래픽 기능을 넣을 때마다 같은 조건으로 비교할 기준이 없다.
- **방식**: `--benchmark [초]`: 고정 시드, 고정 카메라 경로, 봇 입력으로 돌리고 평균·1% 최악 프레임, GPU 시간, 틱당 시뮬레이션 시간, 드로우 콜을 텍스트 보고서(`benchmark.txt`)로 남긴다. GPU 이름·드라이버도 기록.
- **쓰임**: 최소 사양(11세대) 실기 측정, 그래픽 기능 전후 비교, 친구 PC 성능 받기(출시본에도 들어 있다). 성능 예산 표를 이 결과로 갱신한다.
- **GPU 예산 나누기**: 프레임 GPU 예산(8 ms)을 기능별로 나눠 두고(GPU 타임스탬프 쿼리로 패스마다 잰다), 아티스트가 무엇을 얼마나 넣어도 되는지 판단하게 한다. 첫 값(최소 사양 실측으로 고친다):

  | 불투명 물체 | 그림자 | 포스트 | VFX(반투명) | UI | 여유 |
  |---|---|---|---|---|---|
  | 3 ms | 1.5 ms | 1 ms | 1 ms | 0.5 ms | 1 ms |

  보고서와 에디터 성능 패널(4단계)이 패스별 시간을 이 표와 같이 보여 주고, 넘으면 빨갛게 표시한다.

### [ ] 프러스텀 컬링
- **왜**: 지금은 화면 밖 물체도 모두 인스턴스 버퍼에 넣는다. 맵이 커지면 바로 비용이 된다.
- **방식**: `DrawList::add` 전에 바운딩 구로 CPU 컬링. 물체가 수만 개가 되면 메시별 묶음 단위로 먼저 걸러낸다.
- **비용**: 작음. 다른 그래픽 기능보다 먼저 한다.

### [ ] 에셋 핫 리로드 (모델·텍스처·씬) (4단계에서 당김)
- **왜**: 그래픽 콘텐츠를 외부 도구에서 만들기로 했으므로, Blender에서 내보내면 에디터에 바로 보여야 아티스트가 혼자 작업할 수 있다.
- **방식**: 에디터가 `assets/` 변경을 감지(`ReadDirectoryChangesW`)해 모델·텍스처·씬·LUT·효과 파일을 다시 읽는다. 플레이 중에는 화면용 데이터만 바꾸고, 충돌 데이터가 바뀌면 다음 플레이부터 반영한다(콘텐츠 해시).
- **불러오기 경고**: 지원 범위 밖(머티리얼 기능, 뼈 64개 초과, 텍스처 크기 등)은 에디터 로그와 인스펙터에 파일 이름과 함께 보여 준다.

### [ ] Blender 내보내기 애드온
- **왜**: 스타일 프리셋 기능은 glTF `extras` 키로 켜는데, 아티스트가 키를 손으로 적으면 오타·빠뜨림이 생긴다. 내보내기 설정도 사람마다 달라진다.
- **방식**: 엔진 저장소의 Blender 애드온(`tools/blender-addon/`, Python). Penpot 플러그인과 같은 역할이다.
  - 머티리얼 패널에 MealKit 기능(외곽선·바람·림·디졸브)을 체크박스와 값으로 보여 주고 `extras`에 쓴다. 키 목록은 엔진이 내보낸 스키마 파일에서 읽는다(엔진과 어긋나지 않게).
  - 내보내기 전에 지원 범위(머티리얼 노드, 뼈 수, 텍스처 크기)와 에셋 예산을 검사해 경고한다.
  - 버튼 하나로 프로젝트 `assets/`에 정해진 설정으로 glTF를 내보낸다. 에셋 핫 리로드가 받아 바로 보인다.
- **유지**: Blender 버전은 LTS 하나를 정해 맞춘다(`docs/GUIDE.md` 외부 라이브러리 표에 적는다). 엔진 버전을 올릴 때 애드온 스키마도 같이 확인한다.

### [ ] 에셋 예산 경고
- **왜**: 아티스트가 내장 그래픽에서 얼마나 무거운 모델을 써도 되는지 알 수 없다.
- **방식**: 프로젝트 설정에 종류별 한도(캐릭터·소품·배경: 삼각형 수, 텍스처 크기, 뼈 수, 머티리얼 수)를 두고, 불러올 때와 Blender 애드온 내보내기 때 넘으면 경고한다. 에셋 브라우저(4단계)와 인스펙터에 예산 대비 사용량을 보여 준다.
- **기본값**: 템플릿에 내장 그래픽 기준 값을 넣고, 벤치마크로 고친다.

### [ ] 그래픽 회귀 테스트
- **왜**: 셰이더·포스트를 고치다 그림이 깨져도 사람이 보기 전에는 모른다.
- **방식**: `check.ps1`이 고정 장면 몇 개(조명 모델별, 포스트 켜고 끔)를 캡처해 저장소의 기준 이미지와 픽셀 비교한다(허용 오차 있음, UI 픽셀 비교와 같은 도구). 틀리면 차이 이미지를 `build\check\`에 남긴다. 의도한 변경이면 기준 이미지를 다시 만드는 옵션(`-UpdateGolden`).

### [ ] GPU 캡처 버튼과 에디터 보기 모드
- **GPU 캡처**: 에디터·Dev 빌드에서 PIX(`WinPixGpuCapturer`)·RenderDoc이 있으면 다음 프레임 캡처를 버튼·단축키로 남긴다. 없으면 버튼을 숨긴다. 그래픽 프로그래머용.
- **보기 모드**: 씬 뷰에서 오버드로(반투명 겹침), 와이어프레임, LOD 단계, 법선, 머티리얼 기능, 예산 초과 물체를 색으로 본다. 아티스트가 무엇이 비싼지 눈으로 확인한다. 출시 빌드에서는 코드가 빠진다.

### [ ] 텍스처와 머티리얼
- **방식**: glTF의 baseColor 텍스처를 불러올 때 **BC7(색)/BC5(법선)으로 압축**해 캐시 파일로 저장. 밉맵 포함.
  **Shader Model 6.6 bindless**(`ResourceDescriptorHeap[index]`)로 인스턴스의 텍스처 인덱스를 셰이더가 바로 읽는다(드로우 콜 수 유지). 최소 사양 11세대 결정으로 가능해졌다.
- **먼저 확인**: 11세대(Xe-LP) 실기에서 SM 6.6과 리소스 바인딩 티어 3 지원을 확인한다. 셰이더 프로파일을 `vs_6_6`/`ps_6_6`으로 올린다.
- **라이브러리 후보**: 이미지 디코딩 `stb_image`(퍼블릭 도메인), BC7 압축 `bc7enc_rdo`(MIT/퍼블릭 도메인). 압축은 에디터/불러오기 때만, 게임은 압축된 결과만 읽는다.
- **다른 플랫폼**: 모바일 GPU는 BC를 못 읽어 ASTC가 필요하다. 텍스처 캐시는 처음부터 "플랫폼별 형식" 칸을 두고(지금은 BC 하나), ASTC 압축기는 5단계 모바일 때 넣는다.
- **정점 형식**: UV를 추가하면 정점이 28 → 36바이트. 텍스처 없는 메시는 지금 형식을 유지할지 검토.
- **머티리얼**: glTF PBR metallic-roughness를 그대로 쓴다(Blender Principled BSDF가 내보내는 값). 지원 범위: baseColor·normal·metallicRoughness·emissive 텍스처와 계수, 알파 마스크. 그 밖의 확장(클리어코트, 투과 등)은 경고하고 무시한다.
  엔진 머티리얼 에디터·셰이더 그래프는 만들지 않는다. 에디터에서는 머티리얼을 고치지 않고 Blender에서 고친다.
- **스타일 프리셋 셰이더** (아티스트가 셰이더를 짜지 않는다):
  - **조명 모델**은 프로젝트 설정에서 하나 고른다: PBR / 툰(색 단계 램프 텍스처) / 조명 없음. 게임 아트 방향의 가장 큰 스위치다.
  - **머티리얼 기능**은 Blender의 사용자 속성(glTF `extras`)으로 켠다: 외곽선(뒤집은 껍질), 바람 흔들림(세기는 정점 색 채널로 칠함), 림 라이트, 디졸브. 모르는 키는 경고한다.
  - **인스턴스마다 바뀌는 값**(맞았을 때 번쩍임, 디졸브 진행도)은 인스턴스 데이터의 값 하나로 받고, `view/`가 틱 이벤트로 바꾼다. 인스턴스가 48바이트를 넘는지 확인한다.
  - 조합(조명 모델 × 기능)이 엔진에 고정돼 있으므로 **모든 셰이더 조합을 빌드 때 컴파일하고 PSO를 불러오기 화면에서 미리 만든다.** 처음 보는 효과에서 끊기는 일이 없다.

- **룩데브 미리보기**: 에디터에 고정 조명(중립 HDRI) + 회전 받침대 창을 둔다. 씬 조명과 상관없이 모델·머티리얼을 확인하고, 조명 모델과 HDRI를 바꿔 볼 수 있다.

### [ ] 하늘 HDRI와 환경광
- **왜**: 지금 하늘·환경광은 하늘색·땅색 두 가지 그라디언트라 금속·유광 재질이 밋밋하다.
- **방식**: 씬 환경에서 HDRI(`.hdr`, CC0 무료 HDRI 사용 가능)를 고르면 스카이박스로 그리고, 불러올 때 같은 HDRI에서 환경광(구면 조화 9계수)과 반사용 큐브맵(밉맵 = 거칠기)을 구워 캐시한다. HDRI가 없으면 지금 그라디언트를 쓴다.
- **비용**: 스카이박스 한 번 + 셰이더에서 계수·큐브맵 읽기. 매우 작다.

### [ ] 반사 프로브
- **왜**: 실내나 그늘에서도 하늘 큐브맵이 반사되어 어색하다.
- **방식**: 에디터에서 씬에 프로브 물체(`MEALKIT_OBJECT`)를 놓고 "굽기"를 누르면 그 자리의 큐브맵을 구워 `assets/`에 저장한다. 물체는 가장 가까운 프로브 하나를 쓴다(섞지 않음). 실시간 반사는 넣지 않는다.
- **제한**: 씬당 프로브 수를 프로젝트 설정으로 제한한다(기본 8개, 128² 큐브맵).

### [ ] 점광원
- **왜**: 지금은 태양 하나뿐이라 횃불·폭발 빛·실내 조명을 쓸 수 없다.
- **방식**: 포워드 렌더러 그대로, 물체마다 가까운 점광원 최대 4개(설정으로 8개)를 CPU에서 골라 인스턴스에 번호를 넣는다. 그림자는 없다(태양만). 씬 물체로 놓거나, 화면 쪽에서 효과(폭발 빛)로 잠깐 띄운다.
- **예산**: 광원 수백 개가 필요하면 보류 표의 Forward+.

### [ ] 그림자
- **방식**: 태양 방향 그림자 맵 1~2단계(CSM), 1024² ~ 2048². 플레이어 주변만 높은 해상도.
- **예산**: 내장 그래픽에서 1.5 ms 이하. 넘으면 설정에서 끄거나 1단계로.

### [ ] 스켈레탈 애니메이션
- **왜**: 지금 캐릭터는 상자/캡슐이다. 사람·동물 캐릭터를 쓰려면 필요하다.
- **방식**: cgltf가 이미 skin/animation을 읽는다. CPU에서 포즈 샘플링 + GPU 스키닝(뼈 행렬 버퍼), 뼈 64개 제한.
  애니메이션은 Blender 액션으로 만들어 glTF로 내보낸다. 엔진은 재생·섞기만 하고, 에디터는 인스펙터에서 클립 재생 미리보기만 한다.
- **결정론**: 화면용 애니메이션은 **보이기만** 한다. 히트박스·판정은 시뮬레이션의 캡슐로 한다. 화면용 애니메이션 결과가 시뮬레이션에 들어가면 안 된다.
- **시뮬레이션용 포즈 샘플링** (액티브 래그돌용, 결정 기록 참고): 래그돌 목표 포즈처럼 시뮬레이션이 써야 하는 포즈는 화면용과 **다른 경로**로 샘플링한다.
  시간은 틱 번호(실수 시간 아님), 보간은 사칙연산 `nlerp`와 결정론 수학 유틸만, 키프레임은 불러올 때 고정 순서로 굽는다. 결과는 `sim/`에서만 쓰고 화면용 애니메이션과 섞지 않는다.

### [ ] 파티클
- 먼지, 불꽃, 타격 효과. 결정론 밖(오디오와 같은 이벤트 방식): `view/`가 틱 이벤트를 받아 효과 이름 + 위치로 재생한다.
- **방식**: 효과는 외부 효과 도구에서 시각적으로 만든다. 1순위 후보 **Effekseer**(MIT, 전용 에디터, DX12 런타임). 엔진 안 파티클 에디터는 만들지 않는다.
- **먼저 확인** (결과로 확정하고 `third_party/` 규칙대로 넣는다): 최소 사양 내장 그래픽에서 효과 수십 개 GPU 시간, 출시 exe 크기 증가(예산 5 MB), 우리 렌더러(인스턴싱·bindless)와 같은 프레임에 그리는 방법.
- **후보가 맞지 않으면**: CPU 갱신 + 인스턴스 쿼드의 작은 자체 런타임. 효과 값은 `MEALKIT_STRUCT` 파일(`.fx`)로 두고 에디터 인스펙터 + 실시간 미리보기로 고친다(코드로 짜지 않는다).

### [ ] 포스트 프로세싱 (우버 패스 하나 + 색 보정 LUT)
- **왜**: 게임의 색감·분위기는 아티스트가 정해야 하는데, 지금은 코드나 환경 값으로만 바꿀 수 있다.
- **방식**: 내장 그래픽은 메모리 대역폭이 병목이라 효과마다 패스를 따로 두지 않고 **전체 화면 패스 하나(우버 포스트)**에 합친다. 블룸만 별도(절반 해상도 듀얼 필터).

  | 효과 | 들어가는 곳 | 예상 비용 (720p) |
  |---|---|---|
  | 톤 매핑 (AgX 또는 ACES) + 3D LUT | 우버 패스, 기본 켬 | 매우 작음 |
  | 비네트, 필름 그레인, 색수차 | 우버 패스 옵션 | 거의 0 |
  | 블룸 | 절반 해상도 듀얼 필터 → 우버 패스에서 합침 | 0.3~0.5 ms |
  | 안티에일리어싱 | FXAA 기본, 여유 있으면 SMAA | 0.2~0.5 ms |
  | 업스케일 | 동적 해상도와 함께 FSR 1 (MIT, 셰이더 하나) | 0.3 ms |

- **LUT**: `.cube`(32³). 에디터 환경 패널에서 LUT 파일을 고르고, "보정용 캡처" 버튼이 중립 LUT를 넣은 화면 캡처를 남겨 외부 도구(DaVinci Resolve·Photoshop 등)에서 보정 → `.cube`로 내보낸다.
- **편집**: 포스트 값은 씬 환경의 `MEALKIT_STRUCT`로 두고 에디터 환경 패널 슬라이더로 바로 고친다. 화면용 값이라 콘텐츠 해시·결정론과 무관하다. 효과마다 설정에서 끌 수 있다.
- **넣지 않는 것**: SSAO(대신 Blender에서 AO를 정점 색·텍스처로 구워 온다), 피사계 심도·모션 블러·SSR은 보류 표.
- **비용**: 합쳐서 1 ms 이하(GPU 예산 "포스트"). 벤치마크로 확인.

### [ ] 동적 해상도
- GPU 시간이 예산을 넘으면 3D 해상도를 낮추고 업스케일. UI는 원래 해상도로 그린다.

## 3단계 (v0.7): 멀티플레이를 단단하게

### [ ] 중간 참가와 재접속
- **왜**: 지금은 매치가 시작되면 새로 들어올 수 없고, 한 명이 끊기면 다시 못 들어온다.
- **방식**: 호스트가 특정 틱의 **월드 상태 스냅샷**(게임 상태 + Jolt 상태 `SaveState`)을 압축해 보내고, 그 뒤 입력을 따라잡는다(빨리 감기).
- **결정론**: 스냅샷 복원 후 `hash()`가 호스트와 같아야 한다. `mp_test.ps1`에 "늦게 들어온 클라이언트" 시나리오 추가.

### [ ] 리플레이 저장
- 락스텝이라 **매치 시작 값(시드, `matchData`, 플레이어별 로드아웃) + 콘텐츠 해시 + 틱별 입력과 확정 명령**만 저장하면 된다(4인 30분 ≈ 수백 KB). 디싱크 디버깅에도 쓴다.
- **버그 재현 파일**: 에디터 플레이나 게임에서 "기록 저장"을 누르면 리플레이 파일이 남고, 에디터에서 열어 같은 상황을 그대로 다시 재생한다(0단계 되감기와 같은 데이터).

### [ ] 디싱크 진단 도구
- 디싱크가 나면 양쪽이 틱별 해시 + 바디별 상태를 덤프하고, 처음 갈라진 틱과 바디를 알려 주는 비교 도구(`tools/desync_diff`).

### [ ] EOS 백엔드 (크로스플레이 로비·릴레이)
- **왜**: 크로스플레이는 플랫폼 공통 로비·P2P가 필요하다(1단계 온라인 서비스 계층 표). 5단계 이식 전에 Windows에서 먼저 검증해 두면 이식 때 네트워크 문제와 플랫폼 문제가 섞이지 않는다.
- **방식**: EOS Connect로 Steam 계정(또는 기기 ID)에 로그인해 Product User ID를 얻고, EOS 로비로 방을 만들고, EOS P2P를 `net::Transport`로 쓴다. Steam 친구 초대는 EOS 로비 id를 실어 보낸다.
  크로스플레이를 켜면 매치 전송은 EOS 하나다(한 매치에 Steam 릴레이와 EOS가 섞이지 않는다).
- **확인할 것**: EOS P2P 패킷 크기 상한(지금 엔진 상한 1200바이트보다 작으면 엔진 상한을 낮춘다), 릴레이 RTT, 4인 대역폭이 예산(10 KB/s) 안인지, 호스트 이전과 로비 소유자 변경.
- **비용**: Epic 개발자 포털 등록(무료). SDK DLL은 exe 예산 밖이지만 출시 폴더 크기에 들어간다.
- **결정론**: 영향 없음 (`mp_test`에 EOS 전송 시나리오).

### [ ] 호스트 이전
- 방장이 나가면 남은 피어 중 하나가 호스트를 이어받는다. Steam 로비 소유자 변경과 맞춘다.

## 4단계 (v0.8): 게임플레이 프레임워크와 툴

### [ ] 게임 흐름 프레임워크 (GameMode / GameState)
- **왜**: 라운드, 타이머, 팀, 점수, 승리 조건은 거의 모든 멀티플레이 게임이 다시 만든다. 지금 sandbox는 매치 시작·끝 개념이 없다.
- **방식**: 시뮬레이션 안의 매치 상태 머신 `대기 → 카운트다운 → 진행 → 라운드 끝 → 결과 → (다음 판)`. 상태 전환은 틱 번호로 정하고(실수 타이머 없음), 규칙(라운드 수, 제한 시간, 승리 조건, 팀 수)은 튜닝 데이터로 둔다.
  전환이 일어나면 매치 상태 시스템이 게임 함수(`onRoundStart(World&)`, `onPawnDied(World&, ...)` 등)를 직접 호출한다(콜백 등록·구독 없음, `docs/CODING_MODEL.md` "시뮬레이션 안에서 알리기"). 점수판은 `PlayerSlot`에 둔다.
- **결정론**: 매치 상태 전부 `hash()`에. 화면(1단계 "기본 화면 흐름")은 이 상태를 읽기만 한다.
- **의존**: 0단계 플레이어·캐릭터 분리.

### [ ] 캐릭터 이동 모드
- **왜**: 지금 sandbox의 물리 캡슐 하나뿐이다. 게임마다 원하는 조작감이 달라 매번 이동 코드를 새로 짠다.
- **방식**: 상속이 아니라 Pawn 종류마다 **이동 모드 + 튜닝 데이터**를 고른다. 입력(`GameInput`) → 이동 의도(방향, 점프 등) → 모드별 처리 → 물리.

  | 모드 | 방식 | 어울리는 게임 | 주의 |
  |---|---|---|---|
  | 키네마틱 (기본) | Jolt `CharacterVirtual` | 정확한 조작, 계단·경사·움직이는 발판 | 결정론을 `mp_test`로 먼저 검증 |
  | 물리 캡슐 (지금 sandbox) | 리지드바디 + 속도 제어 | 밀치기 파티 게임 | 계단·경사가 어색함 |
  | 플로팅 | 아래로 레이캐스트 + 스프링·감쇠로 띄움 | 물리 상호작용 + 부드러운 이동 | 스프링 튜닝 값 필요 |
  | 액티브 래그돌 | Jolt `Ragdoll` + 모터가 목표 포즈를 따라감 | 몸 개그 물리 게임 | 아래 참고 |

- **순서**: 키네마틱 → 플로팅 → 액티브 래그돌. 물리 캡슐은 지금 코드를 모드로 옮긴다.
- **액티브 래그돌**: 2단계 스켈레탈 애니메이션의 "시뮬레이션용 포즈 샘플링"에 의존한다. 비용은 캐릭터당 바디 약 11~15개와 컨스트레인트. 4인 기준 틱 예산(4 ms) 안인지 벤치마크로 확인하고, 넘으면 관절 수를 줄인 간이 래그돌을 쓴다.
- **결정론**: 모든 모드는 Pawn id 순서로 처리하고, 각도 계산은 결정론 수학 유틸만 쓴다. 모드별 상태는 `hash()`에.

### [ ] 가상 카메라 (시네머신 방식) + 컷신
- **왜**: 카메라는 조작감의 절반인데 게임마다 처음부터 만든다. 카메라 전환·연출도 코드로 짜면 아티스트가 만질 수 없다.
- **가상 카메라**: 씬에 `VirtualCamera` 물체(`MEALKIT_OBJECT`, 장식 종류라 콘텐츠 해시 제외)를 놓고 우선순위, 따라갈 대상, 바라볼 대상, 데드존·화면 구도, 몸체 종류를 정한다.
  몸체 종류: 3인칭 스프링암(벽에 부딪히면 당김), 1인칭, 탑다운, 궤도, 레일(경로를 따라감), 관전 자유 카메라(빙의 없음일 때). 기본 대상은 빙의한 Pawn.
- **카메라 브레인**: `view/`의 브레인이 활성 가상 카메라 중 우선순위가 가장 높은 것으로 정해진 시간·이징으로 블렌드한다. 게임 코드는 카메라를 직접 움직이지 않고 우선순위·활성만 바꾼다.
- **임펄스(흔들림)**: 1단계 "이벤트 → 연출 표"에서 만든 카메라 임펄스를 브레인 결과에 더한다.
- **컷신**: 외부 도구 원칙대로 **Blender에서 카메라 애니메이션을 만들어 glTF로 내보낸다.** 엔진은 재생만 하고 타임라인·시퀀서 에디터는 만들지 않는다(보류 표). 컷신 중 이벤트(소리·효과)는 glTF 마커 이름 → 연출 표로 낸다.
- **멀티플레이**: 컷신이 시뮬레이션을 멈추면 안 된다(락스텝). 시작은 시뮬레이션 틱 이벤트로 정해 모두 같은 틱에 보고, 그동안 입력만 막는다. 혼자 보는 연출(죽었을 때 등)은 화면 쪽에서 바로 재생한다.
- **결정론**: 영향 없음 (`view/`에서만). 지금처럼 이동 방향을 카메라 기준으로 계산해 월드 방향으로 양자화해 보낸다. 벽 충돌 레이캐스트는 화면용 질의로, 시뮬레이션 상태를 바꾸지 않는다.

### [ ] 소스 모듈 시스템 (기능 재사용)
- **왜**: 체력바, 스킬 쿨타임, 미니맵, 인벤토리, 절차적 맵 생성처럼 게임마다 조금씩 다르지만 자주 쓰는 기능을 매번 처음부터 만든다.
  엔진 기본 기능으로 넣으면 엔진이 무거워지고 설계를 하나로 강요한다. 프리팹은 데이터(배치)만 담아 `sim/` 로직을 실어 나를 수 없다. 바이너리 플러그인(DLL)은 정적 단일 출시 exe·SimCheck와 맞지 않는다.
- **방식**: 모듈 = 폴더 하나(`modules/<이름>/`). 안에 `sim/`(상태 `MEALKIT_STRUCT` + 시스템 함수), `view/`(그리기, 뷰 모델 채우기), Penpot 원본과 `.ui` 컴포넌트, 튜닝 기본값, 프리팹, `module.txt`(이름, 버전, 엔진 버전, 의존 모듈).
  - 프로젝트에 **소스째 복사**한다(`mealkit.project`의 `modules=` 목록). 게임이 코드를 고쳐 쓸 수 있고, `mealkit_add_game()`이 같이 모아 SimCheck도 그대로 검사한다.
  - 모듈 함수는 게임의 `World`를 모른다. 자기 상태만 받는다. 예: `cooldown::step(Cooldowns&, u32 tick)`. 게임이 상태를 `WorldState`에 필드로 넣고 `World::step()`에서 순서대로 부른다.
  - 업데이트는 프로젝트 업그레이드 도구와 같은 방식: 고치지 않은 파일(해시 기록)만 새것으로 바꾸고, 고친 파일은 `.new`로 남긴다.
  - 에디터 프로젝트 설정에 모듈 목록(추가·제거·업데이트). 엔진 저장소의 `modules/`가 공식 모듈, 다른 사람 모듈은 폴더·git 주소로 추가한다.
- **공식 모듈 (첫 목록)**:

  | 모듈 | sim | view·UI | 비고 |
  |---|---|---|---|
  | 체력·데미지 | 히트 질의(구·캡슐·레이), 데미지(가해자, 양, 종류), 체력, 무적 틱, 사망 → Pawn 제거 → 리스폰 대기 → 새 Pawn에 빙의 | 체력바·데미지 숫자 `.ui` | 게임은 데미지 계산 규칙만 바꾼다. 히트 결과는 id 순서로 처리 |
  | 쿨타임 | `TickTimer` 묶음 | 쿨타임 아이콘 `.ui` | |
  | 인벤토리 | 고정 배열 슬롯, 아이템 정의는 정의 데이터 표(`.table`) | 그리드 `.ui` | 세이브·매치 시작 데이터와 연결 |
  | 미니맵 | 없음 | 위에서 본 렌더 또는 아이콘 | 화면 전용 |
  | 절차적 생성 | 시드 하나로 생성(`Pcg32`, 결정론 수학) | 없음 | 락스텝에 잘 맞는다(맵 대신 시드만 보낸다). 에디터에서 `.scene`으로 구워 손보는 방식도 제공 |
  | 기본 오브젝트 | 트리거 볼륨, 경로를 따라 움직이는 키네마틱 발판, 아이템 스폰 지점 | 없음 | 0단계 오브젝트 타입 시스템 위에 |

- **결정론**: 모듈 상태는 게임 `WorldState`의 필드라 해시·스냅샷에 자동으로 들어간다. 갱신은 id 순서.
- **의존**: 플레이어·캐릭터 분리, 게임 흐름 프레임워크(체력 모듈의 사망·리스폰), 게임 UI(모듈의 `.ui`).

### [ ] AI 길찾기 (그리드 / 웨이포인트)
- **왜**: AI 컨트롤러가 장애물을 돌아가려면 경로가 필요하다.
- **방식**: 에디터에서 씬 충돌 데이터로 2D 그리드(높이 층 포함)를 굽거나 웨이포인트를 놓고, 시뮬레이션에서 A*로 찾는다. 새 외부 라이브러리 없음. 결과는 에디터 디버그 그리기로 확인.
- **결정론**: 구운 데이터는 콘텐츠 해시에 넣는다. A*의 동점 처리는 노드 번호로 고정하고, 한 틱에 찾는 경로 수를 제한해 순서대로 처리한다.
- **Recast 내비메시**는 보류 표 참고.

### [ ] 프리팹
- 여러 물체 묶음을 파일로 저장하고 씬에 여러 번 배치. 에디터의 복제를 확장.
- 프리팹은 데이터(배치·필드 값)만 담는다. 동작은 `sim/` 코드라 프리팹으로 옮길 수 없고, 동작까지 재사용하려면 소스 모듈이 프리팹을 같이 담는다.

### [ ] 에디터 에셋 브라우저
- `assets/` 트리, 모델 미리보기 썸네일, 끌어서 씬에 놓기.
- **이름 바꾸기·옮기기**: 에셋은 경로로 참조하므로(`docs/CODING_MODEL.md` "에셋 참조와 적재"), 브라우저에서 바꾸면 그 경로를 참조하는 씬·튜닝·`.ui`·연출 표를 같이 고친다. 탐색기에서 바꿔 참조가 끊긴 것은 불러올 때 경고하고 목록으로 보여 준다.

### [ ] 하이트맵 지형
- 하이트맵 + 청크 LOD 렌더링, Jolt `HeightFieldShape` 충돌. 에디터 브러시(올리기/내리기/평탄화).
- 외부 지형 도구(Gaea·World Machine 등)에서 만든 16비트 PNG 하이트맵을 가져올 수 있다. 가져온 뒤 브러시로 다듬는다. 충돌 데이터라 콘텐츠 해시에 들어간다.
- **뿌리기 브러시**: 풀·돌·작은 소품을 지형이나 바닥 위에 칠해서 수천 개를 배치한다(밀도·크기·회전 무작위 범위). 화면 전용 인스턴스라 충돌·결정론·콘텐츠 해시와 무관하고, 청크별로 묶어 컬링한다. 충돌이 필요한 큰 물체는 보통 씬 물체로 놓는다.

### [ ] Job System
- 렌더링 준비(컬링, 인스턴스 채우기, 애니메이션 포즈)를 병렬화. 물리는 이미 Jolt 스레드 풀을 쓰므로 같은 워커를 나눠 쓸지 검토.

### [ ] 크래시 리포트
- 예외 핸들러에서 미니덤프 + 로그를 `crash/`에 저장. 친구 PC에서 난 문제를 재현할 때 필요.

### [ ] 업적·리더보드·통계 (온라인 서비스 계층)
- 게임이 업적 조건을 시뮬레이션 이벤트(라운드 승리, 처치 수)로 정하고, 화면 쪽이 이벤트를 읽어 온라인 서비스 계층에 기록한다(Steam / EOS / 콘솔 트로피). 업적 목록은 데이터 하나로 두고 각 서비스 등록용으로 내보낸다. 서비스가 없으면 사용자 데이터 폴더의 통계에만 남긴다.
- **결정론**: 영향 없음 (결과만 읽는다).

### [ ] 프로젝트 namespace 정리
- 새 프로젝트를 만들 때 게임 코드의 `namespace sandbox`를 프로젝트 이름으로 바꾼다. (새 프로젝트 만들기 자체는 0단계 프로젝트 관리자로 옮겨 간다.)

### [ ] 에셋 쿠킹 + 팩 파일
- **왜**: 지금은 게임이 실행될 때마다 glTF를 파싱하고 meshoptimizer로 최적화·LOD를 만든다. 원본 에셋도 출시 폴더에 그대로 노출된다.
- **방식**: 출시 빌드 때 모델·씬·텍스처를 엔진 전용 바이너리로 바꿔 팩 파일 하나(`<이름>.pak`)에 담는다. 에디터는 계속 원본을 쓴다.
- **무엇을 넣나**: 시작 씬과 프로젝트 설정의 씬 목록에서 시작해 참조(씬 → 모델·프리팹, 튜닝·`.ui`·연출 표 → 소리·효과·이미지)를 따라가 **닿는 것만** 넣는다. 유니티 Resources처럼 폴더를 통째로 넣는 방법은 없다.
  코드에서 경로 문자열로만 여는 에셋은 참조를 따라갈 수 없으므로, 프로젝트 설정의 "항상 포함" 목록에 적는다(빠뜨리면 출시 빌드가 경고).
- **효과**: 로딩이 거의 즉시, 출시 exe에서 cgltf·meshoptimizer 제거.
- **주의**: 물리 껍질 점은 최적화 전 원본 정점에서 뽑아야 한다(결정론). 콘텐츠 해시는 쿠킹 결과 기준으로 계산하고, "에디터에서는 되는데 게임에서는 다르다" 버그를 막도록 에디터 플레이에서도 쿠킹본으로 돌려 보는 옵션을 둔다.

**에디터·디버깅 편의** (아래 항목들)

## 5단계 (v0.9): 다른 플랫폼, 다른 OS 에디터, 크로스플레이

플랫폼 계층(1단계)과 RHI 층(2단계, DX12 + Vulkan) 위에 다른 OS 구현과 남은 그래픽 백엔드(Metal, WebGPU, 콘솔)를 더한다. 시뮬레이션 결정론은 1단계부터 CI가 Linux·macOS에서 검사하고 있다. 목표는 **모든 플랫폼이 한 매치에 같이 들어오는 크로스플레이**와 **Windows·macOS·Linux 어디서나 쓰는 에디터**다.
플랫폼마다 시작할 때 최소 사양·성능 예산 표를 만들고, 기준 샘플 전부가 그 플랫폼에서 Export·`mp_test`(다른 플랫폼 피어 포함)를 통과해야 끝난다.

**플랫폼 등급**:
- **1군** (v0.9·v1.0이 기다린다): Windows, Linux·Steam Deck, macOS. 에디터와 출시 둘 다.
- **2군** (순서대로 하되 v1.0을 막지 않는다): Android·iOS, 웹, 콘솔. 출시만. 콘솔은 개발자 등록과 개발 키트가 생겨야 시작할 수 있다.

| 순서 | 플랫폼 | 그래픽 | CPU·컴파일러 | 먼저 확인할 것 | 비고 |
|---|---|---|---|---|---|
| 1 | Linux · Steam Deck | Vulkan (2단계에 있음) | x64 · Clang (헤드리스는 1단계부터) | Windows exe가 Proton(vkd3d-proton)에서 그대로 도는지(1단계 Steam 실검증 때). 되면 출시는 급하지 않지만 Linux 에디터에는 네이티브가 필요하다 | Steam 그대로. 대소문자를 구분하는 파일 시스템 |
| 2 | macOS | Metal | ARM64 · Clang (헤드리스는 1단계부터) | Metal 백엔드, 앱 번들 | Steam 그대로. 서명·공증 |
| 3 | Android · iOS | Vulkan / Metal | ARM64 · Clang | 모바일 GPU 예산(타일 GPU, 발열), 터치 입력, ASTC, 앱 수명 주기(백그라운드로 가면 매치는?) | Steam 없음 → EOS |
| 4 | 웹 | WebGPU | wasm · Clang | UDP가 없다(WebRTC 데이터 채널 전송), 스레드(SharedArrayBuffer·COOP/COEP), Jolt wasm 크기 | bindless 없음(RHI 층 참고), wasm 5 MB 예산 |
| 5 | Xbox | DX12 (GDK) | x64 · MSVC | 가장 가깝다. GDK의 DX12 차이와 인증 요구 | 콘솔 공통은 아래 "콘솔" |
| 6 | PlayStation 5 | 전용 API | x64 · Clang | 전용 그래픽 API 백엔드 | |
| 7 | Switch (2) | 전용 API (NVN) 또는 Vulkan | ARM64 · Clang | 가장 약한 GPU라 따로 최소 사양 표 | |

### [ ] 플랫폼 사이 결정론 — 실기기 사이 마무리 (CI 검사는 1단계부터)
- **왜**: 락스텝은 모든 피어가 같은 float 결과를 내야 한다. 지금은 MSVC·x86(SSE4.2)만 검증했다. 다른 플랫폼은 컴파일러(Clang)와 CPU(ARM)가 다르다.
- **방식**:
  - 모든 컴파일러에서 실수 연산 축약을 끈다: MSVC `/fp:precise`(지금 그대로), Clang·GCC `-ffp-contract=off`, `-ffast-math` 금지. ARM은 FMA 명령이 기본이라 이 옵션이 필수다. Jolt도 같은 옵션(`CROSS_PLATFORM_DETERMINISTIC=ON` 유지).
  - 시뮬레이션 코드(`sim/`, 엔진 `physics`·`DetMath`)에는 플랫폼 분기(`#ifdef`, 플랫폼별 라이브러리)를 두지 않는다. SimCheck가 `sim/`의 플랫폼 매크로를 막는다.
  - `detmath-bits` 단위 테스트 해시가 모든 플랫폼 빌드에서 같아야 한다.
  - `mp_test`에 "다른 플랫폼 피어" 모드: 두 기기를 이어 봇 입력 900틱 이상. 헤드리스 시뮬레이션(1단계)으로 GPU 없이 돌려 CI에서 플랫폼마다 틱별 해시를 남기고 비교한다.
- **이미 하는 것**: 1단계 CI가 Windows(MSVC·clang-cl)·Linux x64·macOS ARM64에서 같은 입력 기록의 틱별 해시를 매 커밋 비교한다. 이 항목은 그 위에 실제 네트워크로 서로 다른 기기를 잇는 시험과, 모바일·웹(wasm)·콘솔 CPU·컴파일러를 더한다.
- **통과 전까지**: 콘텐츠 해시에 "결정론 그룹"(예: `msvc-x64`, `clang-arm64`)을 넣어 다른 그룹 피어는 접속을 거부한다. 통과한 그룹을 하나로 합쳐 간다.
- **실패하면**: 보류 표 "고정소수점 게임플레이 수학"을 다시 본다.

### [ ] 크로스플레이
- **같은 매치의 조건**:
  - 결정론 그룹이 같다(위 항목).
  - **시뮬레이션 버전**이 같다. exe는 플랫폼마다 달라 exe 해시로 비교할 수 없으므로, 게임 버전 + `sim/`·엔진 시뮬레이션 소스 해시를 빌드 때 박아 비교한다(1단계 "버전 표시와 접속 거부 이유"에서 정한다).
  - 콘텐츠 해시는 플랫폼 공통 데이터(씬 충돌 데이터, 모델 물리 껍질, 튜닝, 표)로만 계산한다. 플랫폼별 쿠킹 결과(텍스처 형식, 셰이더, 화면용 메시)는 넣지 않는다.
- **접속 경로**: 플랫폼마다 릴레이가 달라(Steam 릴레이, 콘솔 네트워크) 서로 닿지 않는다. 플랫폼 공통 로비·P2P 릴레이가 필요하다 → 1단계 "온라인 서비스 계층", 3단계 "EOS 백엔드". 크로스플레이 매치는 항상 EOS 로비·P2P로 잡는다.
- **입력 차이**: 로비가 플레이어별 입력 종류(키보드·마우스 / 게임패드 / 터치)를 매치 시작 데이터에 담아 보여 주고, 섞을지는 게임 설정으로 정한다. 콘솔 정책대로 설정에 "크로스플레이 끄기"를 둔다.
- **결정론**: 위 조건이 맞으면 지금 락스텝 그대로다. 플랫폼별 코드는 화면·입력 양자화 전까지만 있다.

### [ ] 다른 OS 에디터 (macOS, Linux)
- **의존**: 그 OS의 플랫폼 계층과 RHI 백엔드(에디터도 그 백엔드로 그린다).
- **핫 리로드**: 게임 코드를 `.so`/`.dylib`로 빌드해 지금처럼 복사본을 불러온다(`dlopen`). macOS는 서명된 라이브러리 규칙을 확인한다.
- **엔진 공유 라이브러리**: `mealkit.dll`의 MSVC 전용 내보내기(`cmake/FixExportsDef.cmake`) 대신 Clang은 기호 공개 설정으로 같은 결과를 낸다.
- **빌드 스크립트**: `.bat`과 Windows PowerShell 5.1 스크립트를 모든 OS에서 도는 하나로 옮긴다(후보 PowerShell 7 — 지금 `.ps1`을 거의 그대로 쓸 수 있다). 에디터의 [빌드] 메뉴와 프로젝트 관리자도 이것을 부른다.
- **파일 경로**: 에셋 경로는 `/`와 대소문자를 정확히 쓴다. Windows에서도 대소문자가 다른 참조를 `check_layout`이 오류로 잡는다(Linux에서 처음 드러나지 않게).
- **다른 플랫폼 Export**: 에디터가 있는 OS에서 만들 수 없는 출시본(macOS·iOS는 macOS에서만)은 원격 빌드나 CI로 넘기는 길을 그때 정한다.

### [ ] 콘솔 (Xbox, PlayStation, Switch)
- **시작 조건**: 각 플랫폼 개발자 프로그램 등록과 개발 키트.
- **코드 위치**: 콘솔 SDK와 그 위의 코드는 NDA라 이 저장소에 넣지 않는다. 플랫폼 계층 구현·RHI 백엔드·온라인 서비스 백엔드를 비공개 저장소에 두고, CMake가 그 경로(`MEALKIT_PRIVATE_PLATFORMS`)가 있으면 넣는다(Steam SDK의 Stub 방식과 같다).
- **인증 요구를 미리 설계에 넣는다** (나중에 넣으면 앱 흐름을 다시 짠다):
  - 일시정지·재개(앱이 멈췄다 돌아옴): 락스텝 매치에서는 끊김으로 처리하고 재접속(3단계)으로 돌아온다.
  - 사용자 로그인·전환, 컨트롤러 연결 끊김 안내.
  - 세이브는 플랫폼 세이브 API로(사용자 데이터 폴더 직접 쓰기를 막는 플랫폼이 있다) → 1단계 세이브는 플랫폼 계층의 저장 함수로만 쓴다.
  - 업적·친구·초대는 온라인 서비스 계층(콘솔 플랫폼 서비스 백엔드, 크로스플레이 로비는 EOS).
- **최소 사양**: Switch는 따로 표를 만든다(내장 그래픽 프리셋보다 낮을 수 있다).

| 스크립트 언어 (Lua 등) | 보류 | 즉시 수정·모딩이 되지만, 결정론 VM 개조가 필요하고 C++보다 수십 배 느리며 두 언어 디버깅. 0단계 핫 리로드 + 튜닝 데이터화가 효과 대부분을 가져간다 | 핫 리로드로도 부족하거나 모딩이 목표가 될 때 |
| 범용 ECS | 보류 | 객체 수만 개·유연한 조합에 유리하지만, 지금의 단순한 배열과 명시적 실행 순서(결정론 디버깅에 유리)를 잃는다 | 시스템 수·객체 수가 배열 구조로 감당 안 될 때 |
| 언리얼식 Actor 상속 계층 | 넣지 않음 | 빙의 구조만 가져오고(0단계 "플레이어와 캐릭터 분리") 상속 트리·가상 `Tick`은 쓰지 않는다. 실행 순서가 숨고 결정론 디버깅이 어려워진다 | - |
| 싱글톤·서비스 로케이터·DI 컨테이너 | 넣지 않음 | 엔진 기능은 인자(`GameContext&`, `World&`)로 받는다. 전역 상태는 그림자 시뮬레이션(World 두 개)과 핫 리로드를 깨뜨린다 (`docs/CODING_MODEL.md`) | - |
| 시뮬레이션 안의 코루틴·async | 넣지 않음 | 완료 시점이 PC마다 달라 디싱크가 나고, 코루틴 프레임은 해시·스냅샷할 수 없다. 틱 타이머와 `enum` 상태 머신을 쓴다 | - |
| 셰이더 그래프, 엔진 안 머티리얼 에디터 | 넣지 않음 | 머티리얼은 glTF PBR로 Blender에서 만든다. 셰이더 조합이 늘면 내장 그래픽 예산과 컴파일 시간을 관리할 수 없다 | glTF 범위로 안 되는 모양이 여러 게임에서 반복될 때 (그때도 엔진 셰이더 기능으로) |
| 엔진 안 파티클 에디터 | 넣지 않음 | 외부 효과 도구가 맡는다. 맞는 도구가 없으면 필드 선언 + 인스펙터 미리보기로 | - |
| 게임 프로젝트의 자체 셰이더 ("표면 함수" HLSL 조각) | 보류 | 셰이더 조합·예산을 엔진이 관리한다. 넣는다면 테크니컬 아티스트가 `Surface surf(Input)` 함수 하나만 쓰고 조명·그림자·안개는 엔진이 붙이는 방식(셰이더 핫 리로드로 확인) | 물·용암처럼 스타일 프리셋으로 안 되는 모양이 꼭 필요할 때 |
| 화면 공간 외곽선 (깊이·법선 경계) | 보류 | 툰 스타일에만 쓰이고 0.3 ms 정도 든다. 먼저 머티리얼의 뒤집은 껍질 외곽선을 쓴다 | 툰 스타일 게임에서 껍질 외곽선이 부족할 때 |
| SSAO, 피사계 심도, 모션 블러, SSR | 보류 | 내장 그래픽 포스트 예산(1 ms)을 넘는다. AO는 Blender에서 구워 온다 | 최소 사양을 올리거나 "고품질" 프리셋을 만들 때 |
| 에디터 안 UI 디자이너 | 넣지 않음 | Penpot이 맡는다. 에디터는 미리보기 패널만 둔다 | - |
| Figma 연동 | 보류 | 클라우드 전용이고 REST API 호출 제한이 빡빡하다. `.ui`가 중간 형식이라 나중에 Figma 플러그인만 따로 만들 수 있다 | 디자이너가 Figma만 쓸 수 있을 때 |
| HTML/CSS·XAML UI 미들웨어, Rive | 넣지 않음 | 런타임이 크고 무겁다. 상태 전환(시간·이징)으로 기본 움직임은 된다 | 벡터 애니메이션이 게임의 핵심 연출일 때 Rive만 다시 본다 |
| UI 양방향 바인딩, 식 언어, 변환기 | 넣지 않음 | 단방향 뷰 모델 + 액션 하나로 정한다. 입력 위젯만 자기 필드에 쓴다 | - |
| UI 키프레임 애니메이션 (타임라인) | 보류 | 상태 전환으로 시작한다. Penpot 프로토타입 애니메이션은 가져오지 않는다 | 화면 연출 요구가 상태 전환으로 안 될 때 |
| UI 블러 효과 (레이어·배경) | 보류 | 내장 그래픽에서 비싸다. 플러그인이 경고한다 | 성능 예산에 여유가 확인될 때, 끌 수 있는 옵션으로 |
| 글자 모양 조합 (HarfBuzz) | 보류 | 한국어·영어·일본어는 필요 없다 | 아랍어·태국어·힌디어 지원이 필요할 때 |
| Recast 내비메시 | 보류 | 경사·다층 지형에서 정확하지만 큰 외부 라이브러리이고 결정론을 따로 검증해야 한다. 그리드·웨이포인트 길찾기(4단계)를 먼저 쓴다 | 넓은 열린 맵이나 복잡한 다층 지형에서 그리드가 부족할 때 |
| 보이스 챗 | 보류 | 디스코드 권장 (`docs/GUIDE.md` "보이스 챗") | 게임 안 음성이 꼭 필요할 때 Steam Voice 선택 모듈 |
| Rust (엔진·게임 코드 언어) | 넣지 않음 | 위 결정 기록 (빌림 검사기와 게임 코드, 핫 리로드, 생태계) | SimCheck로 못 막는 메모리 버그가 반복될 때 |
| 계정 서버·게임 DB (자체 백엔드) | 보류 | 서비스 운영 문제이고 엔진이 무거워진다. 계정·순위·저장은 Steam으로 | 진행 데이터 조작이 게임에 치명적이거나 Steam 밖 출시가 필요할 때. 그때도 외부 백엔드(Nakama 직접 운영, PlayFab 등)를 게임 모듈로 붙인다 |
| 서버 검증 (로드아웃·진행 데이터) | 보류 | 권위 서버가 없다. 협동·친구끼리 게임에서는 감수한다 | 경쟁 랭크 게임을 만들 때 (계정 서버와 같이) |
| 비동기 에셋 적재·스트리밍 (Addressables식) | 보류 | 매치 단위 동기 적재가 단순하고 순서 문제가 없다 | 로딩 화면이 길어지거나 열린 월드를 만들 때 (Job System 이후) |
| DLC·모드용 추가 팩 | 보류 | `.pak` 덧씌우기로 할 수 있지만 콘텐츠 해시·버전 관리가 늘어난다 | DLC나 모딩이 목표가 될 때 |
| 에셋 GUID·`.meta` 파일 | 넣지 않음 | 경로 참조 + 에디터가 이름 바꾸기 때 참조를 고친다. `.meta`는 버전 관리에서 짝이 어긋나는 문제가 크다 | - |
| 바이너리 플러그인 (게임 기능 DLL) | 넣지 않음 | 출시 exe는 정적 단일 파일이고 `sim/` 코드는 SimCheck를 통과해야 한다. 소스 모듈을 쓴다 | - |
| 엔진 안 타임라인·시퀀서 에디터 | 넣지 않음 | 컷신 카메라·애니메이션은 Blender에서 만든다 | 여러 캐릭터·소리·효과를 맞춘 긴 컷신이 게임의 핵심일 때 |

1. ~~프로젝트 설정~~ → ~~프로젝트 관리자·에디터 언어·exe 아이콘~~ → **위험 확인**(최소 사양 실기·다른 PC 결정론·clang-cl 비교 → Steam 실검증 + 온라인 서비스 계층) → **플랫폼 계층**(+ POSIX 최소 구현) → 헤드리스 시뮬레이션(+ 입력 기록 재생, Linux·macOS 빌드) → CI 빌드 매트릭스(OS·CPU 사이 해시 비교) → ~~라이선스(MIT)~~ → 공개 범위 결정 → 문서 저장소 → **데이터 분리**(화면용 튜닝 + 시간 값 초 → 프로젝트 폴더 구조 강제 → 예제 데이터 분리 정리 → 정의 데이터 표) → 기준 샘플 규칙 → 오디오 → 이벤트 → 연출 표 → 입력 액션 매핑 → 게임패드 → 확정 명령 채널 → 디버그 UI(ImGui) → 로컬라이제이션 → 게임 UI(`.ui` 런타임 + 미리보기 패널) → 설정 시스템 + 표준 설정 화면 → 세이브(진행 데이터) → 매치 시작 데이터(로드아웃) → 기본 화면 흐름 → 네트워크 흉내 → 입력 지연 자동 조절 → 내 캐릭터 겉모습 예측 → 틱레이트 설정 → 버전 표시·접속 거부 이유 **(v0.5)**. 디자이너가 생기면: Penpot 플러그인 + 가져오기 서버 → 배치·픽셀 비교 검사
