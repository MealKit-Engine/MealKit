# Aster 엔진 로드맵

엔진에 넣을 기능과 순서. 게임 프로젝트(`D:\GameEngine\Aster\<게임>`)에서 필요한 것을 기준으로 정했다.
끝낸 항목은 `[x]`로 표시하고, 순서가 바뀌면 이 문서를 고친다.

## 판단 기준

모든 기능은 아래 순서로 따져서 넣을지 정한다.

1. **3D + 멀티플레이를 해치지 않는가.** 시뮬레이션에 닿는 기능은 락스텝 결정론(README "결정론 규칙")을 지켜야 한다.
2. **가벼움과 속도.** 목표 하드웨어는 Intel 내장 그래픽 사무용 PC, **최소 사양은 Intel 11세대(Xe 내장 그래픽) 이상**이다. 아래 예산을 넘는 기능은 끌 수 있어야 한다.
3. **DX12만 쓴다.** RHI 추상화와 다른 API 백엔드는 만들지 않는다.
4. **외부 라이브러리는 꼭 필요할 때만.** Windows에 기본으로 있는 API(XAudio2, XInput 등)를 먼저 쓰고, 그다음 파일 하나짜리 라이브러리를 고른다.

### 성능 예산 (최소 사양 Intel 11세대 Xe 내장 그래픽, 1280×720, 60 fps 기준)

"현재" 값은 최소 사양보다 빠른 Core Ultra 5 125U(Xe-LPG)에서 잰 것이다. 최소 사양 실기에서 다시 재야 한다.

| 항목 | 예산 | 현재 |
|---|---|---|
| 프레임 전체 (GPU) | 8 ms 이하 (60 fps에서 절반을 여유로 남김) | 약 0.3 ms |
| 시뮬레이션 틱 (30 Hz) | 틱당 4 ms 이하 | 0.9~2.5 ms (바디 2,000개) |
| 드로우 콜 | 200회 이하 | 4회 |
| 네트워크 (4인, 호스트 송신) | 10 KB/s 이하 | 약 5 KB/s |
| 게임 실행 파일 | 5 MB 이하 (에셋 제외) | 약 1.4 MB |

## 현재 있는 것 (v0.3)

DX12 포워드 렌더러(인스턴싱, 정점 색), Jolt 물리(결정론), 입력만 보내는 락스텝(UDP/Steam), glTF 모델 + LOD,
`.scene` 씬, 내장 에디터(기즈모, 되돌리기, 플레이 모드, 출시 빌드), Tracy 프로파일링, 프로젝트 템플릿.

**없는 것 중 게임을 만들 때 바로 막히는 것**: 소리, 화면 글자(HUD·메뉴), 게임패드, 텍스처, 중간 참가.

**툴로서 불편한 점**: 게임이 에디터에 자기 오브젝트 종류를 추가할 수 없다(`EntityKind`가 엔진에 고정). 튜닝 값이 코드 상수라 숫자 하나에도 빌드가 필요하다.
코드를 고치면 에디터를 닫아야 빌드된다. 상태 하나를 추가하면 구조체·`step`·`hash`·그리기 네 곳을 고쳐야 하고, `hash`를 빠뜨려도 에러가 나지 않는다.

## 0단계 (v0.4): 개발자 경험

기능을 더 쌓기 전에 툴부터 편하게 만든다. 툴이 불편한 채로 기능을 쌓으면 나중에 그 기능들을 다시 고쳐야 한다.
원칙: **무엇을 어디에, 얼마나는 에디터(데이터)에서, 어떻게 동작하는지는 코드에서** 다룬다. 비주얼 스크립팅은 만들지 않는다.

### [ ] 게임 정의 오브젝트 타입 + 인스펙터 필드
- **왜**: 지금 에디터에 놓을 수 있는 물체 종류(`Solid`/`Decoration`/`SpawnPoint`)가 엔진 `Scene.h`에 박혀 있다. 코인·트리거·점프대를 만들려면 엔진을 고쳐야 한다.
- **방식**: 게임 코드가 타입과 필드를 한 번 선언하면 에디터의 `추가` 메뉴와 인스펙터에 자동으로 나타나고 `.scene`에 저장된다. `World`는 매치를 시작할 때 읽는다.
  ```cpp
  ASTER_OBJECT(JumpPad) {
      ASTER_FIELD(f32, power, 12.0f, "점프 힘");
      ASTER_FIELD(u32, cooldownTicks, 30, "재사용 대기(틱)");
  };
  ```
- **기존 종류**: 상자·장식·스폰도 이 시스템 위의 기본 타입으로 옮긴다. 기존 `.scene`은 그대로 읽히게 한다.
- **결정론**: 필드 값은 콘텐츠 해시에 포함한다(장식용 필드는 표시해서 제외). 순회는 오브젝트 id 순서.

### [ ] 튜닝 값을 데이터로
- **왜**: 이동 속도·점프력·쿨다운이 `World.cpp`의 `constexpr`이라 값 하나 맞추는 데도 빌드가 필요하다.
- **방식**: 위와 같은 필드 선언으로 게임 전역 설정(`assets/game.tuning` 같은 텍스트 파일)을 만들고 에디터 패널에서 고친다.
  에디터 혼자 플레이에서는 값을 바꾸면 바로 적용, 멀티플레이에서는 매치 시작 때 고정하고 콘텐츠 해시에 넣는다.

### [x] 고도식 범용 에디터 + 게임 DLL 핫 리로드 (결정·완료 2026-10-15)
- **구현됨**: `AsterEditor.exe` + `aster.dll`(Editor 빌드, RelWithDebInfo, 동적 CRT), 프로젝트 관리자(최근 목록, 폴더 열기, 새 프로젝트),
  `aster.project`, `<이름>_game.dll`(게임 코드만, 다시 빌드 수 초), 원본 DLL 감시 핫 리로드, `Ctrl+R` 게임 코드 빌드, 빌드 실패 시 이전 DLL 유지,
  엔진이 더 새것이면 열 때 자동 빌드, `GameInstance` API 버전 검사. 출시 exe는 그대로(결정론 해시 동일 확인).
- **남은 것**: 디버거가 붙어 있으면 PDB가 잠겨 핫 리로드 빌드가 실패할 수 있다(PDB 이름을 빌드마다 바꾸는 방식 검토).
  aster.dll을 다시 빌드할 때는 에디터를 닫아야 한다. 디버그 CRT용 에디터 구성(EditorDebug)은 아직 없다.
- **왜**: 지금은 프로젝트마다 에디터 exe가 따로 있고 게임 코드가 그 안에 들어 있어서, 코드를 고치면 에디터를 닫고 빌드하고 다시 열어야 한다. 에디터와 VS Code를 같이 띄워 놓고 일할 수 없다.
- **구조**:
  - 엔진 저장소가 **에디터 하나**(`AsterEditor.exe`)를 만든다. 실행하면 **프로젝트 관리자**(최근 프로젝트, 열기, 새 프로젝트)가 뜨고, 프로젝트 폴더를 연다.
  - 프로젝트는 에디터용으로 **게임 DLL**(`<이름>_game.dll`: World, GameSession)만 빌드한다. 에디터가 이 DLL을 불러 플레이 모드를 돌린다.
  - VS Code에서 DLL만 다시 빌드하면 에디터가 편집 모드에서 바꿔 끼운다(씬·카메라·선택 유지). 컴파일 에러는 에디터 로그 창에도 표시.
  - **출시용 `<이름>.exe`는 지금처럼 정적 단일 exe** (가벼움, 결정론 영향 없음).
- **설계 결정할 것**:
  - 에디터와 게임 DLL이 엔진을 같이 써야 하므로(`PhysicsWorld`, `ModelCache` 등), 에디터 구성에서는 엔진도 DLL(`aster.dll`)로 만들고 CRT는 동적(`/MD`)으로 쓴다. 출시 구성은 정적 그대로.
  - 게임 DLL 진입점은 C 함수 하나(`asterGameCreate`)와 **API 버전 번호**. 엔진과 DLL 버전이 다르면 불러오지 않고 다시 빌드하라고 알린다(크래시 대신).
  - 에디터 플레이와 출시본이 네트워크로 섞이지 않도록 콘텐츠 해시에 빌드 구성을 포함한다.
- **Dev 빌드 구성**: 최적화는 켜고 링크 시간 최적화(LTCG)는 끈 구성. 게임 DLL 다시 빌드를 수 초로 줄인다.
- **영향**: `new_project.ps1`, 프로젝트 템플릿, `aster_add_game()`, 에디터 [빌드] 메뉴(프로젝트 경로를 실행 중에 알게 됨)가 바뀐다. 프로젝트의 `editor.bat`은 엔진 에디터에 프로젝트 경로를 넘기는 역할만 남는다.
- **단점(감수)**: DLL 경계 관리, 엔진·DLL 버전 불일치 처리, 디버깅 설정이 조금 복잡해진다.

### [ ] 게임 코드 구조: `sim/` · `view/` 폴더와 결정론 검사
- **왜**: 모든 규칙이 `World::step()` 하나로 모여 기능이 늘면 한 파일이 수천 줄이 된다. 결정론 규칙은 지금 사람이 기억해야 한다.
- **방식**: 템플릿을 `source/sim/`(결정론, 시스템별 파일: Players, Combat, Pickups, Match), `source/view/`(카메라, 그리기, UI, 소리), `source/app/`(main)으로 나눈다.
  `World::step()`은 시스템을 정해진 순서로 **명시적으로 호출만** 한다(각자 `Update()`를 도는 방식은 쓰지 않는다).
- **검사**: `sim/`에서 `sin`/`cos`/`rand`/`<chrono>`/렌더러 헤더를 쓰면 빌드가 실패하도록 금지 헤더나 검사 스크립트를 둔다.
- **CMake**: `file(GLOB ... CONFIGURE_DEPENDS)`로 바꿔 파일을 추가할 때 `CMakeLists.txt`를 고치지 않게 한다.

### [ ] 상태 필드를 한 번만 선언
- **왜**: 새 상태 하나에 구조체, `step`, `hash`, 그리기를 고쳐야 하고, `hash`를 빠뜨려도 조용히 디싱크 감지에서 빠진다. 중간 참가(스냅샷)를 넣으면 한 곳이 더 는다.
- **방식**: 시뮬레이션 상태도 필드 선언(위와 같은 장치)으로 만들고 **해시, 스냅샷 저장·복원, 에디터 실시간 보기**를 자동 생성한다. 3단계 "중간 참가"의 기반.

### [ ] 씬 트리 계층 (부모·자식)
- **왜**: 여러 물체를 묶어 옮기기, 움직이는 발판 위의 장식 같은 경우 부모·자식이 필요하다.
- **방식**: `Entity`에 `parent` id를 두고 에디터에서는 트리로 보여 준다(끌어서 부모 변경). **게임이 불러올 때 월드 좌표로 펼쳐** 실행 중에는 지금처럼 평평한 배열로 둔다(속도·결정론 유지). 4단계 "프리팹"과 이어진다.

### [ ] 에디터에서 여러 명으로 플레이
- **왜**: 멀티플레이 엔진인데 여러 명 테스트는 명령줄로 창을 직접 띄워야 한다.
- **방식**: 플레이 버튼 옆에서 "플레이어 2~4명"을 고르면 현재 씬(저장 안 된 편집 포함, 임시 파일로)으로 `--host --local` 창 1개 + 참가 창을 자동으로 띄운다.
  추가 창은 봇 입력 또는 직접 조작. 정지하면 모두 닫는다. 유니티 Multiplayer Play Mode에 해당.

### [ ] 그림자 시뮬레이션으로 디싱크 즉시 감지
- **왜**: 결정론 실수는 지금 `mp_test`를 돌려야 드러나고, 어디서 났는지 찾기 어렵다.
- **방식**: 에디터 플레이 중 같은 입력으로 `World`를 하나 더 돌리고 매 틱 해시를 비교한다. 다르면 즉시 멈추고 틱·상태 차이를 보여 준다.
- **잡는 것 / 못 잡는 것**: 초기화 안 된 변수, 포인터 주소 순서, 실제 시간 읽기, 전역 상태는 잡는다. CPU마다 다른 계산(FMA 등)은 못 잡는다(`mp_test`, 다른 PC 테스트로).
- **비용**: 시뮬레이션 CPU 2배 (에디터에서만, 끌 수 있게).

### [ ] 일시정지, 한 틱씩 진행, 되감기
- **왜**: 버그가 난 순간을 다시 보기 어렵다. 결정론이라 입력만 기록하면 어느 틱으로든 돌아갈 수 있다.
- **방식**: 에디터 플레이 중 입력을 기록하고 일정 간격(예: 5초)마다 스냅샷을 남긴다. 타임라인 슬라이더로 가까운 스냅샷에서 빨리 감아 원하는 틱으로 간다. 일시정지 중에는 상태 인스펙터로 값을 본다.
- **의존**: "상태 필드를 한 번만 선언"의 스냅샷 기능.

### [ ] 주기적 자동 저장
- **왜**: 지금은 에디터를 정상 종료할 때만 `.autosave`를 남긴다. 크래시가 나면 그 사이 작업이 사라진다.
- **방식**: 변경이 있으면 1~2분마다 `.autosave`에 쓰고, 다음 실행 때 복구할지 묻는다. 원본 파일은 덮어쓰지 않는다.

## 1단계 (v0.5): 게임이 되게 하는 최소 기능

게임을 실제로 내놓으려면 빠져서는 안 되는 기능. 대부분 렌더링·시뮬레이션과 독립적이라 결정론 위험이 낮다.

### [ ] 오디오
- **왜**: 지금 엔진에는 소리가 전혀 없다. 효과음·배경음 없이는 게임이 되지 않는다.
- **방식**: XAudio2(Windows 기본 포함, 새 의존성 없음). 효과음은 WAV, 배경음은 Ogg Vorbis 스트리밍.
- **API 초안**: `audio::Engine::play(SoundId, Vec3 position, f32 volume)`, 리스너 = 카메라. 3D 감쇠·좌우 패닝(X3DAudio).
- **라이브러리 후보**: `stb_vorbis` (퍼블릭 도메인, 파일 하나)로 Ogg 디코딩.
- **결정론**: 소리는 렌더링처럼 **결과만 읽는다.** 시뮬레이션이 "이벤트"(충돌, 점프)를 남기면 프레임 쪽에서 재생한다. 시뮬레이션이 오디오 상태를 읽으면 안 된다.
- **비용**: CPU 코어 하나의 1% 미만. 개발 중간.

### [ ] 게임 화면 UI (글자, HUD, 메뉴)
- **왜**: 지금은 점수·로비 상태를 창 제목으로만 보여 준다. 에디터의 ImGui는 게임 실행 파일에 넣지 않는다(크기와 원칙).
- **방식**: 글꼴 아틀라스(한글 포함) + 사각형/글자 스프라이트를 한 번의 드로우 콜로 그리는 2D 레이어. 즉시 모드 API(`ui::text`, `ui::button`).
- **한글**: 완성형 2,350자 + 영문을 미리 구운 아틀라스(약 1~2 MB), 또는 쓰는 글자만 런타임에 굽기.
- **라이브러리 후보**: `stb_truetype` (퍼블릭 도메인) 또는 오프라인 도구로 SDF 아틀라스를 만들고 엔진은 텍스처만 읽기.
- **같이 할 것**: 로비 화면(방 만들기/참가/Steam 초대), 일시정지 메뉴, 설정(해상도·수직동기·음량).

### [ ] 게임패드
- **방식**: XInput (Windows 기본 포함). `Input`에 스틱·트리거·버튼 추가, 키보드와 같은 `GameInput` 8바이트로 양자화.
- **결정론**: 이미 입력 단계에서 양자화하므로 영향 없음.
- **비용**: 작음. 하루 이틀.

### [ ] Steam 실검증
- **왜**: SDK(v1.65)로 컴파일·링크만 확인했다. 실제 로비·초대·릴레이는 아직 검증하지 않았다.
- **할 일**: 두 계정(또는 두 PC)으로 `--steam` → 초대 → `+connect_lobby` 참가 → 900틱 이상 디싱크 없음 확인. 끊김·재시도·NAT 상황 로그.
- **같이 할 것**: Steam 오버레이가 DX12 스왑체인 위에 뜨는지 확인.

### [ ] 입력 지연 자동 조절
- **왜**: 지금은 `--delay 3`(100 ms) 고정이다. LAN에서는 너무 길고, 먼 상대에게는 짧아서 멈칫거린다.
- **방식**: 호스트가 피어별 RTT를 보고 매치 시작 때(그리고 진행 중에는 천천히) 입력 지연을 정해 모두에게 같은 틱부터 적용한다.
- **결정론**: 지연 변경 자체를 틱 번호와 함께 확정 입력으로 보내야 한다.

### [ ] 내 캐릭터 겉모습만 예측
- **왜**: 입력 지연(약 100 ms) 때문에 내 조작이 늦게 느껴진다. 롤백 넷코드는 비용이 너무 크다(보류 표).
- **방식**: 시뮬레이션은 그대로 두고, 화면에서만 내 캐릭터를 아직 확정되지 않은 내 입력으로 미리 움직여 그린다. 확정 상태가 오면 부드럽게 맞춘다.
- **결정론**: 영향 없음 (`view/`에서만 한다). 다른 플레이어·물체와의 충돌은 확정 후에 보인다.

### [ ] 틱레이트를 프로젝트 설정으로
- **왜**: 30 Hz 고정. 물체가 적은 액션 게임은 60 Hz가 반응·충돌 정확도에 낫다.
- **방식**: 프로젝트 설정 `tickRate`(30 기본, 60 선택). 콘텐츠 해시에 포함.
- **비용**: 60 Hz는 시뮬레이션 CPU와 입력 패킷이 2배. 바디 수천 개짜리 게임에는 쓰지 않는다.

## 2단계 (v0.6): 보기 좋게 (그래픽)

모두 **끌 수 있는 옵션**으로 넣고, 내장 그래픽 프리셋을 기본값으로 둔다.

### [ ] 프러스텀 컬링
- **왜**: 지금은 화면 밖 물체도 모두 인스턴스 버퍼에 넣는다. 맵이 커지면 바로 비용이 된다.
- **방식**: `DrawList::add` 전에 바운딩 구로 CPU 컬링. 물체가 수만 개가 되면 메시별 묶음 단위로 먼저 걸러낸다.
- **비용**: 작음. 다른 그래픽 기능보다 먼저 한다.

### [ ] 텍스처와 머티리얼
- **방식**: glTF의 baseColor 텍스처를 불러올 때 **BC7(색)/BC5(법선)으로 압축**해 캐시 파일로 저장. 밉맵 포함.
  **Shader Model 6.6 bindless**(`ResourceDescriptorHeap[index]`)로 인스턴스의 텍스처 인덱스를 셰이더가 바로 읽는다(드로우 콜 수 유지). 최소 사양 11세대 결정으로 가능해졌다.
- **먼저 확인**: 11세대(Xe-LP) 실기에서 SM 6.6과 리소스 바인딩 티어 3 지원을 확인한다. 셰이더 프로파일을 `vs_6_6`/`ps_6_6`으로 올린다.
- **라이브러리 후보**: 이미지 디코딩 `stb_image`(퍼블릭 도메인), BC7 압축 `bc7enc_rdo`(MIT/퍼블릭 도메인). 압축은 에디터/불러오기 때만, 게임은 압축된 결과만 읽는다.
- **정점 형식**: UV를 추가하면 정점이 28 → 36바이트. 텍스처 없는 메시는 지금 형식을 유지할지 검토.

### [ ] 그림자
- **방식**: 태양 방향 그림자 맵 1~2단계(CSM), 1024² ~ 2048². 플레이어 주변만 높은 해상도.
- **예산**: 내장 그래픽에서 1.5 ms 이하. 넘으면 설정에서 끄거나 1단계로.

### [ ] 스켈레탈 애니메이션
- **왜**: 지금 캐릭터는 상자/캡슐이다. 사람·동물 캐릭터를 쓰려면 필요하다.
- **방식**: cgltf가 이미 skin/animation을 읽는다. CPU에서 포즈 샘플링 + GPU 스키닝(뼈 행렬 버퍼), 뼈 64개 제한.
- **결정론**: 애니메이션은 **보이기만** 한다. 히트박스·판정은 시뮬레이션의 캡슐로 한다. 애니메이션 결과가 시뮬레이션에 들어가면 안 된다.

### [ ] 파티클
- 먼지, 불꽃, 타격 효과. CPU 갱신 + 인스턴스 쿼드, 결정론 밖(오디오와 같은 이벤트 방식).

### [ ] 동적 해상도
- GPU 시간이 예산을 넘으면 3D 해상도를 낮추고 업스케일. UI는 원래 해상도로 그린다.

## 3단계 (v0.7): 멀티플레이를 단단하게

### [ ] 중간 참가와 재접속
- **왜**: 지금은 매치가 시작되면 새로 들어올 수 없고, 한 명이 끊기면 다시 못 들어온다.
- **방식**: 호스트가 특정 틱의 **월드 상태 스냅샷**(게임 상태 + Jolt 상태 `SaveState`)을 압축해 보내고, 그 뒤 입력을 따라잡는다(빨리 감기).
- **결정론**: 스냅샷 복원 후 `hash()`가 호스트와 같아야 한다. `mp_test.ps1`에 "늦게 들어온 클라이언트" 시나리오 추가.

### [ ] 리플레이 저장
- 락스텝이라 **시드 + 씬 해시 + 틱별 입력**만 저장하면 된다(4인 30분 ≈ 수백 KB). 디싱크 디버깅에도 쓴다.
- **버그 재현 파일**: 에디터 플레이나 게임에서 "기록 저장"을 누르면 리플레이 파일이 남고, 에디터에서 열어 같은 상황을 그대로 다시 재생한다(0단계 되감기와 같은 데이터).

### [ ] 디싱크 진단 도구
- 디싱크가 나면 양쪽이 틱별 해시 + 바디별 상태를 덤프하고, 처음 갈라진 틱과 바디를 알려 주는 비교 도구(`tools/desync_diff`).

### [ ] 호스트 이전
- 방장이 나가면 남은 피어 중 하나가 호스트를 이어받는다. Steam 로비 소유자 변경과 맞춘다.

## 4단계 (v0.8): 게임플레이 프레임워크와 툴

### [ ] 기본 오브젝트 종류 (트리거, 움직이는 발판, 아이템)
- **왜**: 대부분의 게임이 쓰는 종류를 엔진이 미리 제공해, 프로젝트마다 다시 만들지 않게 한다.
- **방식**: 0단계의 오브젝트 타입 시스템 위에 만든다: 트리거 볼륨, 경로를 따라 움직이는 키네마틱 발판, 아이템 스폰 지점. 범용 ECS는 만들지 않는다(가벼움).
- **결정론**: 오브젝트 id 순서로 갱신, 새 상태는 `hash()`에.

### [ ] 프리팹
- 여러 물체 묶음을 파일로 저장하고 씬에 여러 번 배치. 에디터의 복제를 확장.

### [ ] 에셋 핫 리로드 (모델·텍스처·씬)
- 에디터가 `assets/` 변경을 감지(`ReadDirectoryChangesW`)해 모델·텍스처·씬을 다시 읽는다. Blender에서 내보내면 바로 반영.

### [ ] 에디터 에셋 브라우저
- `assets/` 트리, 모델 미리보기 썸네일, 끌어서 씬에 놓기.

### [ ] 하이트맵 지형
- 하이트맵 + 청크 LOD 렌더링, Jolt `HeightFieldShape` 충돌. 에디터 브러시(올리기/내리기/평탄화).

### [ ] Job System
- 렌더링 준비(컬링, 인스턴스 채우기, 애니메이션 포즈)를 병렬화. 물리는 이미 Jolt 스레드 풀을 쓰므로 같은 워커를 나눠 쓸지 검토.

### [ ] 크래시 리포트
- 예외 핸들러에서 미니덤프 + 로그를 `crash/`에 저장. 친구 PC에서 난 문제를 재현할 때 필요.

### [ ] 프로젝트 namespace 정리
- 새 프로젝트를 만들 때 게임 코드의 `namespace sandbox`를 프로젝트 이름으로 바꾼다. (새 프로젝트 만들기 자체는 0단계 프로젝트 관리자로 옮겨 간다.)

### [ ] 에셋 쿠킹 + 팩 파일
- **왜**: 지금은 게임이 실행될 때마다 glTF를 파싱하고 meshoptimizer로 최적화·LOD를 만든다. 원본 에셋도 출시 폴더에 그대로 노출된다.
- **방식**: 출시 빌드 때 모델·씬·텍스처를 엔진 전용 바이너리로 바꿔 팩 파일 하나(`<이름>.pak`)에 담는다. 에디터는 계속 원본을 쓴다.
- **효과**: 로딩이 거의 즉시, 출시 exe에서 cgltf·meshoptimizer 제거.
- **주의**: 물리 껍질 점은 최적화 전 원본 정점에서 뽑아야 한다(결정론). 콘텐츠 해시는 쿠킹 결과 기준으로 계산하고, "에디터에서는 되는데 게임에서는 다르다" 버그를 막도록 에디터 플레이에서도 쿠킹본으로 돌려 보는 옵션을 둔다.

**에디터·디버깅 편의** (아래 항목들)

### [ ] 헤드리스 시뮬레이션
- 창과 GPU 없이 `World`만 N틱 돌리는 모드(`--headless`). 규칙 테스트가 몇 초로 끝나고, CI·AI로 자동 검증하기 쉽다. `mp_test`도 렌더링 없이 돌 수 있게 한다.

### [ ] 디버그 그리기 API

  `sim/`에서 부를 때는 그리기 요청만 기록한다(시뮬레이션이 렌더링 상태를 읽지 않게).

### [ ] 성능 패널과 예산 경고
- 프레임·틱·네트워크·드로우 콜을 이 문서의 성능 예산과 함께 보여 주고, 넘으면 빨갛게 표시한다. 지금은 상태 표시줄과 창 제목에만 나온다.

### [ ] 에러·오브젝트에서 코드로 이동
- 빌드 로그·런타임 로그의 `파일:줄`을 클릭하면 VS Code에서 그 줄을 연다(`code -g file:line`).
- 인스펙터의 오브젝트 타입 옆 "코드 열기"로 그 타입의 선언으로 간다.

### [ ] 로그 콘솔 창
- 지금 로그는 stdout으로만 나간다. 에디터 안에서 레벨별 필터·검색.

### [ ] 다중 선택
- 지금은 한 번에 하나만 선택된다. 드래그 박스 선택, Shift 클릭, 여러 개를 한 번에 이동·복제·삭제.

### [ ] 스냅·정렬 설정
- 그리드 크기, 회전 단위, 바닥에 붙이기, 정렬·균등 배치.

### [ ] 씬 여러 개 다루기
- 레벨 목록, 게임 시작 씬 지정, 에디터에서 씬 전환.

### [ ] 프로젝트 템플릿 여러 종류
- 빈 프로젝트, 아레나 대전(지금 예제), 레이싱·협동 같은 장르별 템플릿. 에디터의 "새 프로젝트"에서 고른다.

## 보류 / 넣지 않을 것

| 기능 | 결정 | 이유 | 다시 볼 조건 |
|---|---|---|---|
| Vulkan/OpenGL 등 다른 그래픽 API, RHI | 넣지 않음 | 절대 규칙 (DX12만) | - |
| 서버 권위형 넷코드 (스냅샷 보간, 예측) | 넣지 않음 | 락스텝이 물체 수와 무관하게 대역폭이 작다 | 수십 명 이상 장르를 만들 때 |
| 레이트레이싱, 디퍼드 렌더링, GI | 넣지 않음 | 내장 그래픽 예산을 넘는다 | - |
| 메시 셰이더 | 넣지 않음 | 최소 사양(Xe-LP)이 지원하지 않는다. GPU 주도 렌더링이 필요하면 ExecuteIndirect + 컴퓨트 컬링으로 | 최소 사양을 다시 올릴 때 |
| 롤백 넷코드 (GGPO 방식) | 보류 | 내 입력이 즉시 반응하지만, 틀릴 때마다 여러 틱을 다시 계산해야 해 물체 수천 개 게임에서는 예산을 넘는다. 대신 "내 캐릭터 겉모습만 예측"(1단계) | 물체가 적은 1:1 대전·격투 게임을 만들 때 |
| GPU 주도 렌더링 (GPU 컬링, ExecuteIndirect) | 보류 | 물체 수만 개에서 CPU 비용이 거의 0이 되지만 구현·디버깅이 어렵고, 수천 개 수준에서는 CPU 컬링이 충분하다 | 실제 게임에서 렌더링 준비 CPU 병목이 측정될 때 |
| Forward+ (광원 다수) | 보류 | 점광원 수백 개가 가능해지지만 내장 그래픽에서 컬링 패스 비용이 든다 | 밤 맵·실내처럼 광원이 많은 게임 |
| 고정소수점 게임플레이 수학 | 보류 | CPU·컴파일러와 무관한 결정론이지만, Jolt가 float라 두 체계가 섞이고 오버플로 버그가 새로 생긴다 | 다른 CPU 사이 디싱크가 실제로 발견될 때 |
