# MealKit coding model: one answer per problem

When the same problem has many approaches like in Unity (singletons / service locators / DI, pooling / ECS, coroutines / Task / UniTask …),
time goes into choosing every time, and shapes diverge even within one project. MealKit settles **just one answer** for each frequent design question.
The engine provides only the tools those answers need and blocks other approaches with build checks. The goal is that even code written without deliberation takes a shape that considers scalability and performance from the start.

- When you hit a question not in the table, don't answer it in code on your own. **Add a row to this document first**, then write the code.
- When changing an answer, record it in the `docs/DECISIONS.md` decision log. Projects don't use different answers.
- `sim/` is deterministic simulation code, `view/` is camera/drawing/UI/sound, `app/` is entry points and screen flow (ROADMAP stage 0).
- **(stage n)** before an answer means the answer is decided but the tool doesn't exist yet (an item in that ROADMAP stage). When that tool is needed, don't work around it with another approach; pull that item forward and build it. Answers without the mark are usable now.

## Answer table

### Structure

| Question | Common choices | MealKit's answer | Why |
|---|---|---|---|
| How to access engine features | singleton / service locator / DI container | **Take them as arguments.** The view side takes one `GameContext&` (`mealkit/game/GameContext.h`: window, input actions, renderer, assets, session, opening/joining matches (`match`), sound, feedback, strings, UI, player settings, view tuning), and `sim/` systems take only `World&`. No mutable global state. **Exceptions**: output-only features that nothing reads back (logging, profile markers, `MEALKIT_ASSERT`) are global functions. Process settings set once when a project opens and never changed during a match (`setProjectRoot`, `reflect::setTickRate`) are global too | The shadow simulation runs two Worlds in one process. With singletons that's impossible. Static state doesn't get tangled during hot reload |
| How to run the game without a window (headless/CI) | a separate main per game / the engine runs state without knowing game code / just an option on the shipping exe | **One class in `app/Headless.cpp` + `MEALKIT_HEADLESS_GAME(class)`** (`mealkit/game/Headless.h`, the same shape as the editor's `MEALKIT_GAME_MODULE`). The game provides only types (`World`, `TuningType`, `ProjectSettingsType`) and `startWorld` (match start)/`botInput`/`defaults` (optional); the engine handles reading data/the content hash (`game::loadMatchData`, the same function as the shipping exe/editor play/join windows), the command line (`game::parseGameArgs`, the same parser as the shipping exe), sessions, hash logs, input recording and replay, and output formats. `<game>_headless` links only `sim/` + this file with the engine core, and the shipping exe calls the same function with `--headless`. `GameSession` uses the same functions for match start and bot input too | The windowed game, editor, and headless use the same match start code, so hashes don't diverge. The output CI reads (`FINAL`, `REPLAY`, hash logs) is the same in every project. This file uses no `view/`/renderer headers, so it builds on Linux/macOS too |
| Frame loop for running windowed games (shipping exe, editor play, join windows) | a main per game / copying the loop per run mode | **One `game::Frontend` (`mealkit/game/Frontend.h`) holds the view-side services and runs them in the same order.** It holds input actions/gamepads/string tables/game UI/player settings/view tuning, builds a `GameContext` with `context()`, and every frame runs `update(now, dt, input, ctx)` before the game's `update` (strings → view tuning → pads → UI takes mouse/keyboard first → settings screen → actions), `afterBuildFrame(frame)` after `buildFrame` (world-space UI camera, listener position, screen color), and `renderUi` after 3D. Sound/feedback are created by the owner and lent (the editor shares them with the [Sound]/[Feedback] previews). **The shipping exe's main is the engine's `game::runGame`** (`mealkit/game/GameMain.h`): the game writes just one line `MEALKIT_GAME_MAIN(GameSession)` in `app/main.cpp` (the same shape as `MEALKIT_GAME_MODULE`/`MEALKIT_HEADLESS_GAME`; `--headless` is split off here too). The command line, window, renderer, session, Steam lobby, automated test output (`FINAL`, `SHADOW`, `REWIND`), and window title (`game.title`, `title.*` string keys) are handled by the engine. Editor join windows call the same `runGame` and pass only the differences via `GameRunOptions` | Adding a service, which used to mean editing three places (shipping exe, editor play, join windows) plus every project's `main.cpp`, becomes one place. Update order doesn't diverge per run mode. Engine features (performance numbers, screen flow) reach existing projects with just an engine upgrade. The shipping exe also uses `GameInstance` virtual calls, but only a few per frame, so there's no cost |
| What the engine builds | the engine builds everything / a plugin ecosystem | **The engine builds only the deterministic simulation, lockstep networking, renderer, and editor (placement/import/checks/debugging). Everything else uses finished external tools.** Authoring tools (Blender, Penpot, Effekseer, VS Code) freely. Runtime libraries: determinism verification if they touch the simulation, source included/version pinned (`third_party/`), permissive licenses, within the shipping exe budget | The engine stays light, and artists/developers use tools they already know. One library touching the simulation that breaks determinism breaks all of multiplayer |
| Dependencies between engine folders (which subsystem includes which) | freely / build modules that toggle each subsystem / runtime plugins (microkernel) | **Each folder is an engine module with an `engine-module.txt`; it includes only the kernel (`core`, `platform`, `jobs`) and the modules in its `requires`, which form a graph without cycles** (changed 2026-11-08 from one fixed folder order, `docs/ENGINE_MODULES.md`). Kinds: `kernel`, `sim` (simulation side, no view modules), `view`, `tool` (dev builds and the editor) | Without cycles, subsystems can be understood/tested/ported separately (headless links only the front part), and boundaries don't collapse when attaching source modules/other platforms. The shipping exe is at half its budget and the general-purpose editor is one DLL, so toggleable modules would add more check combinations than they gain now |
| Collecting and showing performance numbers (frame time, simulation time per tick, draw calls, network, sound voices) | computed directly per screen / a global profiler registry / Tracy only | **Measurement by each subsystem's own `stats()`** (`render::RenderStats`, `net::SessionStats`, `audio::Stats`, `GameInstance::takeSimMsPerTick`), **gathering/averaging/text by one `game::FrameStats` (`mealkit/game/FrameStats.h`).** The engine loop (shipping exe main, editor) calls `update(dt, {renderer, session, audio, game})` every frame; on the frame a report period (0.25 s) ends it returns `true` → `sample()` (including average/worst frame) and `line()` (one " | "-separated line)/`lines()` (one line per item). Missing sources (the session in edit mode etc.) are skipped. GPU time (RHI timestamps, per renderer pass `render::GpuPass`) is summed every frame and averaged, and the 1% worst frame (`frameMsPercentile`)/process memory/GPU memory go into the same batch. The window title/F1 overlay/automated run `perf:` log/editor status bar read only this, and the benchmark report (`game::Benchmark`, `--benchmark`: accumulating batches and frame times)/performance panel (stage 4) are built on it too. Timing inside functions is Tracy `MEALKIT_ZONE` (output-only global, Profile builds only) | The same number isn't computed differently per screen. Values that empty on read like `takeSimMsPerTick` aren't split between two readers. A registry is global state that gets read, so it isn't used (first row of this table), and lower layers don't call an upper profiler, keeping the folder order |
| Settings read by the simulation | a global settings object / reading the file every time | **The `World` copies tuning/scene data when the match starts and keeps it.** Systems read via `world.tuning`. It goes into the content hash, not the state hash | System arguments stay a single `World&` |
| Game object composition | inheritance / components / general ECS | **Flat arrays per kind + integer ids + system functions.** No inheritance or virtual `Update`. Rule for splitting arrays: **same array with a `kind` enum if the same systems process them, different arrays if different systems do.** Behaviors that may or may not be present are fields and flags | Cache-friendly with a fixed order (`DECISIONS.md`: no Actor inheritance, general ECS deferred) |
| Finding other objects | name/tag search / type search / holding references | **Store ids in fields and look them up in Pools.** Objects within a range are found with physics queries. There's no name/tag search | Lookup is O(1), and generation numbers tell when the target is gone |
| Creation and destruction | immediate creation/deletion / object pooling | **All simulation objects come from `Pool<T>` (`mealkit/sim/Pool.h`).** Creation is immediate (usable by id within this tick). But **they don't appear in iteration on the tick they're created.** Deletion only marks (excluded from `get`/iteration after that), and `endTick(onDestroy)` at the end of `World::step()` processes them in batch in slot order (physics body deletion in `onDestroy`). Ids carry generation numbers | No deliberating about pooling. Removes create/delete-during-iteration bugs, allocation spikes, and determinism problems at once. Creation is immediate, so projectiles don't come out a tick late |
| When a Pool is full | - | Capacity is set from data when the match starts (`World::reset`: in sandbox, boxes = sum of scene box spawn areas, controllers = players + the tuning's AI count, Pawns = controllers × 2). On overflow, creation fails (an invalid id, the same on all peers) and `MEALKIT_ASSERT` fires | Keeps determinism while being caught right away in Dev |
| Data that survives match/scene changes | never-destroyed singletons / static classes | **Inside a match it's `World` (scores in `PlayerSlot`), outside a match it's `app/` (`GameSession`, which owns the screen flow `Flow`'s screen state and the save `SaveData`), on disk it's the user data folder.** `GameInstance` stays alive between matches, and only `start`/`stop` are called again per match | There are only three places to choose from |
| Features reused across games (health, cooldowns, inventory, minimap, procedural generation) | built-in engine features / prefabs / binary plugins / asset store packages | **(stage 4)** **Source modules** (`modules/<name>/`: `module.txt`, `sim/`, `view/`, `assets/<kind>/`, details in `docs/MODULES.md`). One module = one git repo (official ones too); find them in the `MealKit-Modules` registry, copy them as source into the project with `tools\module.ps1` and modify freely, and update the way the upgrade tool does (only unedited files are refreshed). Module functions don't know the game's `World` and take only their own state (`cooldown::step(Cooldowns&, u32 tick)`; a module's `sim/` can't include `source/`). The game puts the state in as a `WorldState` field and the tuning as a nested `Tuning` field, and calls it from `World::step()` | The engine doesn't get heavier; prefabs hold only data and can't carry logic; DLLs don't fit the static shipping exe and SimCheck. Being source, SimCheck, hashes, and snapshots apply as is |

### Flow

| Question | Common choices | MealKit's answer | Why |
|---|---|---|---|
| Execution order and time | multiple Update phases + execution order settings, deltaTime | **`World::step()` calls systems in order.** `sim/` uses only integer ticks; the view uses only the interpolation `alpha` and frame `dt` | The order is visible in one place in code |
| Notifying within the simulation | events / delegates / message bus | **Call functions directly.** e.g. `damage(world, target, amount, source)`. No subscriptions or observers | Looking only at `step()` and the call paths shows who reacts when. Events would add another producer/consumer ordering rule |
| Notifying the view from the simulation (sound, effects, screen shake) | callbacks / the view guesses state changes | **A tick event array** (`mealkit::sim::TickEvents<T, N>`). `sim/` only writes with `world.events.push(Hit{...})` and never reads. Cleared at tick start. Each time `GameSession` calls `step()` it moves the events to a view-side queue, so nothing is dropped even if several ticks run in one frame. Events don't go into the state hash | The simulation doesn't know the view, and the view misses no events |
| Things that take time | coroutines / Task / async-await | **No async in `sim/`.** "N ticks later" is `TickTimer` (`mealkit/sim/TickTimer.h`, state is a single `u32 readyTick`), multiple steps are an `enum` state machine. **On the view/app side, one Job System (`mealkit/jobs/Jobs.h`: `parallelFor`, `run` → `Task::isReady()` polling).** Loading is still done synchronously on the loading screen until async loading comes. Coroutines, callbacks, `std::async` are banned | If async completion timing differs per PC, it desyncs. Since all state is data, snapshots and rewind work |
| Background work inside the engine/editor (file watching, UI import server, music streaming, build process) | callbacks / each thread its own way / event loop library | **One thread per feature; results go into a locked queue and the main thread takes them out at frame start.** Other threads don't touch engine/game state directly. If an external API calls a callback on its own thread (XAudio2 etc.), that callback only pushes to the queue too. This approach is used only in the engine's `platform/`, `audio/`, `editor/` code; game code (`sim/`, `view/`, `app/`) follows the row above | State is modified only on the main thread, so there are no locking bugs. It doesn't overlap with the Job System (short parallel computation) |
| Screen flow from title to results (menus, hosting/joining, lobby, pause, results) | the engine builds all the screens / each game opens sessions itself / a screen per scene | **Sessions are the engine's `game::MatchService` (`ctx.match`), screens are the game's `app/Flow`.** Game menus only call `ctx.match`'s `playOffline`, `host`, `hostOnline`, `join` (address or LAN room), `joinOnline`, `start`, `returnToLobby`, `leave`, and never open or close sessions directly (command line `--host`, `--join`, `--steam` are opened by the engine with the same functions). Which screen is shown is decided by the session phase (`ctx.match.phase()`: menu, connecting, lobby, match, disconnected) and the simulation phase (`mealkit::sim::MatchFlow`: waiting, countdown, playing, round end, results), and screens fill one `.ui` each (title, menu, join, lobby, loading, pause, results, notice) with view models. `sim/` decides the end of a match so all peers see results on the same tick, and the host sends everyone back to the lobby with `returnToLobby` (several matches per session). The engine calls `GameInstance::start` one frame after the loading screen once the match becomes Running, and `stop` when Running ends. Lobby names, ready, loadouts, and chat are `ctx.session`. If the game sets `GameInstance::menus()` to true, the engine doesn't use Esc/Enter | Session lifetime (Steam lobbies, LAN room announcements, rematch packets) isn't rewritten per game. Screen shapes and order are a template the game modifies. Results come from the simulation, so they don't differ per peer |
| Match flow (rounds, timers, teams, scores, win conditions) | each game writes its own phase enum and timers / a GameMode class with virtual hooks | **`mealkit::sim::MatchFlow` in `WorldState` + `advanceMatch()` once per tick.** It returns the transition of that tick (`FlowEvent`), and `sim/Match.cpp` switches on it and calls the game's functions (`onRoundStart`, ...). Rules are tuning (`MatchRules`: countdown, round length, rounds, score limit, lives/elimination, teams); the scoreboard is in `PlayerSlot` and passed in as `MatchPlayer` each tick | One tested implementation for every game, no callbacks, and all of it is hashed state |
| Character movement (walking, jumping, stairs, slopes) | each game writes its own controller / a Character class to inherit | **Each Pawn kind picks a `mealkit::sim::MoveMode` + `MoveTuning`** (`mealkit/sim/Movement.h`): Kinematic (Jolt `CharacterVirtual`, stairs/slopes/moving platforms), Capsule (rigid capsule, shoving), Floating (spring hover), Ragdoll (active ragdoll, `mealkit/sim/Ragdoll.h`: hovering pelvis + motorized parts, `knockRagdoll` goes limp). Input/AI → `MoveIntent` → `move()` before the physics step → `senseMover()` after it, in Pawn id order. The `Mover` is a Pawn field; characters are in physics snapshots/hashes | Control feel is a data choice, not rewritten per game, and every mode is hashed and snapshotted the same way |
| Pathfinding (AI going around obstacles) | navmesh library / each game's own grid | **`mealkit::sim::NavGrid`** (`mealkit/sim/NavGrid.h`): `bakeNavGrid` rays the static scene bodies at match start (before dynamic bodies) into a 2D grid with height layers, shrunk by the agent radius; `findPath` is A* with integer costs and (cost, node number) ordering. The grid is derived the same way on every peer, so it isn't state; waypoints are (a `MEALKIT_ARRAY` in the controller). Searches per tick are limited by the game and run in controller order | No external library, the same result on every platform, and a bounded cost per tick |
| State machines | enum switch / State pattern classes / graph tools | **`enum class` + `switch` + entry tick** | State is two integers, so hashing and snapshots are easy |
| Time values (cooldowns, respawn waits, durations) | tick counts / seconds (float) / frame counts | **Seconds in data, ticks in `sim/`.** Tuning, table, and scene fields are declared with the time type (`MEALKIT_FIELD(Ticks, name, Ticks::seconds(0.5f), ...)`), and appear in seconds in files and the editor. On load they're rounded once at the project tick rate into integer ticks, and `sim/` handles only integer ticks as now (`TickTimer::start(tick, world.tuning.respawn)`) | Changing the tick rate (30/60 Hz) doesn't require fixing data. Float time doesn't enter the simulation |
| Non-input commands into the simulation (cheats, input delay changes, pause votes, mid-match settings changes) | modify state directly / squeeze into input bytes / separate packet per command | **One confirmed command channel.** Separately from tick input (8 bytes per player), variable-length commands sent by peers are attached to the tick the host confirms and distributed to everyone like input (inside `net::TickInputs`). Command types are `MEALKIT_STRUCT`s in the game's `sim/` (no strings); the view side uses `sim::sendCommand(ctx.session, command)`, and at the very start of `World::step()` they're processed with `sim::forEachCommand` in a fixed order (player number → send order) (`mealkit/sim/Commands.h`). 256 bytes per tick, overflow goes to the next tick. They go into input recording and rewind too | The 8-byte input isn't enlarged. Modifying state directly desyncs other peers and the shadow simulation. Cheats and delay changes don't each make their own path |

### Data and I/O

| Question | Common choices | MealKit's answer | Why |
|---|---|---|---|
| Data and settings | asset objects / JSON / inspector serialization | **One field declaration** (`mealkit/core/Reflect.h`: `MEALKIT_STRUCT`/`MEALKIT_OBJECT`/`MEALKIT_FIELD`/`MEALKIT_TABLE`) → `.scene` object fields, `game.tuning`/`view.tuning`, `.table` rows, `mealkit.project`, saves (stage 1), state hash/snapshots, editor widgets. Scene objects are read with `scene::readObject<T>(entity)`. Assets are one `findAsset` path | Hashing, saving, and the inspector line up automatically |
| Where to put numbers (magic numbers) | code constants / everything in one settings file / ad hoc | **Game rule values (speed, mass, probability, cooldowns) → `Tuning` (`game.tuning`, content hash). Values that differ per map (areas, spawns, fall-death height, spawn counts) → scene objects (ranges/heights are the position/size of the area object `kObjectArea` itself, counts are fields). Values that are only visual (camera, colors, effect durations) → `ViewTuning` (`view.tuning`, excluded from the hash, applied immediately even during multiplayer, on the view side `ctx.viewTuning<ViewTuning>()`). Many rows of the same shape → `.table` (`MEALKIT_TABLE`). Time is written in seconds (see "Time values" below). Project-wide settings → `mealkit.project`.** The only things allowed to stay in code are unit conversions, algorithm constants (physics step counts etc.), and self-evident values like 0 and 1. SimCheck warns on float literals in `sim/` (SIM012), and algorithm constants are marked with `// const-ok: <reason>` at the end of the line | Changed without a build, and there's no wondering where to look. Values that go into the hash and those that don't split naturally |
| Many items of the same shape (weapons, items, skills, enemies) | ScriptableObject lists / JSON arrays / code arrays | **Definition data tables**: declare the row type with `MEALKIT_STRUCT`, register with `MEALKIT_TABLE(Row, "tables/x.table", flags)`, values in `assets/tables/*.table`. Other data references rows with `RowRef<Row>` (a name id), which is turned into an index on load (`data::resolveRows`, `sim::Table::find`) so `sim/` reads by index. When the app starts a match it reads them with `data::loadTable` and copies them into the `World`. Simulation tables are in the content hash, view-only tables (`kTableView`) are outside it. Editor [Tables] panel, CSV import/export (balancing in spreadsheets) | Designers work in spreadsheets, and hashing/widgets are handled by the field declarations |
| Per-project settings (tick rate, lighting model, asset budgets, scene list, modules) | several settings files / code constants / engine settings window | **One `mealkit.project`** (the engine's `game::ProjectSettings` (`mealkit/game/ProjectSettings.h`) + the game's added `GameClass::ProjectSettingsType`, with a `game.` prefix in the file). "path value" lines. Editor [File] > [Project Settings] window. The game executable reads it with `game::loadGameProject`, and the editor and tools also read the start scene from this file. Items that don't touch the simulation are excluded from the content hash with `MEALKIT_VIEW_FIELD`. Game rule values go in `Tuning`, not here | The same information doesn't live in two places (code and file) |
| String data such as names and paths | `char[N]` / fixed-length strings / `std::string` | **`std::string` fields** (`MEALKIT_FIELD(std::string, ...)`). Used in project settings, tuning, scene fields, `.table` rows. **Not put in simulation state (`WorldState`, Pool items)**: state holds ids or indices and names are looked up in data (`game::Simulation` blocks it at compile time. `RowRef` has an id string too, so the same applies) | No dealing with length limits or truncation. State byte copies and hashes stay correct as is |
| Project folder layout | free / by kind (Models, Textures) / by feature (Player, Weapon) | **One layout decided by the engine.** The project top level has `mealkit.project`, `source/` (`sim/`, `view/`, `app/`), `assets/` (what ships), `art/` (external tool sources: `.blend`, Penpot, PSD, excluded from shipping and hash), `modules/`, `third_party/`, and generated `build/`, `export/`. Directly under `assets/` there are only **kind folders**: `scenes/ prefabs/ models/ textures/ sounds/ effects/ ui/ fonts/ tables/ strings/ lut/ probes/ terrain/` (`probes/` only for reflection probes baked by the editor, `terrain/` for 16-bit PNG heightmaps and `.scatter` layers), plus fixed single files (`game.tuning`, `view.tuning`, `input.bindings`, `feedback.table`, `sounds.events`). Subfolders inside kind folders are free. Module folders repeat the same layout inside. New projects create all these folders, and editor import and external tool plugins write only to the kind folder matching the extension. Misplaced files are warned about by the editor and fail `check.ps1`/Export (rules in one place, `tools\check_layout.ps1`) | No deliberating over folder layout. The engine and tools know file locations without configuration. Sources and shipping files don't mix |
| Placing external libraries | package manager (vcpkg) / git submodules / copying source | **Copy the source in and pin the version.** The engine uses `third_party/<lib>/`, games use the project's `third_party/<lib>/`. Each folder has the original `LICENSE` and a `mealkit.txt` (name, version, license, licenseFile, source, usedIn, inGame, kept, why, and cmakeTarget/include if there's something to build). `VERSIONS.txt` and `THIRD_PARTY_NOTICES.txt` aren't written by hand; `tools\gen_notices.ps1` generates them from these two files. Originals aren't modified; if a change is truly needed it's kept as `patches/*.patch`. Game libraries can't be used in `sim/` (SimCheck SIM011), and libraries already in the engine aren't added again. Export merges the engine's and game's notices and checks the license allow list and exe budget | Guarantees offline builds and a static single exe. Adding or removing a library is one folder. External code touching the simulation uses only what the engine has verified for determinism |
| Asset references and loading | Resources / AssetBundle / Addressables / GUID references | **One project-relative path string** (`findAsset`). No GUIDs or `.meta`. Renaming makes the editor asset browser fix references. Shipping builds follow references from the start scene and put **only what's reached** into the `.pak` (things opened only from code go in an "always include" list). Loading is **per match**: the loading screen loads everything that scene uses, and it's unloaded when the match ends. No reference counting or streaming | Three questions (what goes in the build, how to find it, when to load it) get one answer each. The content hash is computed from the same path list |
| Saving progress data (saves) | PlayerPrefs / custom serialization / server DB | **(stage 1)** **Inside a match it's `WorldSnapshot`; progress outside a match is one `MEALKIT_STRUCT(SaveData)` in `AppState`, in the user data folder.** It writes a format version and is read and written via the field declaration mechanism. Cloud is the online service layer (Steam Auto-Cloud / EOS / console saves). There are no account servers or DBs in the engine (accounts are online service accounts) | No deliberating over save formats. In lockstep without an authoritative server, a server DB is a service operations problem |
| Online features (accounts, friends/invites, lobbies, relays, achievements, cloud saves) | calling platform SDKs directly / separately per platform / own server | **(stages 1·3)** **One `mealkit/online/` layer.** The game and the rest of the engine call only this interface. Backends are Steam (stage 1), EOS (stage 3), console platform services (stage 5), and none (LAN UDP), chosen at build time. **Lobbies/P2P for crossplay matches are always EOS** (Steam and console accounts log in via EOS Connect without an Epic account). SDKs aren't put in the repo; without them it's a Stub | Game code stays the same as platforms grow. Steam only reaches Steam, so a common path is needed for crossplay |
| Per-player values taken into a match (characters, gear, unlocks) | sent separately during the match / each reads locally | **(stage 1)** **Match start data**: the game's `MEALKIT_STRUCT(Loadout)` is sent to the host in the lobby, and the host confirms and distributes it at `startMatch`. `World::reset` copies it into `PlayerSlot`, and the simulation reads only those values. The simulation doesn't read save or settings files directly | All peers have the same values, and they go into hashes and snapshots |
| Input | checking keys directly / several input systems | **One input action mapping.** Actions and bindings are the engine table `assets/input.bindings` (row = action: kind `Button`/`Axis`/`Axis2`/`Delta`/`Delta2`, keys/mouse/gamepad); the view side reads only `ctx.actions.axis2("move")`, `pressed("jump")` (`window.input()` is only for engine/debug keys). Keys changed by the player go to the user folder (`game::userFolder`), only the changed rows. The game quantizes action values into the 8-byte `GameInput` and sends them | Key rebinding, gamepads, and bots use the same path |
| How to build game UI | written in code / visual editor inside the engine / HTML/XAML middleware | **(changed 2026-11-04, `docs/DECISIONS.md`) Screens are placed WYSIWYG in the editor's [UI] panel, which draws with the real runtime and saves `.ui`; a screen may instead come from Penpot, and then that file opens read-only in the panel (one source per file).** What follows is the Penpot path: **design in Penpot → the plugin exports to `.ui` → the engine's retained-mode runtime.** The Penpot source is the reference and `.ui` is generated, so it isn't edited by hand. Bindings and actions are also set inside Penpot (the plugin panel, shapes' plugin data). The plugin is the engine's `tools/penpot-plugin` (TypeScript, the build output `dist/` is kept in the repo), and the editor's import server (`editor/ImportServer`, 127.0.0.1 + a token per run) serves the plugin files and writes received files into the project (a zip without the editor). Without a designer, editing `.ui` text directly is fine. Screens exported by the plugin aren't edited by hand (told apart by a mark on the file's first line; a hand-written file with the same name isn't overwritten) | Non-programmers design visually. There's nothing to fix on the engine side, so there's no round-trip problem. The sample's HUD and menus can be built even without the plugin |
| UI written in code | sharing the game UI system / a separate tool | **Debug only, with Dear ImGui.** The game uses ImGui directly inside `GameInstance::debugUi(ctx)`, wrapped in `#if MEALKIT_DEBUG_UI` (F1 overlay in the dev exe, during play in the editor). Shipping builds (`build.bat Export` → `build\Export`) don't have ImGui. Buttons that change the simulation go through confirmed commands. Not used for game UI | Dev screens are built fast and don't mix with game UI |
| Editor UI strings and languages | Korean only / key names (`L("editor.menu.file")`) / source text as key | **Code uses English source text, and that is the key**: text is `tr("File")`, names whose IDs must persist like windows/tabs/popups are `trl("Scene Tree")` (`translation###source`, so docking/popup IDs stay the same when the language changes), and with values `trf("Saved %s", path)`. ## Determinism rules (simulation code)

Lockstep only works if every PC does bit-identical computation. The game's simulation code lives in the `sim/` folder, and `World::step()` calls system functions directly in a fixed order.
The engine's `engine/src/mealkit/physics` follows the same rules. `sim/` files are checked by SimCheck before the build (see 2 in "How it's enforced" below). This section is the canonical version, and the docs repo's explanations point here.

- Use only the four arithmetic operations and `sqrt`. CRT functions like `sin/cos/atan2/pow/exp` can take different paths (FMA) depending on the CPU. For angle computation use `detSin`/`detCos`/`detAtan2`/`detQuatFromAxisAngle` from `mealkit/core/DetMath.h`, or compute at the input stage and send quantized.
- Compiler options are pinned to `/fp:precise`. `/fp:fast`, `/fp:contract`, `/arch:AVX2` aren't used. Clang/GCC (other platforms) use `-ffp-contract=off` and don't use `-ffast-math`. Jolt uses `CROSS_PLATFORM_DETERMINISTIC`, with AVX/FMA off (up to SSE4.2).
- Random numbers use only `Pcg32` (seed-based).
- Physics bodies are created and destroyed in the same order on every peer, and forces are applied in the same order.
- Iteration order is fixed. Don't iterate hash maps, and don't depend on pointer addresses.
- The simulation doesn't read real time, the camera, frame rate, or rendering LOD.
- State that persists across ticks is declared with `MEALKIT_FIELD` inside `WorldState`. `World::hash()` and snapshots use the declarations as is, so nothing can be missed.
- No platform branches (`#ifdef`, platform-specific libraries) in simulation code (crossplay).

## How it's enforced

1. **The tools the engine provides are the answer.** Only `Pool<T>`, tick events, tick timers, `GameContext`, confirmed commands (`mealkit/sim/Commands.h`), and the Job System (`mealkit/jobs/Jobs.h`) are provided, and no other helpers doing the same job are made. Source modules are built only on these tools too.
2. **`sim/` ban check.** Static mutable variables, `new`/`delete`/`make_unique`, `virtual`, `co_await`, `std::thread`/`async`/`future`, `<chrono>`, CRT trig functions, `unordered_map`, renderer/platform/settings headers.
   Comments and strings are excluded from the check. A hit fails the build and says what to use instead ("use `Pool<T>`").
   Float literals (except 0, 1, 2, 0.5, and inside field declaration macros) give only warning SIM012 (silenced with `// const-ok: <reason>`).
   Implementation: `engine/tools/SimCheck.cpp` (run before the build by `mealkit_add_game()`, error codes `SIM001`~`SIM011`, `SIM013`~`SIM015`; SIM011 is project `third_party/` headers, SIM013/SIM014 are when a source module's `sim/` includes the game's `source/` or a module not in `requires`, SIM015 is `#if`/`#ifdef` on platform/compiler/CPU macros (crossplay runs the same simulation code everywhere)). When changing rules, update this document and the tool together.
3. **Simulation state type restrictions.** State fields use only `f32/i32/u32/bool/Vec3/Quat/Id<T>/physics::BodyId/fixed arrays`. Pool items get `static_assert(std::is_trivially_copyable_v<T>)`,
   and `std::string` fields in `WorldState` are blocked by `game::Simulation`'s `static_assert(!reflect::hasStringField<State>())` (string fields are for settings/data).
   Pointers, `std::string`, and `vector` don't enter state, so hashes and snapshots always line up.
4. **Runtime checks.** Using global state is caught right away by the shadow simulation, and finally `mp_test` confirms. `MEALKIT_ASSERT` is on in Debug and Editor builds (`MEALKIT_ASSERTS`). On failure it logs, and if a debugger is attached it stops right there.
5. **Templates, cookbook, and CLAUDE.md use the same answers.** New projects start with this structure, and even when AI writes code it picks the same answers.
6. **Folder check.** `tools\check_layout.ps1` (check.ps1, Export, when the editor opens a project) finds unknown files directly under `assets/`, extensions that don't match their kind folder, source formats (`.blend` etc.) inside `assets/`, and `third_party/` folders without `mealkit.txt`/`LICENSE`. The editor warns with the same rules.
7. **Engine module check.** `tools\check_modules.ps1` (check.ps1, CI) reads `engine-module.txt` in every `engine/src/mealkit/<folder>/` (`docs/ENGINE_MODULES.md` "Manifest") and fails when a manifest is malformed, `requires` has a cycle, a file includes a module outside its own, the kernel (`core`, `platform`, `jobs`) and its `requires`, or a kind rule breaks (kernel includes only kernel, sim only kernel and sim; `transitional` lists the known exceptions until step 4 of the split and fails once stale). A new folder needs a manifest. It replaced the folder order check (`check_layers.ps1`) on 2026-11-08.
   The same script also checks that core files (`MEALKIT_CORE_SOURCES` in `engine/CMakeLists.txt`, which headless/Linux/macOS link) include only headers in the core list. That's because folder order can't catch core → view-side includes (`Frontend.h`, `GameMain.h`, `FrameStats.h`) within the same folder (`game/`). For core to use header-only types (`platform/Input.h` etc.), add them to the core list.
8. **Public header check.** `tools\check_public_headers.ps1` (check.ps1 static group) fails when game code in `samples/`, `templates/` or a source module includes an engine header that isn't in `engine/public_headers.txt`, the headers v1.x keeps source compatible (`docs/DECISIONS.md` 2026-11-03). A game that needs another header gets it added to the list (adding is free, removing waits for v2.0). `-Path <folder>` checks a game project or module checkout too.

## Considered but not changed

| Alternative | Why not changed |
|---|---|
| SoA (an array per field) | For thousands of objects, arrays of structs (AoS) stay within the tick budget and the code is much easier to read. If measurement shows a bottleneck, change only that array |
| General ECS (archetypes) | Runtime composition works, but execution order hides in system registration order and the engine gets heavier. Same as the conditions in the `DECISIONS.md` deferred table |
| C++20 coroutines inside the simulation (advancing by tick) | Order can be made deterministic, but coroutine frames can't be hashed or snapshotted, breaking mid-match joining and rewind |
| Banning only iteration of `unordered_map` | The check gets harder (it'd have to judge whether it's iterated), and Pool ids solve most cases. A total ban is simpler |
| Immediate-mode game UI written in code | Non-programmers couldn't build UI. Immediate mode is used only for debug UI (ImGui) |
| UI designer inside the engine editor (UMG style) | The largest development cost. Penpot already has canvases, components, and tokens |
| Figma | Designers use it most, but it's cloud-only and REST API rate limits are tight. `.ui` is an intermediate format, so if needed only a Figma plugin would be built separately |
| Shader graph / material editor inside the engine | Large development cost, and as combinations grow the integrated graphics budget and shader compile time can't be managed. Most looks work within the glTF PBR range |
| Per-project surface function HLSL | Not until v1.0: style presets are what games have now. Planned first among the opt-in rendering features after v1.0 (`docs/DECISIONS.md` 2026-11-04, `docs/ROADMAP.md` "Opt-in rendering features") |
| Particle editor inside the engine | Curves, gradients, and previews would all have to be built, a large development cost. External effect tools already have them |
| Layout libraries like Yoga or Clay | Since it must compute exactly like Penpot's layout, building it directly against Penpot is more reliable than matching another library's rules |
| RmlUi, Noesis, Gameface, Rive | Either text markup rather than visual editing (RmlUi), or commercial/heavy runtimes. Rive's runtime is MIT but the editor that exports game files is paid (`DECISIONS.md` 2026-10-20) |
| Pre-baked font of the 2,350 precomposed Hangul syllables | Can't show rare Hangul or nicknames in other languages |
| Rust | Same performance and determinism, and most of the memory safety benefit is already covered by the `sim/` ban rules and Pool ids. The borrow checker clashes with game code that passes `World&` to modify several Pools, the unstable ABI makes DLL hot reload hard, and the libraries used (Jolt, Effekseer, Steamworks, ImGui, PIX, Tracy) are all C/C++ |
| View values in the same tuning | View values would go into the content hash and couldn't change during multiplayer, and friends using different graphics settings would be refused connection |
| Asset GUIDs and `.meta` files | References don't break on rename, but `.meta` pairs drifting in version control is the bigger problem. For renames, the editor fixes references |
| Reusing features with prefabs only | Prefabs hold only placement and field values. Behavior is `sim/` code, so source modules are needed (modules carry prefabs too) |
| FMOD / Wwise (audio middleware) | Strong authoring tools, events, and spatial audio, but paid commercial SDKs that don't fit the permissive-license/source-included rules, and runtime DLLs/banks shake the single exe / 5 MB budget. Only the event/container/voice management approach and authoring tool structure are borrowed, built as MealKit Audio (runtime + authoring tool) in a separate repo |
| Binary plugin DLLs | The shipping exe is a static single file and `sim/` code must pass SimCheck |
| Account servers/DBs in the engine | Lockstep without an authoritative server makes it a service operations problem. Online services' (Steam, EOS) accounts, cloud, and leaderboards cover most of it |
| 2D game features (sprites, tilemaps, 2D physics) | 3D is an absolute rule. 2D physics would need one more determinism verification |
| Per-feature folders (models, sounds, code together in `Player/`) | The engine and tools need to know per-kind locations to work without configuration. Per-feature bundles are handled by source modules |
| Banning subfolders inside kind folders (flat) | Hard to find things once there are hundreds of assets. References are paths, so the asset browser fixes references when moving subfolders |
| Referencing assets by name (regardless of path) | Adds one more rule that names don't collide within a kind, and doesn't match the pack file / content hash path lists |
| vcpkg / git submodules | Builds need the network, and separate configs are needed for both static and dynamic CRT builds. Submodules go missing when a project is copied as a zip or via `new_project` |

## What we accept

- Components can't be attached/detached at runtime. Each kind processed by different systems needs one array and one system. If kinds reach the hundreds, revisit the ECS deferral.
- `Pool` needs its maximum count decided up front.
- No "access from anywhere" convenience. The price is longer function argument lists.
- Time values are rounded to the tick rate (at 30 Hz, one tick = 33 ms units).
- Direct calls inside the simulation require the caller to know the callee. In exchange, the flow isn't hidden.
- Graphics content depends on external tools. Materials outside the glTF range the engine reads (SSS, clearcoat, etc.) can't be used, and special looks must be added as engine shader features.
- Progress data and loadouts live on each PC, so they can be tampered with. Every peer holds the full state, so map hacks can't be prevented (the price of lockstep).
- One feature's (e.g. a weapon's) files are scattered across `models/`, `sounds/`, `tables/`. To bundle them together for reuse, make a source module.
- Moving assets in File Explorer breaks references (warned on load). Move them in the editor asset browser.
- Game UI depends on Penpot (it's open source and can be self-hosted, so the risk is small). We have to follow Penpot's layout/text computations and maintain the plugin (TypeScript) and Node.js dev tools.
