# MealKit 코딩 방식: 한 문제에 한 답

유니티처럼 같은 문제에 방법이 여러 개(싱글톤 / 서비스 로케이터 / DI, 풀링 / ECS, 코루틴 / Task / UniTask …)이면
매번 고르느라 시간을 쓰고, 프로젝트 안에서도 모양이 갈린다. MealKit은 자주 만나는 설계 질문마다 **답을 하나만** 정해 둔다.
엔진은 그 답에 필요한 도구만 제공하고, 다른 방법은 빌드 검사로 막는다. 고민 없이 짜도 처음부터 확장성과 성능을 고려한 모양이 되게 하는 것이 목표다.

- 표에 없는 질문을 만나면 코드에서 각자 답하지 않는다. **이 문서에 행을 먼저 추가**하고 쓴다.
- 답을 바꿀 때는 `docs/DECISIONS.md` 결정 기록에 남긴다. 프로젝트마다 다른 답을 쓰지 않는다.
- `sim/`은 결정론 시뮬레이션 코드, `view/`는 카메라·그리기·UI·소리, `app/`은 진입점과 화면 흐름이다 (ROADMAP 0단계).
- 답 앞의 **(n단계)** 는 답은 정했지만 도구가 아직 없다는 뜻이다(ROADMAP 그 단계의 항목). 그 도구가 필요해지면 다른 방법으로 우회하지 말고 그 항목을 당겨서 만든다. 표시가 없는 답은 지금 쓸 수 있다.

## 답 표

### 구조

| 질문 | 흔한 선택지 | MealKit의 답 | 이유 |
|---|---|---|---|
| 엔진 기능에 어떻게 접근하나 | 싱글톤 / 서비스 로케이터 / DI 컨테이너 | **인자로 받는다.** 화면 쪽은 `GameContext&`(`mealkit/game/GameContext.h`: 창, 입력 액션, 렌더러, 에셋, 세션, 매치 열기·참가(`match`), 소리, 연출, 문자열, UI, 플레이어 설정, 화면용 튜닝) 하나, `sim/` 시스템은 `World&`만 받는다. 전역 가변 상태 금지. **예외**: 아무것도 읽어 가지 않는 출력 전용 기능(로그, 프로파일 마커, `MEALKIT_ASSERT`)은 전역 함수로 쓴다. 프로젝트를 열 때 한 번 정하고 매치 중에 바뀌지 않는 프로세스 설정(`setProjectRoot`, `reflect::setTickRate`)도 전역이다 | 그림자 시뮬레이션은 한 프로세스에서 World 두 개를 돌린다. 싱글톤이 있으면 불가능하다. 핫 리로드 때 static 상태가 꼬이지 않는다 |
| 창 없이(헤드리스·CI) 게임을 돌리는 방법 | 게임마다 main을 따로 짠다 / 엔진이 게임 코드를 모르고 상태만 돌린다 / 출시 exe에 옵션만 | **`app/Headless.cpp`의 클래스 하나 + `MEALKIT_HEADLESS_GAME(클래스)`**(`mealkit/game/Headless.h`, 에디터의 `MEALKIT_GAME_MODULE`과 같은 모양). 게임은 타입(`World`, `TuningType`, `ProjectSettingsType`)과 `startWorld`(매치 시작)·`botInput`·`defaults`(선택)만 내놓고, 데이터 읽기·콘텐츠 해시(`game::loadMatchData`, 출시 exe·에디터 플레이·참가 창과 같은 함수)·명령줄(`game::parseGameArgs`, 출시 exe와 같은 파서)·세션·해시 로그·입력 기록과 재생, 출력 형식은 엔진이 한다. `<게임>_headless`는 `sim/` + 이 파일만 엔진 코어와 링크하고, 출시 exe는 `--headless`로 같은 함수를 부른다. `GameSession`도 매치 시작과 봇 입력에 같은 함수를 쓴다 | 창 있는 게임·에디터·헤드리스가 같은 매치 시작 코드를 쓰므로 해시가 갈리지 않는다. CI가 보는 출력(`FINAL`, `REPLAY`, 해시 로그)이 프로젝트마다 같다. 이 파일은 `view/`·렌더러 헤더를 쓰지 않아 Linux·macOS에서도 빌드된다 |
| 창 있는 게임을 돌리는 프레임 루프 (출시 exe, 에디터 플레이, 참가 창) | 게임마다 main을 짠다 / 실행 방식마다 루프를 복사한다 | **화면 쪽 서비스는 `game::Frontend`(`mealkit/game/Frontend.h`) 하나가 갖고 같은 순서로 돌린다.** 입력 액션·게임패드·문자열 표·게임 UI·플레이어 설정·화면용 튜닝을 갖고, `context()`로 `GameContext`를 만들고, 매 프레임 게임 `update` 전에 `update(now, dt, input, ctx)`(문자열 → 화면용 튜닝 → 패드 → UI가 마우스·키보드를 먼저 → 설정 화면 → 액션), `buildFrame` 뒤에 `afterBuildFrame(frame)`(월드 위 UI 카메라, 듣는 위치, 화면 색), 3D 다음에 `renderUi`. 소리·연출은 주인이 만들어 빌려 준다(에디터는 [소리]·[연출] 미리보기와 같이 쓴다). **출시 exe의 main은 엔진의 `game::runGame`**(`mealkit/game/GameMain.h`): 게임은 `app/main.cpp`에 `MEALKIT_GAME_MAIN(GameSession)` 한 줄만 쓴다(`MEALKIT_GAME_MODULE`·`MEALKIT_HEADLESS_GAME`과 같은 모양, `--headless`도 여기서 나뉜다). 명령줄·창·렌더러·세션·Steam 로비·자동 시험 출력(`FINAL`, `SHADOW`, `REWIND`)·창 제목(`game.title`, `title.*` 문자열 키)은 엔진이 한다. 에디터 참가 창도 같은 `runGame`을 부르고 다른 점만 `GameRunOptions`로 넘긴다 | 서비스를 하나 더할 때 세 곳(출시 exe, 에디터 플레이, 참가 창)과 프로젝트마다의 `main.cpp`를 고치던 것이 한 곳이 된다. 갱신 순서가 실행 방식마다 갈리지 않는다. 엔진 기능(성능 숫자, 화면 흐름)이 기존 프로젝트에 엔진 업그레이드만으로 들어간다. 출시 exe도 `GameInstance` 가상 호출을 쓰지만 프레임당 몇 번이라 비용이 없다 |
| 엔진이 무엇까지 만드나 | 엔진이 다 만든다 / 플러그인 생태계 | **엔진은 결정론 시뮬레이션, 락스텝 네트워크, 렌더러, 에디터(배치·가져오기·검사·디버깅)만 만든다. 나머지는 완성된 외부 것을 가져다 쓴다.** 제작 도구(Blender, Penpot, Effekseer, VS Code)는 자유롭게. 런타임 라이브러리는 시뮬레이션에 닿으면 결정론 검증, 소스 포함·버전 고정(`third_party/`), 허용 라이선스, 출시 exe 예산 안 | 엔진이 가볍고, 아티스트·개발자가 이미 아는 도구를 쓴다. 시뮬레이션에 닿는 라이브러리 하나가 결정론을 깨면 멀티플레이 전체가 깨진다 |
| 엔진 폴더 사이 의존 (어느 하위 시스템이 어느 것을 include하나) | 자유롭게 / 하위 시스템마다 켜고 끄는 빌드 모듈 / 플러그인 | **`engine/src/mealkit/`의 폴더 순서를 하나 정하고, 폴더는 자기보다 앞의 폴더만 include한다.** 기반 `core`·`platform`(서로 include 가능) → 시뮬레이션 쪽 `net` → `physics` → `sim` → `data`(표 파일 읽기) → 개발 도구 연결 `live`(라이브 연결 서버) → 화면 쪽 `loc` → `scene` → `rhi`(2단계) → `render` → `asset` → `online` → `debug` → `input` → `audio` → `ui` → `feedback` → `settings` → 게임 경계 `game` → `editor`. 새 폴더는 이 순서에 자리를 정하고 넣는다. `platform/<os>/` 구현 파일은 여러 폴더의 헤더(`net/Socket.h` 등)를 구현하므로 이 검사에서 빼고 플랫폼 검사가 본다. 하위 시스템을 빌드 옵션으로 빼는 것은 실제로 필요한 게임이 생길 때 행을 더한다 | 순환이 없어 하위 시스템을 따로 이해·시험·이식할 수 있고(헤드리스는 앞쪽만 링크), 소스 모듈·다른 플랫폼을 붙일 때 경계가 무너지지 않는다. 출시 exe는 예산의 절반이고 범용 에디터는 DLL 하나라, 켜고 끄는 모듈은 지금 얻는 것보다 검사 조합이 더 늘어난다 |
| 성능 숫자 모으기와 보여 주기 (프레임 시간, 틱당 시뮬레이션 시간, 드로우 콜, 네트워크, 소리 목소리) | 화면마다 직접 계산 / 전역 프로파일러 등록소 / Tracy만 | **측정은 각 하위 시스템이 자기 `stats()`로**(`render::RenderStats`, `net::SessionStats`, `audio::Stats`, `GameInstance::takeSimMsPerTick`), **모으기·평균·글자는 `game::FrameStats`(`mealkit/game/FrameStats.h`) 하나.** 엔진 루프(출시 exe의 main, 에디터)가 매 프레임 `update(dt, {renderer, session, audio, game})`를 부르고, 보고 주기(0.25초)가 끝난 프레임에 `true` → `sample()`(평균·최악 프레임 포함)과 `line()`(" | " 구분 한 줄)·`lines()`(항목마다 한 줄). 없는 출처(편집 모드의 세션 등)는 건너뛴다. GPU 시간(RHI 타임스탬프, 렌더러 패스별 `render::GpuPass`)은 매 프레임 더해 평균을 내고, 1% 최악 프레임(`frameMsPercentile`)·프로세스 메모리·GPU 메모리도 같은 묶음에 넣는다. 창 제목·F1 오버레이·자동 실행 `perf:` 로그·에디터 상태 표시줄이 이것만 읽고, 벤치마크 보고서(`game::Benchmark`, `--benchmark`: 묶음과 프레임 시간을 쌓는다)·성능 패널(4단계)도 이것 위에 만든다. 함수 안 시간 재기는 Tracy `MEALKIT_ZONE`(출력 전용 전역, Profile 빌드만) | 같은 숫자가 화면마다 다르게 계산되지 않는다. `takeSimMsPerTick`처럼 읽으면 비워지는 값을 두 곳이 나눠 갖지 않는다. 등록소는 읽어 가는 전역 상태라 쓰지 않고(이 표 첫 행), 아래 계층이 위의 프로파일러를 부르지 않아 폴더 순서도 지킨다 |
| 시뮬레이션이 읽는 설정값 | 전역 설정 객체 / 매번 파일에서 읽기 | **`World`가 매치를 시작할 때 튜닝·씬 데이터를 복사해 갖는다.** 시스템은 `world.tuning`으로 읽는다. 상태 해시가 아니라 콘텐츠 해시에 들어간다 | 시스템 인자는 계속 `World&` 하나 |
| 게임 오브젝트 구성 | 상속 / 컴포넌트 / 범용 ECS | **종류별 평평한 배열 + 정수 id + 시스템 함수.** 상속과 가상 `Update`는 쓰지 않는다. 배열을 나누는 기준: **같은 시스템이 처리하면 같은 배열에 `kind` enum, 다른 시스템이 처리하면 다른 배열.** 있을 수도 없을 수도 있는 동작은 필드와 플래그로 둔다 | 캐시 친화적이고 순서가 고정된다 (`DECISIONS.md`: Actor 상속 넣지 않음, 범용 ECS 보류) |
| 다른 객체 찾기 | 이름·태그 검색 / 타입 검색 / 참조 보관 | **id를 필드에 저장하고 Pool에서 조회한다.** 범위 안의 물체는 물리 질의로 찾는다. 이름·태그 검색은 없다 | 조회는 O(1), 대상이 사라지면 세대 번호로 알 수 있다 |
| 생성과 파괴 | 즉시 생성·삭제 / 오브젝트 풀링 | **시뮬레이션 객체는 전부 `Pool<T>`(`mealkit/sim/Pool.h`)에서.** 생성은 즉시(이번 틱에 id로 바로 쓸 수 있다). 다만 **만든 틱에는 순회에 나오지 않는다.** 삭제는 표시만 하고(그 뒤로 `get`·순회에서 빠진다) `World::step()` 끝의 `endTick(onDestroy)`가 슬롯 순서로 일괄 처리한다(물리 바디 삭제는 `onDestroy`에서). id에 세대 번호를 붙인다 | 풀링 여부를 고민하지 않는다. 순회 중 생성·삭제 버그, 할당 스파이크, 결정론 문제를 한 번에 없앤다. 생성이 즉시라 발사체가 한 틱 늦게 나오지 않는다 |
| Pool이 가득 찼을 때 | - | 용량은 매치 시작 때 데이터에서 정한다(`World::reset`: sandbox는 상자 = 씬 상자 생성 영역의 합, 컨트롤러 = 플레이어 + 튜닝의 AI 수, Pawn = 컨트롤러 × 2). 넘치면 생성이 실패하고(무효 id, 모든 피어가 같다) `MEALKIT_ASSERT`가 걸린다 | 결정론을 지키면서 Dev에서 바로 알 수 있다 |
| 매치·씬이 바뀌어도 남는 데이터 | 안 지워지는 싱글톤 / 정적 클래스 | **매치 안은 `World`(점수는 `PlayerSlot`), 매치 밖은 `app/`(화면 흐름 `Flow`의 화면 상태, 세이브 `SaveData`를 가진 `GameSession`), 디스크는 사용자 데이터 폴더.** `GameInstance`는 매치 사이에도 살아 있고 매치마다 `start`·`stop`만 다시 불린다 | 어디에 둘지 고민할 곳이 세 군데뿐이다 |
| 여러 게임에서 다시 쓰는 기능 (체력, 쿨타임, 인벤토리, 미니맵, 절차적 생성) | 엔진 기본 기능 / 프리팹 / 바이너리 플러그인 / 에셋 스토어 패키지 | **(4단계)** **소스 모듈**(`modules/<이름>/`: `sim/`·`view/`·`.ui`·튜닝·프리팹). 프로젝트에 소스째 복사해 고쳐 쓰고, 업그레이드 도구 방식(고치지 않은 파일만 갱신)으로 업데이트한다. 모듈 함수는 게임의 `World`를 모르고 자기 상태만 받는다(`cooldown::step(Cooldowns&, u32 tick)`). 게임이 상태를 `WorldState` 필드로 넣고 `World::step()`에서 부른다 | 엔진이 무거워지지 않고, 프리팹은 데이터만 담아 로직을 옮길 수 없고, DLL은 정적 출시 exe·SimCheck와 맞지 않는다. 소스라 SimCheck·해시·스냅샷이 그대로 적용된다 |

### 흐름

| 질문 | 흔한 선택지 | MealKit의 답 | 이유 |
|---|---|---|---|
| 실행 순서와 시간 | 여러 Update 단계 + 실행 순서 설정, deltaTime | **`World::step()`이 시스템을 순서대로 호출.** `sim/`은 틱 정수만, 화면은 보간 `alpha`와 프레임 `dt`만 | 순서가 코드 한 곳에 보인다 |
| 시뮬레이션 안에서 알리기 | 이벤트 / 델리게이트 / 메시지 버스 | **함수를 직접 호출한다.** 예: `damage(world, target, amount, source)`. 구독·옵저버 없음 | `step()`과 호출 경로만 보면 누가 언제 반응하는지 보인다. 이벤트를 쓰면 생산자·소비자 순서 규칙이 하나 더 생긴다 |
| 시뮬레이션 → 화면 알리기 (소리, 효과, 화면 흔들림) | 콜백 / 화면이 상태 변화를 추측 | **틱 이벤트 배열**(`mealkit::sim::TickEvents<T, N>`). `sim/`은 `world.events.push(Hit{...})`로 쓰기만 하고 읽지 않는다. 틱 시작 때 비운다. `GameSession`이 `step()`을 부를 때마다 이벤트를 화면 쪽 큐로 옮기므로, 한 프레임에 틱이 여러 번 돌아도 빠지지 않는다. 이벤트는 상태 해시에 넣지 않는다 | 시뮬레이션은 화면을 모르고, 화면은 놓치는 이벤트가 없다 |

## 결정론 규칙 (시뮬레이션 코드)

락스텝은 모든 PC가 비트 단위로 같은 계산을 해야 동작한다. 게임의 시뮬레이션 코드는 `sim/` 폴더에 두고, `World::step()`이 시스템 함수를 정해진 순서로 직접 부른다.
엔진의 `engine/src/mealkit/physics`도 같은 규칙을 따른다. `sim/` 파일은 빌드 전에 SimCheck가 검사한다(아래 "강제하는 방법" 2). 이 절이 정본이고, 문서 저장소의 설명은 여기를 가리킨다.

- 사칙연산과 `sqrt`만 쓴다. `sin/cos/atan2/pow/exp` 같은 CRT 함수는 CPU에 따라 다른 경로(FMA)를 탈 수 있다. 각도 계산은 `mealkit/core/DetMath.h`의 `detSin`/`detCos`/`detAtan2`/`detQuatFromAxisAngle`을 쓰거나, 입력 단계에서 계산해 양자화해서 보낸다.
- 컴파일 옵션은 `/fp:precise`로 고정한다. `/fp:fast`, `/fp:contract`, `/arch:AVX2`는 쓰지 않는다. Clang·GCC(다른 플랫폼)는 `-ffp-contract=off`이고 `-ffast-math`를 쓰지 않는다. Jolt는 `CROSS_PLATFORM_DETERMINISTIC`, AVX/FMA 끔(SSE4.2까지).
- 난수는 `Pcg32`(시드 기반)만 쓴다.
- 물리 바디는 모든 피어에서 같은 순서로 만들고 지우고, 힘도 같은 순서로 준다.
- 순회 순서를 고정한다. 해시맵을 순회하지 않고, 포인터 주소에 의존하지 않는다.
- 실제 시간, 카메라, 프레임레이트, 렌더링 LOD를 시뮬레이션이 읽지 않는다.
- 틱을 넘어 남는 상태는 `WorldState` 안에 `MEALKIT_FIELD`로 선언한다. `World::hash()`와 스냅샷이 선언을 그대로 쓰므로 빠뜨릴 수 없다.
- 시뮬레이션 코드에 플랫폼 분기(`#ifdef`, 플랫폼별 라이브러리)를 두지 않는다(크로스플레이).

## 강제하는 방법

1. **엔진이 주는 도구가 곧 답이다.** `Pool<T>`, 틱 이벤트, 틱 타이머, `GameContext`, 확정 명령(`mealkit/sim/Commands.h`), Job System(4단계)만 제공하고, 같은 일을 하는 다른 헬퍼는 만들지 않는다. 소스 모듈도 이 도구 위에서만 만든다.
2. **`sim/` 금지 검사.** static 가변 변수, `new`/`delete`/`make_unique`, `virtual`, `co_await`, `std::thread`/`async`/`future`, `<chrono>`, CRT 삼각함수, `unordered_map`, 렌더러·플랫폼·설정 헤더.
   주석과 문자열은 빼고 검사한다. 걸리면 빌드가 실패하고 대신 쓸 것을 알려 준다("`Pool<T>`를 쓰세요").
   실수 리터럴(0·1·2·0.5 제외, 필드 선언 매크로 안 제외)은 경고 SIM012만 낸다(`// const-ok: <이유>`로 끈다).
   구현: `engine/tools/SimCheck.cpp` (`mealkit_add_game()`이 빌드 전에 실행, 오류 코드 `SIM001`~`SIM011`, SIM011은 프로젝트 `third_party/` 헤더). 규칙을 바꾸면 이 문서와 도구를 같이 고친다.
3. **시뮬레이션 상태 타입 제한.** 상태 필드는 `f32/i32/u32/bool/Vec3/Quat/Id<T>/physics::BodyId/고정 배열`만 쓴다. Pool 항목은 `static_assert(std::is_trivially_copyable_v<T>)`,
   `WorldState`의 `std::string` 필드는 `game::Simulation`의 `static_assert(!reflect::hasStringField<State>())`가 막는다(문자열 필드는 설정·데이터용).
   포인터, `std::string`, `vector`가 상태에 들어가지 않으므로 해시와 스냅샷이 항상 맞는다.
4. **실행 중 검사.** 전역 상태를 쓰면 그림자 시뮬레이션이 바로 잡고, 마지막으로 `mp_test`가 확인한다. `MEALKIT_ASSERT`는 Debug와 Editor 빌드(`MEALKIT_ASSERTS`)에서 켜진다. 실패하면 로그를 남기고, 디버거가 붙어 있으면 그 자리에서 멈춘다.
5. **템플릿·쿡북·CLAUDE.md가 같은 답을 쓴다.** 새 프로젝트는 이 구조로 시작하고, AI가 코드를 짜도 같은 답을 고른다.
6. **폴더 검사.** `tools\check_layout.ps1`(check.ps1, Export, 에디터가 프로젝트를 열 때)이 `assets/` 바로 밑의 알 수 없는 파일, 종류 폴더와 맞지 않는 확장자, `assets/` 안의 원본 형식(`.blend` 등), `mealkit.txt`·`LICENSE`가 없는 `third_party/` 폴더를 찾는다. 에디터는 같은 규칙으로 경고한다.
7. **엔진 폴더 계층 검사.** `tools\check_layers.ps1`(check.ps1)이 `engine/src/mealkit/`의 `#include "mealkit/<폴더>/..."`를 보고, 위 "엔진 폴더 사이 의존" 순서보다 뒤의 폴더를 include하거나 순서에 없는 폴더가 생기면 실패한다. 순서는 이 스크립트 한 곳에 있고, 바꾸면 이 문서와 같이 고친다.
   같은 스크립트가 코어 파일(`engine/CMakeLists.txt`의 `MEALKIT_CORE_SOURCES`, 헤드리스·Linux·macOS가 링크하는 것)이 코어 목록에 있는 헤더만 include하는지도 본다. 폴더 순서로는 같은 폴더(`game/`) 안의 코어 → 화면 쪽(`Frontend.h`, `GameMain.h`, `FrameStats.h`) include를 못 잡기 때문이다. 헤더만 있는 타입(`platform/Input.h` 등)을 코어가 쓰려면 코어 목록에 넣는다.

## 감수하는 것

- 컴포넌트를 실행 중에 붙였다 뗄 수 없다. 처리하는 시스템이 다른 종류마다 배열 하나와 시스템 하나가 필요하다. 종류가 수백 개가 되면 ECS 보류를 다시 본다.
- `Pool`은 최대 개수를 미리 정해야 한다.
- "아무 데서나 접근"하는 편의가 없다. 함수 인자가 길어지는 대가를 치른다.
- 시간 값은 틱레이트에 맞춰 반올림된다(30 Hz에서 한 틱 = 33 ms 단위).
- 시뮬레이션 안 직접 호출은 호출하는 쪽이 받는 쪽을 알아야 한다. 대신 흐름이 숨지 않는다.
- 그래픽 콘텐츠는 외부 도구에 의존한다. 엔진이 읽는 glTF 범위 밖의 머티리얼(SSS, 클리어코트 등)은 쓸 수 없고, 특수한 모양이 필요하면 엔진 셰이더 기능으로 추가해야 한다.
- 진행 데이터와 로드아웃은 각자 PC에 있어 고치려면 고칠 수 있다. 모든 피어가 전체 상태를 가져 맵핵을 막을 수 없다(락스텝의 대가).
- 기능 하나(예: 무기)의 파일이 `models/`·`sounds/`·`tables/`에 흩어진다. 한데 모아 다시 쓰려면 소스 모듈로 만든다.
- 탐색기에서 에셋을 옮기면 참조가 끊긴다(불러올 때 경고). 옮기기는 에디터 에셋 브라우저에서 한다.
- 게임 UI는 Penpot에 의존한다(오픈소스라 직접 띄울 수 있어 위험은 작다). Penpot 레이아웃·글자 계산을 따라가야 하고, 플러그인(TypeScript)과 Node.js 개발 도구를 유지해야 한다.
