# MealKit 코딩 방식: 한 문제에 한 답

유니티처럼 같은 문제에 방법이 여러 개(싱글톤 / 서비스 로케이터 / DI, 풀링 / ECS, 코루틴 / Task / UniTask …)이면
매번 고르느라 시간을 쓰고, 프로젝트 안에서도 모양이 갈린다. MealKit은 자주 만나는 설계 질문마다 **답을 하나만** 정해 둔다.
엔진은 그 답에 필요한 도구만 제공하고, 다른 방법은 빌드 검사로 막는다. 고민 없이 짜도 처음부터 확장성과 성능을 고려한 모양이 되게 하는 것이 목표다.

- 표에 없는 질문을 만나면 코드에서 각자 답하지 않는다. **이 문서에 행을 먼저 추가**하고 쓴다.
- 답을 바꿀 때는 `docs/ROADMAP.md` 결정 기록에 남긴다. 프로젝트마다 다른 답을 쓰지 않는다.
- `sim/`은 결정론 시뮬레이션 코드, `view/`는 카메라·그리기·UI·소리, `app/`은 진입점과 화면 흐름이다 (ROADMAP 0단계).

## 답 표

### 구조

| 질문 | 흔한 선택지 | MealKit의 답 | 이유 |
|---|---|---|---|
| 엔진 기능에 어떻게 접근하나 | 싱글톤 / 서비스 로케이터 / DI 컨테이너 | **인자로 받는다.** 화면 쪽은 `GameContext&`(`mealkit/game/GameContext.h`: 창·입력, 렌더러, 에셋, 세션. 소리·UI는 생기면 추가) 하나, `sim/` 시스템은 `World&`만 받는다. 전역 가변 상태 금지. **예외**: 아무것도 읽어 가지 않는 출력 전용 기능(로그, 프로파일 마커, `MEALKIT_ASSERT`)은 전역 함수로 쓴다 | 그림자 시뮬레이션은 한 프로세스에서 World 두 개를 돌린다. 싱글톤이 있으면 불가능하다. 핫 리로드 때 static 상태가 꼬이지 않는다 |
| 시뮬레이션이 읽는 설정값 | 전역 설정 객체 / 매번 파일에서 읽기 | **`World`가 매치를 시작할 때 튜닝·씬 데이터를 복사해 갖는다.** 시스템은 `world.tuning`으로 읽는다. 상태 해시가 아니라 콘텐츠 해시에 들어간다 | 시스템 인자는 계속 `World&` 하나 |
| 게임 오브젝트 구성 | 상속 / 컴포넌트 / 범용 ECS | **종류별 평평한 배열 + 정수 id + 시스템 함수.** 상속과 가상 `Update`는 쓰지 않는다. 배열을 나누는 기준: **같은 시스템이 처리하면 같은 배열에 `kind` enum, 다른 시스템이 처리하면 다른 배열.** 있을 수도 없을 수도 있는 동작은 필드와 플래그로 둔다 | 캐시 친화적이고 순서가 고정된다 (결정 기록: Actor 상속 넣지 않음, 범용 ECS 보류) |
| 다른 객체 찾기 | 이름·태그 검색 / 타입 검색 / 참조 보관 | **id를 필드에 저장하고 Pool에서 조회한다.** 범위 안의 물체는 물리 질의로 찾는다. 이름·태그 검색은 없다 | 조회는 O(1), 대상이 사라지면 세대 번호로 알 수 있다 |
| 생성과 파괴 | 즉시 생성·삭제 / 오브젝트 풀링 | **시뮬레이션 객체는 전부 `Pool<T>`(`mealkit/sim/Pool.h`)에서.** 생성은 즉시(이번 틱에 id로 바로 쓸 수 있다). 다만 **만든 틱에는 순회에 나오지 않는다.** 삭제는 표시만 하고(그 뒤로 `get`·순회에서 빠진다) `World::step()` 끝의 `endTick(onDestroy)`가 슬롯 순서로 일괄 처리한다(물리 바디 삭제는 `onDestroy`에서). id에 세대 번호를 붙인다 | 풀링 여부를 고민하지 않는다. 순회 중 생성·삭제 버그, 할당 스파이크, 결정론 문제를 한 번에 없앤다. 생성이 즉시라 발사체가 한 틱 늦게 나오지 않는다 |
| Pool이 가득 찼을 때 | - | 용량은 매치 시작 때 정한다(`World::reset` 인자, 튜닝 시스템이 생기면 튜닝 값으로). 넘치면 생성이 실패하고(무효 id, 모든 피어가 같다) `MEALKIT_ASSERT`가 걸린다 | 결정론을 지키면서 Dev에서 바로 알 수 있다 |
| 매치·씬이 바뀌어도 남는 데이터 | 안 지워지는 싱글톤 / 정적 클래스 | **매치 안은 `World`(점수는 `PlayerSlot`), 매치 밖은 `app/`의 `AppState` 하나, 디스크는 사용자 데이터 폴더.** | 어디에 둘지 고민할 곳이 세 군데뿐이다 |

### 흐름

| 질문 | 흔한 선택지 | MealKit의 답 | 이유 |
|---|---|---|---|
| 실행 순서와 시간 | 여러 Update 단계 + 실행 순서 설정, deltaTime | **`World::step()`이 시스템을 순서대로 호출.** `sim/`은 틱 정수만, 화면은 보간 `alpha`와 프레임 `dt`만 | 순서가 코드 한 곳에 보인다 |
| 시뮬레이션 안에서 알리기 | 이벤트 / 델리게이트 / 메시지 버스 | **함수를 직접 호출한다.** 예: `damage(world, target, amount, source)`. 구독·옵저버 없음 | `step()`과 호출 경로만 보면 누가 언제 반응하는지 보인다. 이벤트를 쓰면 생산자·소비자 순서 규칙이 하나 더 생긴다 |
| 시뮬레이션 → 화면 알리기 (소리, 효과, 화면 흔들림) | 콜백 / 화면이 상태 변화를 추측 | **틱 이벤트 배열**(`mealkit::sim::TickEvents<T, N>`). `sim/`은 `world.events.push(Hit{...})`로 쓰기만 하고 읽지 않는다. 틱 시작 때 비운다. `GameSession`이 `step()`을 부를 때마다 이벤트를 화면 쪽 큐로 옮기므로, 한 프레임에 틱이 여러 번 돌아도 빠지지 않는다. 이벤트는 상태 해시에 넣지 않는다 | 시뮬레이션은 화면을 모르고, 화면은 놓치는 이벤트가 없다 |
| 시간이 걸리는 일 | 코루틴 / Task / async-await | **`sim/`에는 비동기가 없다.** "N틱 뒤"는 `TickTimer`(`mealkit/sim/TickTimer.h`, 상태는 `u32 readyTick` 하나), 여러 단계는 `enum` 상태 머신. **화면·앱 쪽은 Job System 하나 + `isReady()` 폴링.** Job System이 생기기 전까지 로딩은 로딩 화면에서 동기로 한다. 코루틴·콜백·`std::async` 금지 | 비동기 완료 시점이 PC마다 다르면 디싱크. 상태가 전부 데이터라 스냅샷·되감기가 된다 |
| 상태 머신 | enum switch / State 패턴 클래스 / 그래프 도구 | **`enum class` + `switch` + 진입 틱** | 상태가 정수 두 개라 해시·스냅샷이 쉽다 |

### 데이터와 입출력

| 질문 | 흔한 선택지 | MealKit의 답 | 이유 |
|---|---|---|---|
| 데이터와 설정 | 에셋 객체 / JSON / 인스펙터 직렬화 | **필드 선언 하나**(`MEALKIT_OBJECT`/`MEALKIT_FIELD`) → `.scene`, `.tuning`. 에셋은 `findAsset` 경로 하나 | 해시·저장·인스펙터가 자동으로 맞는다 |
| 입력 | 키 직접 확인 / 입력 시스템 여러 개 | **입력 액션 매핑 하나**(1단계). 게임은 액션 값만 읽고, 그 값을 `GameInput` 8바이트로 양자화해 보낸다 | 키 바꾸기·게임패드·봇이 같은 길을 쓴다 |
| 게임 UI를 만드는 방법 | 코드로 짜기 / 엔진 안 비주얼 에디터 / HTML·XAML 미들웨어 | **Penpot에서 디자인 → 플러그인이 `.ui`로 내보냄 → 엔진의 유지 모드 런타임.** Penpot 원본이 기준이고 `.ui`는 생성물이라 손으로 고치지 않는다. 바인딩·액션도 Penpot 안(플러그인 패널)에서 정한다 | 프로그래머가 아닌 사람이 시각적으로 디자인한다. 엔진 쪽에서 고칠 것이 없어 왕복 문제가 없다 |
| 코드로 짜는 UI | 게임 UI 시스템을 같이 쓰기 / 별도 도구 | **디버그용만, Dear ImGui로.** Editor·Dev 빌드에만 있고 출시 빌드에서는 코드가 빠진다. 게임 UI에는 쓰지 않는다 | 개발용 화면은 빨리 만들고, 게임 UI와 섞이지 않는다 |
| 게임 코드와 UI 연결 | 이름으로 위젯 찾기 / 양방향 바인딩(MVVM) / 콜백 등록 | **단방향 뷰 모델 + 액션.** 게임이 `MEALKIT_VIEWMODEL`로 필드를 선언하고 매 프레임 상태 → 뷰 모델을 채운다. 버튼은 액션 이름(`pause.resume`)을 내고 `onUiAction` 한 곳에서 처리한다. 입력 위젯만 자기 필드에 값을 쓰고 `changed` 액션을 낸다. 식 언어·변환기 없음. UI는 시뮬레이션 상태를 고치지 않고 입력이나 `AppState` 변경만 만든다 | 흐름이 한 방향이라 디버깅이 쉽고, 디자이너가 고를 필드 목록이 코드에서 자동으로 나온다 |
| UI 배치 | 절대 좌표 / 앵커 / flexbox | **Penpot의 Flex·Grid 레이아웃 그대로**, 레이아웃 밖 자식은 Constraints(앵커). 엔진은 Penpot과 같은 계산을 하고 픽셀 비교로 확인한다. 좌표는 기준 보드(1920×1080)의 논리 단위, 배율은 화면 크기 × 설정의 UI 배율 | 디자이너가 보는 그대로 나오고, 해상도·UI 배율이 저절로 해결된다 |
| UI 모양, 상태, 테마 | 이미지(9-slice) / 코드에 색 상수 / 애니메이션 도구 | **도형은 셰이더 SDF로 직접 그림**(채우기·테두리·둥근 정도·그림자). 그 밖의 벡터·아이콘은 PNG로 구워 아틀라스에(WIC로 읽음). 상태는 컴포넌트 variants + 전환 시간·이징. 색·숫자는 Penpot 디자인 토큰 = 테마 토큰 | 단순한 패널은 이미지가 필요 없고, 숫자는 Penpot에서 고치면 바로 반영된다 |
| 글자와 글꼴 | 미리 굽는 아틀라스 / 실행 중 굽기 / 한 상자에 스타일 하나 | **여러 스타일 글자**(문단 → 스타일 구간)를 처음부터 지원. 글꼴은 **`stb_truetype`로 쓰는 글자만 실행 중에 SDF로 굽는 캐시**. 로컬라이제이션 문자열은 구간을 번호 태그(`<1>…</1>`)로 표시 | 어떤 글자(드문 한글, 닉네임)도 보이고, 크기마다 다시 굽지 않는다. 나중에 스타일 구간을 넣으면 형식을 다시 고쳐야 한다 |
| 메뉴 조작 (게임패드·키보드) | 수동 이동 표 / 엔진별 내비게이션 | **위젯 id로 포커스를 기억하고, 방향 입력이면 그 방향에서 가장 가까운 위젯으로.** 필요한 곳만 플러그인에서 "다음 포커스" 지정. 확인·뒤로·이동은 입력 액션 | 위젯마다 이웃을 적지 않는다 |
| 그리기 | 렌더 파이프라인 여러 개 | **포워드 렌더러 하나 + `DrawList`.** 게임은 인스턴스만 넣는다 | DX12 전용, 내장 그래픽 예산 |
| 네트워크 | RPC / 동기화 변수 / 스냅샷 | **입력 락스텝 하나.** 보내는 것은 8바이트 입력뿐 | 결정 기록 |
| 실패 처리 | 예외 / null / Result | **예외 안 씀.** 값을 돌려주는 함수는 `std::optional<T>`, 값이 없으면 `bool`. 실패 이유는 실패한 곳에서 로그로 남긴다. 프로그래머 실수는 `MEALKIT_ASSERT` | 실패 경로가 함수 모양에 보인다 |
| 메모리 | 아무 데서나 할당 | `sim/`은 `Pool`과 고정 배열만, 틱 도중 할당 금지, `unordered_map` 금지(조회는 Pool id로). 화면 쪽은 **매 프레임 `clear()`로 재사용하는 컨테이너**(지금 `DrawList` 방식) | 할당 스파이크·순서 문제가 없다. 별도 할당기를 만들지 않는다 |

## 강제하는 방법

1. **엔진이 주는 도구가 곧 답이다.** `Pool<T>`, 틱 이벤트, 틱 타이머, `GameContext`, Job System만 제공하고, 같은 일을 하는 다른 헬퍼는 만들지 않는다.
2. **`sim/` 금지 검사.** static 가변 변수, `new`/`delete`/`make_unique`, `virtual`, `co_await`, `std::thread`/`async`/`future`, `<chrono>`, CRT 삼각함수, `unordered_map`, 렌더러·플랫폼·설정 헤더.
   주석과 문자열은 빼고 검사한다. 걸리면 빌드가 실패하고 대신 쓸 것을 알려 준다("`Pool<T>`를 쓰세요").
   구현: `engine/tools/SimCheck.cpp` (`mealkit_add_game()`이 빌드 전에 실행, 오류 코드 `SIM001`~`SIM010`). 규칙을 바꾸면 이 문서와 도구를 같이 고친다.
3. **시뮬레이션 상태 타입 제한.** 필드 선언은 `f32/i32/u32/bool/Vec3/Quat/Id<T>/physics::BodyId/고정 배열`만 받고 `static_assert(std::is_trivially_copyable_v<T>)`로 확인한다.
   포인터, `std::string`, `vector`가 상태에 들어가지 않으므로 해시와 스냅샷이 항상 맞는다.
4. **실행 중 검사.** 전역 상태를 쓰면 그림자 시뮬레이션이 바로 잡고, 마지막으로 `mp_test`가 확인한다. `MEALKIT_ASSERT`는 Debug와 Editor 빌드(`MEALKIT_ASSERTS`)에서 켜진다. 실패하면 로그를 남기고, 디버거가 붙어 있으면 그 자리에서 멈춘다.
5. **템플릿·쿡북·CLAUDE.md가 같은 답을 쓴다.** 새 프로젝트는 이 구조로 시작하고, AI가 코드를 짜도 같은 답을 고른다.

## 검토했지만 바꾸지 않은 것

| 대안 | 바꾸지 않은 이유 |
|---|---|
| SoA(필드별 배열) | 물체 수천 개에서는 구조체 배열(AoS)로 틱 예산 안이고 코드가 훨씬 읽기 쉽다. 측정해서 병목이면 그 배열만 바꾼다 |
| 범용 ECS(아키타입) | 실행 중 조합이 되지만 실행 순서가 시스템 등록 순서로 숨고, 엔진이 무거워진다. 보류 표 조건 그대로 |
| 시뮬레이션 안의 C++20 코루틴(틱으로 진행) | 순서는 결정론으로 만들 수 있지만 코루틴 프레임은 해시·스냅샷할 수 없어 중간 참가·되감기가 깨진다 |
| `unordered_map`은 순회만 금지 | 검사가 어려워지고(순회 여부를 판단해야 한다) Pool id로 대부분 해결된다. 통째로 금지가 단순하다 |
| 코드로 짜는 즉시 모드 게임 UI | 프로그래머가 아니면 UI를 만들 수 없다. 즉시 모드는 디버그 UI(ImGui)에만 쓴다 |
| 엔진 에디터 안의 UI 디자이너 (UMG 방식) | 개발량이 가장 크다. Penpot이 캔버스·컴포넌트·토큰을 이미 갖고 있다 |
| Figma | 디자이너가 가장 많이 쓰지만 클라우드 전용이고 REST API 호출 제한이 빡빡하다. `.ui`가 중간 형식이라 필요하면 Figma 플러그인만 따로 만든다 |
| Yoga·Clay 같은 레이아웃 라이브러리 | Penpot 레이아웃과 똑같이 계산해야 하므로, 다른 라이브러리의 규칙을 맞추는 것보다 Penpot 기준으로 직접 만드는 편이 확실하다 |
| RmlUi, Noesis, Gameface, Rive | 텍스트 마크업이라 시각 편집이 아니거나(RmlUi), 상용·무거운 런타임이다 |
| 미리 굽는 완성형 2,350자 글꼴 | 드문 한글과 다른 언어 닉네임을 못 보여 준다 |

## 감수하는 것

- 컴포넌트를 실행 중에 붙였다 뗄 수 없다. 처리하는 시스템이 다른 종류마다 배열 하나와 시스템 하나가 필요하다. 종류가 수백 개가 되면 ECS 보류를 다시 본다.
- `Pool`은 최대 개수를 미리 정해야 한다.
- "아무 데서나 접근"하는 편의가 없다. 함수 인자가 길어지는 대가를 치른다.
- 시뮬레이션 안 직접 호출은 호출하는 쪽이 받는 쪽을 알아야 한다. 대신 흐름이 숨지 않는다.
- 게임 UI는 Penpot에 의존한다(오픈소스라 직접 띄울 수 있어 위험은 작다). Penpot 레이아웃·글자 계산을 따라가야 하고, 플러그인(TypeScript)과 Node.js 개발 도구를 유지해야 한다.
